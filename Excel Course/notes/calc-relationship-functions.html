DAX Relationship Functions

Your data model's relationships decide which table can filter which. Relationship functions in DAX either walk those links (RELATED, RELATEDTABLE) or rewire them on the fly (CROSSFILTER, USERELATIONSHIP) — the key to calculating the median salary of an associated skill.

What Are DAX Relationship Functions?

Four tools for navigating and rewiring the links in your data model.

BIG PICTURE
FunctionJobDirection it walksReturns
RELATED(Col)Pull a column value across a linkMany → OneA single value
RELATEDTABLE(Tbl)Pull the related rows across a linkOne → ManyA table
CROSSFILTER(A, B, dir)Flip the filter arrow at query timeBoth directionsNew filter context
USERELATIONSHIP(A, B)Switch on an inactive relationshipActivate dormant linkNew filter context

Why you need them: aggregates like MEDIAN answer "what's the number?" — but only inside the filter context the model lets you build. When the arrows won't let a table (Job Skills) filter another (Jobs), relationship functions are the fix.

Median Salary Skills := CALCULATE([Median Salary], CROSSFILTER(JobSkills[Job ID], Jobs[Job ID], BOTH))

The Problem — One-Way Filtering

Every skill shows the SAME median salary. The arrow is pointing the wrong way.

The symptom: put Skill on rows and [Median Salary] on values, and every skill shows the same 105,000 — the median of the whole dataset. Excel even warns "relationships between tables may be needed", and Auto Detect finds "no new relationships". The data is fine; the filter direction is not.

The fix in one line: we can't flip the arrow in Excel's UI (Power BI lets you), so we flip it inside a DAX measure with CROSSFILTER — coming in section 6.

1

Diagnose it in Diagram View

Open Power Pivot ▸ Manage ▸ Diagram View. The arrow points from Jobs to JobSkills, meaning salary values in Jobs can only flow toward skills — never the other way. That's why the skill pivot couldn't filter the salaries.

Excel limitation: you can double-click a relationship and change direction per-relationship, but you cannot switch a filter to both the way Power BI's "cross filter direction: Both" option does. DAX is the only escape hatch — and that's exactly why CROSSFILTER exists.

RELATED — Pull a Value from the One Side

From a row in the many table, grab a column from its related one-table row.

MANY → ONE
RELATED(Jobs[Salary]) → 115,000
Job IDSkillSalary via RELATED
1SQL115,000
1Excel115,000
2Excel75,000
4Python95,000
5Python960,000
8Python140,000

How to use it: RELATED needs row context — a calculated column in the many table, or inside an iterator like SUMX. Each JobSkills row finds its single matching Jobs row and copies the salary across. Great for "flattening" a star schema onto a child table.

Classic trap: if the relationship points the wrong way or you call RELATED without row context, you get a DAX error ("RELATED must be used in row context" / the column isn't related). Check Diagram View first.

RELATEDTABLE — Pull Rows from the Many Side

From a row in the one table, grab every matching row in the many table.

ONE → MANY
Skills Per Job := COUNTROWS(RELATEDTABLE(JobSkills)) → 2
Job IDJob TitleSkills Per Job
1Data Analyst2
2Data Analyst2
3Data Analyst1
4Data Scientist2
7Business Analyst1

The mirror image of RELATED: RELATED walks many→one and returns a value; RELATEDTABLE walks one→many and returns a table. A table can't be shown on its own — always wrap it in an aggregate like COUNTROWS, SUMX or MAX.

Memory aid: RELATED = "get the one" (singular value), RELATEDTABLE = "get the many" (plural rows). Same relationship, opposite directions, one returns a value and the other a table.

CROSSFILTER — Flip the Arrow in DAX

The course's star function: change filter direction just for one measure.

THE FIX
CROSSFILTER(Column1, Column2, Direction)
DirectionMeaningUse it when…
BOTHFilters flow either wayYou want the skill to filter the salary (our fix)
ONEWAYDefault single directionYou want to confirm the model's existing behavior
NONENo filtering at allYou want to break a link for this measure
LEFT / RIGHTForce a specific one-way directionYou need the arrow pointing a particular way

Remember from the course: CROSSFILTER is a filter function, so it only works inside a filter-modifying formula you already know — CALCULATE. Standalone, it does nothing.

Median Salary Skills := CALCULATE([Median Salary], CROSSFILTER(JobSkills[Job ID], Jobs[Job ID], BOTH))

Real stumble from the lesson: the formula errored with a missing ) — close every parenthesis. And a measure named Median Salary already lived in another table, so Excel rejected the duplicate and the measure was renamed Median Salary Skills.

CROSSFILTER in Action — the Skill Salary Fix

Before vs after: each skill finally gets its own associated median salary.

1

Create the measure in the Job Skills table

Power Pivot ▸ Add Measure. New Table = JobSkills, name it Median Salary Skills. Start with CALCULATE and reference the explicit [Median Salary] measure we already built in Jobs.

2

Add the CROSSFILTER argument

Second argument: CROSSFILTER(JobSkills[Job ID], Jobs[Job ID], BOTH). The two columns are the link between the tables; BOTH opens the arrow both ways just for this measure.

3

Format & drop into the pivot

Format as currency, 0 decimals. Replace the flat Median Salary with Median Salary Skills on values — now every skill shows its own associated median, no longer the 105,000 whole-dataset value.

USERELATIONSHIP — Wake a Dormant Relationship

When two tables share two links, only one is active. Activate the other just for a measure.

INACTIVE LINKS
Order IDOrder DateShip DateAmount
101Jan 5Jan 91200
102Jan 8Jan 12300
103Jan 10Jan 1060
104Feb 2Feb 5250
105Feb 4Jan 281200
Orders := COUNTROWS(Orders)
Shipments := CALCULATE(COUNTROWS(Orders), USERELATIONSHIP(Orders[Ship Date], DimDate[Date]))
MonthOrders (order date)Shipments (ship date)
Jan33
Feb21

Why it matters: the same pair of tables can hold several relationships (order date, ship date, due date…). Only one is active at a time. USERELATIONSHIP(Orders[Ship Date], DimDate[Date]) temporarily swaps which link the measure filters on — without touching the model.

Rules: used inside CALCULATE, and the two columns must already exist as a (usually inactive) relationship in the model. It activates the link for this calculation only — the rest of the model keeps its default link.

Filter Direction vs Filter Type

CROSSFILTER is a filter modifier — it changes the arrow, not the values you filter on.

EASY TO MIX UP
ToolWhat it changesExample
CALCULATE(expr, col=value)Adds a direct filter on a column's valuesCALCULATE([Median Salary], Jobs[Country]="United States")
CROSSFILTER(A, B, dir)Changes which relationship arrows can flowCALCULATE([Median Salary], CROSSFILTER(JobSkills[Job ID], Jobs[Job ID], BOTH))
USERELATIONSHIP(A, B)Swaps to a different (inactive) relationshipCALCULATE(COUNTROWS(Orders), USERELATIONSHIP(Orders[Ship Date], DimDate[Date]))

The mental model: CALCULATE is the steering wheel — it always drives filters. CROSSFILTER and USERELATIONSHIP are the gears inside it that choose which road (relationship) the filters may travel, while the column condition picks which values to keep.

Practice Problem — Skill Likelihood

% of job postings that mention each skill — and the one-way arrow does us a favour.

FROM THE COURSE
Skill Likelihood := DIVIDE([Skill Count], [Job Count])
SkillSkill CountJob Count (stays 8!)Skill Likelihood
SQL3837.5%
Excel4850.0%
Tableau1812.5%
Python4850.0%
1

Spot the trick

Because the arrow still flows Jobs → JobSkills, the skills can't filter [Job Count] — so the denominator stays the grand total (8 in our mini model; 32,672 rows in the real dataset). That's exactly the denominator we want.

2

Guard with DIVIDE

Use DIVIDE, not / — it returns blank instead of an error if [Job Count] is ever 0. Format the result as a percentage.

Real numbers from the project: for Data Analyst in the United States (8,339 jobs), SQL scored ~53% and Excel ~41% — "SQL and Excel are the skills you should be learning." A percentage beats a raw count when explaining why a skill matters.

Common Pitfalls

The mistakes that made the course run into "issues with the data model".

WATCH OUT
PitfallWhat happensFix
RELATED vs RELATEDTABLE mix-upValue where a table belongs (or vice versa)RELATED = single value; RELATEDTABLE = table → wrap in COUNTROWS/SUMX
CROSSFILTER outside CALCULATENothing happens — it's a filter functionAlways nest inside CALCULATE(expr, CROSSFILTER(…))
Forgotten closing parenthesisFormula error with the little red XCount the brackets before clicking OK
Duplicate measure name in another table"A column with the name X already exists"Rename it (e.g. Median Salary Skills)
BOTH on an ambiguous many-to-manyUnexpected/duplicated resultsKeep direction explicit (BOTH / ONEWAY / LEFT / RIGHT)
RELATED with no row contextDAX error — must be in a calculated column or iteratorUse it in a column or inside SUMX/MAXX/…

The biggest one of all: forgetting that Excel can't flip a relationship to both directions in the UI — so a "stagnant" number in a pivot (every skill = 105,000) isn't broken data, it's a one-way arrow. Diagnose in Diagram View before rewriting formulas.

Copy-paste ready relationship functions (written as measures with :=).
