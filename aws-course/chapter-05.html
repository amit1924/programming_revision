IAM — Identity & Access Management

So far you've built servers (EC2) and databases (RDS). But who is allowed to touch them? This chapter is about security identity: users, groups, roles, and the JSON policies that decide who can do what. IAM is the single most tested AWS topic — and the thing your company would be hacked without.

Why IAM?

Continue the story of www.amit.com. You now own a VPC (office), an EC2 server (computer), and an RDS database (record room). You hire a team:

  • Amit — the owner, needs full access.
  • Rahul — a developer, needs EC2 + code access but not the billing.
  • Maria — an analyst, needs to read the database reports but never delete them.
The company ID-card problem
      Without IAM            With IAM
   ┌─────────────────┐    ┌─────────────────┐
   │  Everyone has   │    │  Amit  → full    │
   │  the MASTER KEY │    │  Rahul → dev     │
   │  to the vault   │    │  Maria → read    │
   │  😱 total chaos │    │  ✅ controlled  │
   └─────────────────┘    └─────────────────┘
🪪
IAM = the ID-card system for your AWS account

IAM (Identity & Access Management) is a free AWS service that lets you create identities (who) and decide what they can do (access). Every action in AWS — every ec2 run-instances, every rds describe-db-instances you ran in earlier chapters — runs as some identity, and IAM decides if it's allowed.

Why this chapter matters more than the rest The #1 cause of hacked AWS accounts is bad IAM: someone leaves a master key lying around. Learn IAM once, and you'll automatically secure every service you've already built. On the exam, IAM is everywhere.

The 4 Building Blocks of IAM

Everything in IAM is built from just four ideas. Master these and the whole service makes sense.

User

A person (or app) that needs access. Has a name, an optional password, and optional access keys for programs. Rahul is a user.

Group

A collection of users that share permissions. You attach policies to the group, and every member inherits them. developers is a group.

Role

A temporary identity for machines (EC2, Lambda) or federated users. It's assumed, not logged into. Your EC2 server can assume a role.

Policy

The permission document — a JSON file that says who can do what on which resource. This is the heart; the next section dives in.

How the pieces fit
       Policies (the rules)  ──attach──►  Groups  ◄──join──  Users
           │                                   ▲                  ▲
           │                                   │                  │
           └─────────────attach────────────────┘                  │
                                                                  │
       Roles  ◄──assume──  EC2 / Lambda / apps          │
                                                                   
       your company: users have IDs, groups share rules, roles drive machines

Policies — The Heart of IAM

A policy is just JSON. It says: "allow or deny these actions on these resources." Read a policy top to bottom, and you know exactly what it permits.

An IAM policy document (JSON) 
// Give read access to any S3 bucket
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:ListAllMyBuckets",
      "Resource": "*"
    }
  ]
}
KeyWhat it means
EffectAllow or Deny. If a request matches any Deny, it's denied — even if an Allow matches too.
ActionThe API call(s), written as service:operation — e.g. s3:GetObject, ec2:RunInstances, or * for everything.
ResourceWhich thing the action applies to, written as an ARN (see below). * = all.
VersionPolicy language version. Always 2012-10-17 — just leave it.
🔖
ARN — the address of every AWS resource

An ARN (Amazon Resource Name) is the universal ID for anything in AWS. They look like arn:aws:s3:::my-bucket or arn:aws:ec2:us-east-1:123456789012:instance/i-abc. Policies use ARNs to point at exactly which resource you're allowed to touch.

The evaluation rule (memorize this) Every request is checked against all policies. AWS evaluates them as: explicit Deny → Allow → default Deny. Explicit Deny always wins, everything not explicitly allowed is denied by default. AWS = "default to locked."

Who Am I? Root User vs IAM User

The very first identity in every AWS account is the root user — the account you signed up with. It's like being the building owner: you can do literally everything.

Root vs IAM user
   ROOT USER (the account itself)          IAM USERS (the people/machines)
   ┌─────────────────────────────┐    ┌──────────────────────────────┐
   │ full access to everything   │    │ rahul    → limited per policy │
   │ can delete the whole AWS    │    │ maria    → read-only reports  │
   │ account 😱                   │    │ billing  → maybe not even    │
   │ only used to make IAM users │    │ safest way to do real work   │
   └─────────────────────────────┘    └──────────────────────────────┘
The #1 security rule in AWS Never use the root user for daily work. Create an IAM user with just the permissions you need, and use that. On Floci, the account is emulated — you'll see the emulator's own "root" identity when you check sts get-caller-identity.
Who does what? The IAM triangle Authentication = who are you? (username/password or access keys). Authorization = what may you do? (policies). Identity = who do your actions appear as in logs? (your user/role ARN). IAM handles all three.

Hands-On: Build Your First IAM User

Enough theory. Let's actually create Rahul's identity on Floci, command by command — exactly the way you'd do it on real AWS.

1

Who Am I Right Now?

Check the identity behind your CLI
Command
awslocal sts get-caller-identity
🕵️
What did this just do?

STS (Security Token Service) answers one question: "who am I?" It returns the identity behind your access keys. On Floci you're the emulated root user (...:root). On real AWS this would show your account number and role/user ARN. Run this before any other IAM work — it tells you who you're acting as.

Run it live
Breaking down the command
sts get-caller-identity
The service + action: "tell me who is making this call."
UserId
A unique ID for the identity making the call.
Account
Your 12-digit AWS account number.
Arn
The full identity address — here the root user of the account.
2

Create a User — Welcome Rahul

Make an identity with no permissions yet
Command
awslocal iam create-user --user-name rahul
🧑‍💻
What did this just do?

You created an IAM user named rahul in your account. A brand-new user has zero permissions — like handing someone a blank ID card. The output gives the user a UserId and its ARN (...:user/rahul). Rahul can't do anything yet — that comes later with policies.

Run it live
Breaking down the command
iam create-user
Service + action: "create a new identity."
--user-name rahul
The identity's name — must be unique in your account.
arn:aws:iam::000000000000:user/rahul
Rahul's ARN — his permanent address in AWS. Policies and logs reference it.
A new user = no access By default a fresh IAM user can't do anything — not even list buckets. That's the security model working. Permissions are added only when you attach a policy. This "least privilege by default" is exactly what you want.
3

Give Rahul a Key Pair — For Programs

How a script logs in as a user
Command
awslocal iam create-access-key --user-name rahul
🗝️
What is an access key?

People log in to the AWS console with a username + password. But your code (AWS CLI, SDKs) can't type a password — it uses an access key instead: an AccessKeyId (like a login) and a SecretAccessKey (like a password). Note it's for the rahul user, not root — good practice.

Run it live
Breaking down the command
iam create-access-key
Generates a programmatic login for a user.
--user-name rahul
Which user the key belongs to.
AccessKeyId
The public half — identifies who you are.
SecretAccessKey
The private half — proves it's you. Shown once only. Never share it.
The biggest mistake beginners make The SecretAccessKey is printed only once at creation. If you lose it, you must generate a new key. And never commit it to GitHub — that's how AWS accounts get hacked in hours. (Rotate keys periodically; delete old ones with delete-access-key.)
4

Group Rahul with the Developers

Permissions once, shared by many
Commands
awslocal iam create-group --group-name developers
awslocal iam add-user-to-group --group-name developers --user-name rahul
👥
Why groups?

Instead of giving every developer the same permission one-by-one (and updating them one-by-one forever), you make a developers group, attach the permissions to the group, and add users to it. New dev joins → add to group → done. Permissions update once → everyone gets it. This is how real companies manage teams.

Run it live
Breaking down the commands
iam create-group --group-name developers
Creates the team container.
iam add-user-to-group --group-name developers --user-name rahul
Adds Rahul as a member of the team.
iam get-group
Lists who's in a group — your verification tool.
The rule of thumb Put people in groups, attach policies to groups, never attach policies directly to users. Groups are the standard pattern for humans. Roles (next step) are the standard pattern for machines.
5

Attach a Policy — Rahul Can Now Read S3

The moment permissions actually exist
Command
awslocal iam attach-user-policy --user-name rahul --policy-arn arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess
📜
AWS managed policies — ready-made permissions

Instead of writing JSON by hand, AWS ships hundreds of managed policies. AmazonS3ReadOnlyAccess is one — it already contains the JSON that allows every S3 read action (s3:GetObject, s3:ListBucket, ...) and denies nothing else. You just attach it by its ARN. You'll find them all under arn:aws:iam::aws:policy/....

Run it live
Breaking down the command
iam attach-user-policy
Attaches a policy document to a user.
--user-name rahul
Who receives the permission.
--policy-arn arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess
The ARN of the ready-made policy to attach.
list-attached-user-policies
Verify — shows which policies a user has.
What just happened
   AmazonS3ReadOnlyAccess (policy)
        │  attach
        ▼
   rahul (user)  ── member of ──►  developers (group)
        │
        ▼
   ✅ can:  s3:GetObject, s3:ListBucket, s3:ListAllMyBuckets ...
   ❌ cannot: ec2:* , rds:* , iam:* , s3:PutObject ...
6

Roles — Give Permissions to Machines

Never put keys in code. Let EC2 assume a role instead.
Commands
awslocal iam create-role --role-name ec2-app-role --assume-role-policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"ec2.amazonaws.com"},"Action":"sts:AssumeRole"}]}'
awslocal iam attach-role-policy --role-name ec2-app-role --policy-arn arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess
🎭
Why roles instead of access keys for machines?

You could create a user, make an access key, and hardcode it into your EC2 server's code. Bad idea — the secret lives in code and gets stolen. Instead, AWS roles let a service assume a temporary identity: your EC2 instance gets short-lived credentials automatically, no secrets stored anywhere. The trust policy says "who may wear this hat" (here: EC2), and the permission policy (attached after) says "what the hat may do."

Run it live
Breaking down the commands
iam create-role --role-name ec2-app-role
Creates a machine identity called ec2-app-role.
--assume-role-policy-document '{...}'
The trust policy — JSON that declares who may assume this role (here: the EC2 service).
"Principal": {"Service": "ec2.amazonaws.com"}
The trust target — the EC2 service is allowed to take this hat.
"Action": "sts:AssumeRole"
The action of switching into the role.
iam attach-role-policy ... AmazonS3ReadOnlyAccess
The permission policy — what the role may do once assumed.
Role flow
   EC2 instance ──assume──►  ec2-app-role
                                     │  (trust: ec2.amazonaws.com)
                                     ▼
                           AmazonS3ReadOnlyAccess (permission policy)
                                     │
                                     ▼
                             ✅ reads S3 buckets
                             ❌ no keys, no secrets in code
7

Clean Up — Delete What You Made

Tidy account, safe account
Commands
awslocal iam delete-access-key --user-name rahul --access-key-id AKIAR3UEMIZ4OMH97RRY
awslocal iam detach-user-policy --user-name rahul --policy-arn arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess
awslocal iam remove-user-from-group --group-name developers --user-name rahul
awslocal iam delete-user --user-name rahul
awslocal iam delete-group --group-name developers
awslocal iam detach-role-policy --role-name ec2-app-role --policy-arn arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess
awslocal iam delete-role --role-name ec2-app-role
🧹
Deleting needs the right order

IAM enforces order: you must detach policies and remove users from groups before you can delete them. Same habit you learned in Chapters 3 & 4: create → use → delete. Real AWS is pay-as-you-go, and an unused account with old keys is a security risk — always tidy up.

Run it live
Breaking down the cleanup
delete-access-key / detach-user-policy / remove-user-from-group
Remove the user's credentials, permissions, and group membership first.
delete-user
Only now can the user be deleted.
delete-group / delete-role
Delete the group and role once nothing references them.
Complete IAM flow — copy & paste 
# 0. Who am I?
awslocal sts get-caller-identity

# 1. Create a user
awslocal iam create-user --user-name rahul

# 2. Programmatic access key (secret shown once!)
awslocal iam create-access-key --user-name rahul

# 3. Put the user in a group
awslocal iam create-group --group-name developers
awslocal iam add-user-to-group --group-name developers --user-name rahul

# 4. Give permission via a managed policy
awslocal iam attach-user-policy --user-name rahul --policy-arn arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess

# 5. Roles for machines (no keys in code!)
awslocal iam create-role --role-name ec2-app-role --assume-role-policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"ec2.amazonaws.com"},"Action":"sts:AssumeRole"}]}'
awslocal iam attach-role-policy --role-name ec2-app-role --policy-arn arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess

# 6. Clean up (detach/remove before delete)
awslocal iam detach-user-policy --user-name rahul --policy-arn arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess
awslocal iam remove-user-from-group --group-name developers --user-name rahul
awslocal iam delete-user --user-name rahul
awslocal iam delete-group --group-name developers
awslocal iam detach-role-policy --role-name ec2-app-role --policy-arn arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess
awslocal iam delete-role --role-name ec2-app-role
Final mental model — IAM in one picture
IAM = the building's ID-card + lock system.

   User      = a person (or app)        →  rahul
   Group     = a team sharing rules       →  developers
   Policy    = the list of allowed actions  →  s3 read-only
   Role      = a hat machines can wear    →  ec2-app-role
   Access key= username+password for code
   ARN       = the address of any identity/resource

   Remember: default deny. Explicit deny beats allow.
   Never use root for daily work. Put humans in groups, give machines roles.
Honest note — what Floci does & doesn't enforce I tested this live. Floci fully supports IAM identity management: users, groups, roles, policies, access keys, and sts get-caller-identity all work exactly as shown. But like real AWS's free local emulators, Floci does not enforce permissions — I attached only AmazonS3ReadOnlyAccess to a user and that user could still create EC2 instances and S3 buckets. So practice the commands here freely (they're 100% accurate), but understand that permission enforcement only happens on real AWS. On real AWS, an S3-read-only user would genuinely be blocked from everything else.

Security Best Practices — IAM Edition

The official AWS "well-architected" advice for IAM, boiled down to what actually matters:

PracticeWhy
Never use the root user dailyRoot can delete the whole account. Create IAM users for everything.
Enable MFA on the root userA second factor (phone/app) stops password thieves from owning your account.
Least privilegeGive the minimum permission needed. Read-only where possible. You can always grant more later.
Use groups, not per-user policiesOne change updates the whole team. Simpler to audit.
Use roles for machinesEC2/Lambda assume roles. Never hardcode access keys in code or config.
Rotate & delete old access keysStolen keys are the #1 breach vector. Regular rotation limits the damage.
Monitor with CloudTrailLog every API call so you can see who did what (Chapter 6 territory).
Shared responsibility, again (from Chapter 1) AWS secures the cloud of the platform; you secure what's in it — and IAM is how you do that. Even a perfect VPC, EC2, and RDS setup is worthless if one leaked access key unlocks it all. IAM is your front door.

Glossary — Chapter 5

IAM

Identity & Access Management — AWS's free service for users, groups, roles, and policies.

User

An identity for a person or application. Has login credentials and optional access keys.

Group

A collection of users that share the same permissions.

Role

A temporary identity that services (EC2, Lambda) can assume — no stored secrets.

Policy

A JSON document defining allowed/denied actions and resources.

Access key

AccessKeyId + SecretAccessKey used by code to authenticate (shown once).

ARN

Amazon Resource Name — the unique address of any AWS resource or identity.

STS

Security Token Service — sts get-caller-identity answers "who am I?".

Root user

The account owner with unlimited access. Never use it for daily work.

Least privilege

Give only the minimum permissions needed — the core IAM security principle.

MFA

Multi-factor authentication — a second verification step that blocks stolen passwords.

Trust policy

The part of a role that declares who is allowed to assume it.
