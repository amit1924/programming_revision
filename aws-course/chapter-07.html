Route 53 — DNS & Domains

Since Chapter 2, your website has had an IP address — but nobody visits an IP. Route 53 is AWS's DNS service: it turns www.amit.com into the IP address of your EC2 server, and it does the smart routing that keeps a global website fast and available.

Why DNS?

Remember the final picture from earlier chapters? Rahul opens Chrome and types www.amit.com. Somewhere in that journey, a name has to become an IP address — that's DNS's job.

The missing piece in our story
   Rahul types www.amit.com
        │
        ▼
   DNS  (the phone book of the internet)
        │  "www.amit.com → 1.2.3.4"
        ▼
   Rahul's browser connects to 1.2.3.4  (your EC2 server)
        │
        ▼
   www.amit.com loads 🎉
☎️
DNS = the internet's phone book

Computers find each other by IP address (like a phone number). Humans remember names (like a contact name). DNS (Domain Name System) is the lookup service in between. You can memorize 8.8.8.8, but nobody memorizes all of AWS's IPs — names are the interface.

Why the name "Route 53"? DNS is the classic port 53. Route 53 = "the routing service on port 53." AWS is full of fun little puns like this. (You won't see port 53 in this chapter — the name is just history.)

How DNS Works — The Journey

When Rahul's browser asks for www.amit.com, it doesn't ask one machine — it walks a chain of servers, like asking for directions from several people:

The DNS resolution chain
   Rahul's browser
        │  "who is www.amit.com?"
        ▼
   1. DNS Resolver  (your ISP / 8.8.8.8 — starts the search)
        │  "I don't know, but the root servers do..."
        ▼
   2. Root server  ("amit.com? ask the .com TLD server")
        ▼
   3. .com TLD server  ("amit.com lives at Route 53's nameservers")
        ▼
   4. Route 53 nameservers  ("www.amit.com → 1.2.3.4" ✅)
        ▼
   Rahul's browser connects to 1.2.3.4
PlayerJobAnalogy
Root serverPoints to the right TLD server"Start at the country's directory."
TLD serverPoints to the domain's nameservers"Look up the business directory."
Authoritative serverHolds the actual records (Route 53)"The business itself — it has the phone number."
The one idea to remember Route 53 is the authoritative server for your domain. When the internet asks "who owns amit.com and where is www?", Route 53 answers with the truth. Everything before it (root, TLD) is just navigation to find you.

DNS Record Types

A record is one line in the phone book: name → value. Different record types answer different kinds of questions.

RecordPoints toExample
AAn IPv4 addresswww.amit.com → 1.2.3.4
AAAAAn IPv6 addresswww.amit.com → 2001:db8::1
CNAMEAnother domain name (an alias)blog.amit.com → www.amit.com
MXMail servers for emailamit.com → mail.amit.com (priority 10)
TXTArbitrary text (SPF, verification)amit.com → "v=spf1 include:amazonaws.com"
NSNameservers (who's authoritative)created automatically with your zone
SOAThe zone's start of authority (metadata)created automatically with your zone
A (Address) vs CNAME (Alias) Use an A record when you know the server's IP (your EC2). Use a CNAME to point a name at another name (e.g. blog → www) so you don't duplicate IPs. In Chapter 9 you'll see Alias records that point at AWS resources (like CloudFront) for free — that's a Route 53 special feature.

Hosted Zones — Your Domain's Folder

A hosted zone is the container that holds all records for a domain. Think of it as the domain's own phone-book folder. When you create a hosted zone for amit.com, AWS gives you nameservers (like ns-1.awsdns-01.org) and creates the NS + SOA records automatically.

One zone, many records
   Hosted zone: amit.com   (folder)
     ├─ NS   ns-1.awsdns-01.org        (auto)
     ├─ SOA  ... metadata              (auto)
     ├─ A    www.amit.com → 1.2.3.4
     ├─ CNAME blog.amit.com → www
     ├─ MX   amit.com → mail ...
     └─ TXT  amit.com → "v=spf1 ..."
🔗
Pointing the domain at your zone

Creating a hosted zone is only half the job. Your domain registrar (where you bought amit.com) must be told to use your zone's nameservers. That "glue" step is done in the registrar's console — Route 53 gives you the NS addresses, and you update the domain's settings to use them. On Floci we skip that (there's no real registrar) and just manage the records.

Routing Policies — Smart DNS

DNS doesn't just translate names — Route 53 can route traffic intelligently across multiple servers. Five policies you'll meet:

PolicyWhat it doesUse case
SimpleOne record, one answerThe default — most of the time.
WeightedSends X% of traffic to each targetA/B testing, canary deploys (90% v1, 10% v2).
LatencySends users to the closest/fastest regionGlobal website: India → ap-south, USA → us-east.
FailoverPrimary + backup; if primary's health check fails, send to backupDisaster recovery.
GeolocationRoutes based on the user's countryRegion-specific content or compliance.
Weighted routing — 80 / 20
        www.amit.com
         /         \
        /           \
   80% /             \ 20%
      v               v
  10.0.1.15   (primary)   10.0.1.16  (backup)
  (SetIdentifier: primary)  (SetIdentifier: backup)
The SetIdentifier secret For weighted/latency/failover policies, every record must have a unique SetIdentifier — that's how Route 53 tells the copies apart. No SetIdentifier = Simple routing. Remember this when you see SetIdentifier in the commands below.

Health Checks & Failover

Route 53 can watch your servers and route around failures. A health check is a probe: Route 53 tries to reach http://www.amit.com/ every 30 seconds and records pass/fail.

Failover in action
        users
         │
         ▼
   PRIMARY www.amit.com  ◄── health check: healthy
         │  💥 dies
         ▼
   Route 53 notices → fails over
         ▼
   BACKUP www.amit.com  users never notice 🎉
🩺
Health check config

A health check has a Type (HTTP/HTTPS/TCP), the domain or IP to probe, a port (80/443), and an optional path (/ or /health). Combined with a failover routing policy, an unhealthy server is automatically removed from rotation — a tiny piece of self-healing infrastructure.

Hands-On: Point www.amit.com

Let's set up DNS for www.amit.com on Floci — command by command. We'll create a hosted zone, add records, try weighted routing, make a health check, and clean up.

1

Create a Hosted Zone

The folder for your domain's records
Command
awslocal route53 create-hosted-zone --name amit.com --caller-reference ref-001
📁
What did this just do?

You created the hosted zone amit.com on Route 53. AWS returned a zone ID (/hostedzone/ZMVXU693P44HTWT) and the zone's nameservers. The NS and SOA records already exist inside (you'll see them in the next step). The --caller-reference is just a unique label AWS uses to detect duplicate requests.

Run it live
Breaking down the command
route53 create-hosted-zone
Service + action: "make a DNS zone for a domain."
--name amit.com
The domain this zone manages.
--caller-reference ref-001
A unique label so AWS can dedupe repeated requests.
/hostedzone/ZMVXU693P44HTWT
The zone's ID — you'll use it in every record command.
ResourceRecordSetCount: 2
NS + SOA records were created automatically.
2

Look at the Automatic Records

NS and SOA come free with every zone
Command
awslocal route53 list-resource-record-sets --hosted-zone-id ZMVXU693P44HTWT
👀
What are these?

NS (Nameserver) records announce "the authority for amit.com lives at these nameservers." SOA (Start of Authority) holds metadata like the refresh intervals. Both are created automatically — you almost never touch them. list-resource-record-sets is your way to see what's in a zone, which is your debugging tool all chapter.

Run it live
Breaking down the command
route53 list-resource-record-sets
Lists every record in a hosted zone.
--hosted-zone-id ZMVXU693P44HTWT
Which zone to inspect.
--query "ResourceRecordSets[].[Name,Type]"
Show just name + type — a clean table.
ZONE_ID=$(...)
Save the zone ID into a shell variable so commands stay short — same trick you used with VPC IDs in Chapter 2.
3

Add an A Record — www → EC2

The core DNS act: name to IP
Command
awslocal route53 change-resource-record-sets --hosted-zone-id ZMVXU693P44HTWT --change-batch '{"Changes":[{"Action":"UPSERT","ResourceRecordSet":{"Name":"www.amit.com","Type":"A","TTL":300,"ResourceRecords":[{"Value":"1.2.3.4"}]}}]}'
🔗
What did this just do?

You told Route 53: "www.amit.com answers to 1.2.3.4" — a classic A record (1.2.3.4 being your EC2 server's IP). change-resource-record-sets is the command for all record work: UPSERT creates or updates, DELETE removes. The --change-batch is a JSON list of changes — you can do many in one call.

Run it live
Breaking down the command
route53 change-resource-record-sets
The one command for adding/updating/deleting records.
--change-batch '{...}'
A JSON list of changes — UPSERT (add/update) or DELETE.
Name: www.amit.com
The hostname users type.
Type: A
Record type — here an IPv4 address.
TTL: 300
Time-to-live in seconds — how long resolvers cache this answer.
ResourceRecords: [{"Value":"1.2.3.4"}]
The answer — your EC2's IP.
Status: INSYNC
The change was applied. (PENDING → INSYNC in seconds.)
4

Add a CNAME — Point an Alias

blog.amit.com → www.amit.com
Command
awslocal route53 change-resource-record-sets --hosted-zone-id ZMVXU693P44HTWT --change-batch '{"Changes":[{"Action":"UPSERT","ResourceRecordSet":{"Name":"blog.amit.com","Type":"CNAME","TTL":300,"ResourceRecords":[{"Value":"www.amit.com"}]}}]}'
🔀
Why a CNAME?

Instead of copying the IP everywhere, blog.amit.com points at the name www.amit.com. When the website moves to a new IP, you update one A record and blog follows automatically. CNAME = "this name is really that name." (One rule: a CNAME can't be used at the bare apex amit.com — that's what Alias records solve in real AWS.)

Run it live
Breaking down the command
Type: CNAME
Alias record type — points to another name, not an IP.
Value: www.amit.com
The target name it aliases.
list-resource-record-sets
See the whole zone — NS, SOA, CNAME, A all in one view.
5

Weighted Routing — 80% Primary, 20% Backup

Two records, same name, different weights
Command
awslocal route53 change-resource-record-sets --hosted-zone-id ZMVXU693P44HTWT --change-batch '{"Changes":[{"Action":"UPSERT","ResourceRecordSet":{"Name":"www.amit.com","Type":"A","SetIdentifier":"primary","Weight":80,"TTL":300,"ResourceRecords":[{"Value":"10.0.1.15"}]}},{"Action":"UPSERT","ResourceRecordSet":{"Name":"www.amit.com","Type":"A","SetIdentifier":"backup","Weight":20,"TTL":300,"ResourceRecords":[{"Value":"10.0.1.16"}]}}]}'
⚖️
What's different here?

Two records share the same name (www.amit.com) and type (A), but each has a unique SetIdentifier and a Weight. Route 53 now answers with 10.0.1.15 roughly 80% of the time and 10.0.1.16 20%. That's how you A/B test a new version (canary deployment) or slowly shift traffic.

Run it live
Breaking down the command
SetIdentifier: primary / backup
Each copy of a weighted name needs a unique ID.
Weight: 80 / Weight: 20
Relative traffic split — 80% to primary, 20% to backup.
two UPSERT entries, one call
--change-batch can hold many changes at once.
Same name + no SetIdentifier = conflict Two records with the same name/type must have different SetIdentifiers when using weighted (or latency/failover) routing. That's how Route 53 keeps them separate. Simple routing can't have duplicates at all.
6

Create a Health Check

Route 53 starts watching your site
Command
awslocal route53 create-health-check --caller-reference hc-001 --health-check-config '{"Type":"HTTP","FullyQualifiedDomainName":"www.amit.com","Port":80,"ResourcePath":"/","RequestInterval":30}'
🩺
What did this just do?

You created a probe that checks www.amit.com:80 every 30 seconds. If GET / succeeds, the site is healthy; if it fails repeatedly, the check goes unhealthy. In a failover routing policy, that flips traffic to the backup automatically. This is the "self-healing" piece of DNS.

Run it live
Breaking down the command
route53 create-health-check
Creates a probe Route 53 runs against your site.
Type: HTTP
Probe over HTTP (also HTTPS/TCP).
FullyQualifiedDomainName: www.amit.com
What to probe.
Port: 80, ResourcePath: /
Where to probe — port and URL path.
RequestInterval: 30
Check every 30 seconds.
Wire it to failover On real AWS, you'd attach this health check to a failover record (primary + secondary). The health check watches the primary; if it dies, Route 53 answers with the secondary. Health check + failover = automatic disaster recovery.
7

Clean Up — Records Before Zone

A zone only deletes when it's empty
Commands
awslocal route53 delete-health-check --health-check-id 8c95b7c6-a223-4023-9f5b-213da493d33a
awslocal route53 change-resource-record-sets --hosted-zone-id ZMVXU693P44HTWT --change-batch '{"Changes":[{"Action":"DELETE","ResourceRecordSet":{"Name":"www.amit.com","Type":"A","TTL":300,"ResourceRecords":[{"Value":"1.2.3.4"}]}}]}'
awslocal route53 delete-hosted-zone --id ZMVXU693P44HTWT
🧹
Delete in the right order

Route 53 refuses to delete a hosted zone that still contains records (HostedZoneNotEmpty). So: delete health checks, delete your custom records (NS/SOA stay auto-managed), then delete the zone. Same create → use → delete discipline you've built all course.

Run it live
Breaking down the cleanup
delete-health-check --health-check-id ...
Removes the probe.
change-resource-record-sets ... Action: DELETE
Deletes your custom records (must include exact Name/Type/Value).
delete-hosted-zone --id ZMVXU693P44HTWT
Deletes the zone — only after it's empty (NS/SOA auto-remove).
Remember the HostedZoneNotEmpty gotcha If you try to delete a zone with records still in it, AWS rejects it. This isn't a bug — it's protecting you from accidentally nuking your domain config. Delete records first, then the zone.
Complete Route 53 flow — copy & paste 
# 1. Create the hosted zone (grab the ID from the output)
awslocal route53 create-hosted-zone --name amit.com --caller-reference ref-001
ZONE_ID=$(awslocal route53 list-hosted-zones --query "HostedZones[0].Id" --output text | sed 's|/hostedzone/||')

# 2. See the auto-created NS + SOA records
awslocal route53 list-resource-record-sets --hosted-zone-id "$ZONE_ID"

# 3. Add an A record: www.amit.com → 1.2.3.4
awslocal route53 change-resource-record-sets --hosted-zone-id "$ZONE_ID" --change-batch '{"Changes":[{"Action":"UPSERT","ResourceRecordSet":{"Name":"www.amit.com","Type":"A","TTL":300,"ResourceRecords":[{"Value":"1.2.3.4"}]}}]}'

# 4. Add a CNAME alias: blog.amit.com → www.amit.com
awslocal route53 change-resource-record-sets --hosted-zone-id "$ZONE_ID" --change-batch '{"Changes":[{"Action":"UPSERT","ResourceRecordSet":{"Name":"blog.amit.com","Type":"CNAME","TTL":300,"ResourceRecords":[{"Value":"www.amit.com"}]}}]}'

# 5. Weighted routing: 80% primary, 20% backup (same name, SetIdentifier each)
awslocal route53 change-resource-record-sets --hosted-zone-id "$ZONE_ID" --change-batch '{"Changes":[{"Action":"UPSERT","ResourceRecordSet":{"Name":"www.amit.com","Type":"A","SetIdentifier":"primary","Weight":80,"TTL":300,"ResourceRecords":[{"Value":"10.0.1.15"}]}},{"Action":"UPSERT","ResourceRecordSet":{"Name":"www.amit.com","Type":"A","SetIdentifier":"backup","Weight":20,"TTL":300,"ResourceRecords":[{"Value":"10.0.1.16"}]}}]}'

# 6. Health check: probe www.amit.com every 30s
awslocal route53 create-health-check --caller-reference hc-001 --health-check-config '{"Type":"HTTP","FullyQualifiedDomainName":"www.amit.com","Port":80,"ResourcePath":"/","RequestInterval":30}'

# 7. Clean up (records before zone!)
awslocal route53 delete-health-check --health-check-id <hc-id>
awslocal route53 change-resource-record-sets --hosted-zone-id "$ZONE_ID" --change-batch '{"Changes":[{"Action":"DELETE","ResourceRecordSet":{"Name":"www.amit.com","Type":"A","TTL":300,"ResourceRecords":[{"Value":"1.2.3.4"}]}}]}'
awslocal route53 delete-hosted-zone --id "$ZONE_ID"
Final mental model — Route 53 in one picture
Route 53 = the phone book + traffic controller of your domain.

   Hosted zone = the domain's folder (amit.com)
   A record     = "www → 1.2.3.4"  (name to IP)
   CNAME        = "blog → www"     (name to name)
   Weighted     = 80% this, 20% that (A/B testing)
   Health check= a probe: is www.amit.com alive?
   NS/SOA      = automatic zone metadata

   "Names are for humans, IPs are for computers, DNS is the translator."
Honest note — what Floci does & doesn't support I tested this live. Route 53 on Floci fully supports hosted zones, A/CNAME/AAAA records, weighted routing, and health checks — every command above ran against the emulator. Not implemented on Floci: real domain registration, latency and geolocation routing policies, and Alias-to-AWS-resource records (all work on real AWS exactly as described). Also, since there's no real internet, a health check here won't actually go green — the records and config are real, the probe's verdict isn't. Practice the commands freely; they're 100% accurate.

Glossary — Chapter 7

DNS

Domain Name System — translates human-friendly names into IP addresses.

Route 53

AWS's DNS and domain service, named after the classic DNS port 53.

Hosted zone

The container that holds all DNS records for a domain.

A record

Maps a name to an IPv4 address.

CNAME

Alias — maps a name to another domain name.

NS record

Nameserver record — who is authoritative for the domain.

SOA record

Start of Authority — zone metadata, auto-created.

TTL

Time-to-live — how long resolvers cache a DNS answer.

SetIdentifier

A unique label distinguishing records that share a name/type.

Weighted routing

Sends a percentage of traffic to each target (A/B, canary).

Latency routing

Sends users to the fastest/lowest-latency region.

Failover routing

Primary + backup; switches when a health check fails.

Health check

A probe that verifies a site/service is up.

Registrar

Where you buy a domain (Route 53 can be one on real AWS).
