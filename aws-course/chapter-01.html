Welcome & The Big Picture

Before we touch a single command, let me tell you a story — because every single thing in this course exists to solve a real problem that somebody had. If you understand the problem, the technology becomes obvious. If you don't, it's just a pile of confusing acronyms.

Close your eyes for a moment and imagine it's the year 2005. You are a developer building a website. Your website starts to get popular — thousands, then millions of users. To handle the traffic, you need servers. So you go to a computer hardware store, buy physical machines, install them in a room at your office (or a "data center"), plug in the power, configure the network, install an operating system, and then finally install your application. Congratulations — you are now also a full-time electrician, network engineer, and hardware technician.

The pain of the old world This whole process takes weeks. And then one day your startup fails or your app goes viral — and you need 10x more servers immediately. What do you do? Wait weeks again. Or maybe your app flops, and you now own a room full of expensive hardware doing nothing. This is the problem cloud computing solves.

Now imagine instead: you open a website (or run a single command), and within seconds a fully-working server is handed to you — already networked, already secured, already running an operating system. You pay only for it while you use it. When you need 10,000 more, they appear in seconds too. When you're done, you release them and stop paying.

That is the cloud. Renting someone else's computers, over the internet, on demand, paying only for what you use. Amazon, Google, and Microsoft built enormous networks of computers in massive data centers all over the world, and let anyone rent tiny slices of them. Amazon's version of this service is called AWS — Amazon Web Services.

Think of it like electricity Before the electric grid, every factory had to build and maintain its own power generator. After the grid, they just "plug in" and pay for what they use. Cloud computing does the same for computing power. You don't build a power plant; you don't build a server room. You plug in and pay per use.

What Exactly Is Cloud Computing?

Let me give you the official definition (from NIST, the U.S. standards body) and then translate it into human language — because the official one is dense but worth knowing.

The official definition "Cloud computing is a model for enabling ubiquitous, convenient, on-demand network access to a shared pool of configurable computing resources (networks, servers, storage, applications, and services) that can be rapidly provisioned and released with minimal management effort or service provider interaction."

Let's unpack the five key phrases, because each one is a promise the cloud makes:

1. On-demand network access

You get resources over the internet, when you want them — with a command or an API call, not a purchase order. No phone calls, no contracts, no waiting for shipping.

2. Shared pool of resources

Millions of customers share the same physical hardware. Your virtual server is a slice of a big machine. This sharing is what makes it cheap — the provider's machines are always busy.

3. Rapid provisioning

Resources appear in seconds or minutes, not weeks. Need 50 servers before lunch? Done. This speed is the superpower that enables modern DevOps.

4. Pay only for what you use

If you use a server for 1 hour, you pay for 1 hour. Turn it off, and the meter stops. This is called OPEX (operational expense) instead of CAPEX (capital expense).

5. Measured service

The provider meters your usage (CPU hours, gigabytes stored, requests made) and bills you precisely. You can even use that metering for your own cost controls.

6. Essentially unlimited

Want a million servers? The cloud has them. You never "run out" — you just keep scaling. Small startups now have the same hardware access as giant corporations.

On-Premises vs Cloud — The Full Comparison

This is the core trade-off that defines all cloud decisions. Let me walk you through exactly what changes when you move from running your own hardware ("on-premises") to the cloud.

Concern On-Premises (your hardware) Cloud (AWS)
Time to get a server Weeks — order, ship, rack, wire, install Seconds — run a command
Cost model CAPEX — big upfront hardware bill OPEX — small ongoing usage bill
Scaling up Buy & install more hardware (slow) Click / command — instant elasticity
Scaling down Stuck with expensive idle hardware Release resources, stop paying instantly
Hardware maintenance You — broken disks, dead power supplies AWS — invisible, handled for you
Geographic reach Limited to your buildings Data centers on every continent
Disaster recovery Build expensive backup sites yourself Replicate across regions with a few clicks
Security responsibility Physical + logical, all yours Split — AWS secures hardware, you secure your data
Getting started Months and big budget Free tier, start today
Why this matters for DevOps DevOps is all about moving fast and automating everything. You cannot automate "ordering a physical server." You can absolutely automate "creating a cloud server" — it's just an API call. That's why cloud computing and DevOps grew up together. The cloud made infrastructure programmable.

The 3 Service Models: IaaS, PaaS, SaaS

Here's a mental model I want you to keep forever. Imagine the whole "stack" of running software as a layer cake:

The full stack (top to bottom)
App/Data  ← you write this
Runtime    ← Node, Python, Java running your app
OS           ← Linux/Windows on the machine
Virtualization ← the hypervisor
Server         ← physical hardware (CPU, RAM, disk)
Network       ← cables, switches, routers
Data Center   ← power, cooling, the building

The three service models are simply different "cut points" in this cake — how much of the stack the cloud provider manages for you vs how much you manage yourself.

IaaS — Infrastructure as a Service

You rent raw hardware: virtual servers, storage, networks. You install and manage the OS, runtime, and app yourself. Max flexibility, max control.

AWS EC2 AWS S3

PaaS — Platform as a Service

You rent a managed platform. The provider handles the OS, runtime, scaling, and maintenance. You just deploy your code. Less control, way less work.

AWS Elastic Beanstalk AWS RDS

SaaS — Software as a Service

You rent a finished product. The whole app is managed for you — you just use it through a browser or API. Gmail, Slack, Microsoft 365.

Gmail Slack

OSYouProviderProvider

Data CenterProviderProviderProvider
Teacher's analogy IaaS is like renting an apartment (you bring furniture, electricity bill is yours). PaaS is like a fully-furnished rental (you just move in with your stuff). SaaS is like living in a hotel (someone else runs everything, you just enjoy the room). In this course, we mostly live in the IaaS and PaaS apartments — because learning them teaches you how the whole machine works.

Deployment Models: Public, Private, Hybrid

"Cloud" doesn't have to mean "someone else's data center." There are three ways you can run a cloud, and companies often mix them.

Public Cloud

You rent from a provider (AWS, Azure, GCP) over the public internet. Resources are shared but isolated. This is what this course teaches.

Private Cloud

You build cloud-style infrastructure on hardware you own, usually for security/compliance (banks, hospitals, governments). Same tech, your building.

Hybrid Cloud

You connect your private data center to the public cloud (via a private network like AWS Direct Connect). Sensitive data stays home; burst workloads go to the cloud.

There's also a fourth that's become the default for modern apps: multi-cloud — using several public providers at once (AWS for compute, GCP for AI, etc.). For learning, we focus 100% on public AWS, which is what this course (and most of the real world) uses.

AWS Global Infrastructure

AWS isn't one giant computer — it's a network of huge data centers scattered across the planet, organized into three nested layers you must memorize: Regions → Availability Zones (AZs) → Edge Locations.

Regions

A Region is a physical geographic area (e.g., us-east-1 = North Virginia, ap-south-1 = Mumbai, eu-west-1 = Ireland). Each Region is a completely independent set of data centers. There are ~30+ regions worldwide.

  • Independence: Regions are isolated from each other. A disaster in one Region never affects another. This is how AWS survives huge outages.
  • Latency: Put your servers close to your users. Serving India? Use ap-south-1, not us-east-1.
  • Compliance: Some data must stay in a specific country by law (GDPR, banking regulations). Region choice is often a legal requirement.
  • Pricing: Prices differ per Region. Some Regions cost more than others.

Availability Zones (AZs)

Inside each Region, AWS builds multiple Availability Zones — usually 3 or more. An AZ is one or more data centers with independent power, cooling, and networking, located close enough to talk to each other but far enough apart that a flood or fire won't take out more than one.

Why AZs are the heart of AWS reliability Real AWS engineers spread their servers across at least 2–3 AZs. If one AZ's data center catches fire, the app in the other AZs keeps running. This "design for failure" mindset is the AWS cultural principle — everything fails all the time; good architecture survives it.

Edge Locations / CDN

Edge Locations are small servers in hundreds of cities worldwide that cache copies of your content close to users (this powers CloudFront, Chapter 9). They don't run your app — they serve copies of static content super fast. We'll cover this deeply later.

ConceptWhat it isExample
Region A physical area with several data centers us-east-1 (Virginia), ap-south-1 (Mumbai)
Availability Zone A set of independent data centers inside a Region us-east-1a, us-east-1b, us-east-1c
Edge Location A caching server in a city, near users CloudFront PoPs worldwide

The Shared Responsibility Model

This is the single most important security concept in all of AWS. The exam asks about it; interviewers ask about it; real-world breaches happen because people misunderstand it.

Simply put: AWS is responsible for security OF the cloud. You are responsible for security IN the cloud.

AWS handles (of the cloud)You handle (in the cloud)
Physical data center security Your IAM users, passwords & keys
Host hardware (CPU, RAM, disks) Your data — encryption, access controls
Networking & virtualization layer Your OS patches & config (for IaaS)
Hypervisor isolation Your application code & its vulnerabilities
Power, cooling, redundancy Your firewall & security group rules
The classic misunderstanding "AWS is secure, so my data is automatically secure!" Wrong. AWS protects the building; it does not protect your data inside it. A customer's S3 bucket left public with sensitive data is the customer's fault, not AWS's. AWS is secure by design — but only you can make your account secure.

Why AWS? The Key Benefits

AWS is the oldest and largest cloud provider (launched 2006), with the most services (~200+) and the biggest market share. But "most popular" isn't the whole story — here are the six concrete benefits that matter to an engineer:

Trade capital expense for variable expense

No huge upfront hardware bills. You pay a small bill that changes with your actual usage.

Massive economies of scale

AWS buys power and hardware in bulk nobody else can match. Those savings pass to you — you rent servers cheaper than you could self-host.

Stop guessing capacity

You don't predict demand years ahead. You scale up/down instantly, paying only for what you run.

Speed and agility

New environments in minutes, not months. Developers experiment freely — create, test, destroy, repeat. This fuels the DevOps loop.

Stop spending money running data centers

No more facilities teams, hardware procurement, or weekend power-outage callouts. That time and money goes to building your product.

Go global in minutes

Deploy the same app in 30+ regions and serve the whole planet from locations near each user. Physically impossible on your own hardware.

How AWS Pricing Works

Understanding pricing helps you understand why the cloud works the way it does. Four simple principles:

  • Pay-as-you-go: Pay only for resources actually used, per second or per hour.
  • Save when you reserve: Commit to 1–3 years of usage and get up to ~70% off (Reserved Instances / Savings Plans).
  • Pay less by using more: Volume discounts on storage, data transfer, etc.
  • Free tier: New AWS accounts get a generous free allowance for 12 months to learn with.
Good news for this course You don't need any of that — we run everything against Floci, a free local AWS emulator. Every command in this course costs you $0.00 and works offline. When you're ready for the real thing, AWS's free tier + pay-as-you-go has your back.

Meet the AWS CLI — Command by Command

Everything you do in the AWS web console, you can also do from the terminal with the AWS Command Line Interface (CLI). For DevOps, the CLI is where the real work happens — because it can be scripted and automated. Below I break down every single command you'll run in this chapter: what each piece means, what it returns, and why it matters. No abstract theory — you'll run every one of these against Floci.

The universal AWS CLI pattern — memorize this 
# Pattern: aws <service> <action> [options]
aws s3 ls                     # service=s3, action=ls (list)
aws ec2 describe-instances    # service=ec2, action=describe-instances
aws lambda list-functions     # service=lambda, action=list-functions

# Against Floci, we add the endpoint flag (or use the awslocal alias):
awslocal s3 ls                # alias = aws --endpoint-url=http://localhost:4566

2

Create the awslocal Alias

The one-time setup that makes every future command shorter
Commands
aws --endpoint-url=http://localhost:4566 s3 ls

alias awslocal="aws --endpoint-url=http://localhost:4566"

awslocal s3 ls
🤔
Why do we need this?

Real AWS talks to https://aws.amazon.com. Floci talks to http://localhost:4566. The only difference is one flag: --endpoint-url=http://localhost:4566. Typing that on every command is painful — so we wrap it in a shell alias named awslocal (same convention as LocalStack). Set it once, use it forever.

aws + --endpoint-url=http://localhost:4566 ⇒ awslocal (same thing, shorter)
❌ Without the alias (every time)
aws --endpoint-url=http://localhost:4566 s3 ls
✅ With the alias
awslocal s3 ls
Run it live
Breaking down the command
aws s3 ls
The real AWS CLI listing your S3 buckets. ls = "list".
--endpoint-url=http://localhost:4566
The magic flag: "don't talk to real AWS — talk to Floci on my machine instead."
alias awslocal="..."
Tells your shell: whenever you type awslocal, replace it with the full command. It's just a typing shortcut.
Aliases are temporary in your current terminal That alias only lives in the shell where you typed it. New terminal? Gone. To keep it forever on Linux/macOS, add this line to your ~/.zshrc: alias awslocal="aws --endpoint-url=http://localhost:4566". Then every terminal has it, always. (We already added it for you in Chapter 1 setup.)

What is an S3 bucket?

S3 (Simple Storage Service) is AWS's object storage — think of it as a cloud file cabinet. A bucket is the top-level folder you create in it. mb = "make bucket" (that's the official abbreviation).

What you just made
S3 (the whole storage cloud)
 └── s3://test-bucket  ← your new bucket (a folder for files)
        └── (empty for now)
Breaking down the command
awslocal s3 mb s3://test-bucket
s3 = the service. mb = "make bucket". s3://test-bucket = the bucket's address and name. Returns make_bucket: test-bucket on success.
awslocal s3 ls
Lists every bucket in your account with its creation date. You'll see test-bucket now appear.

Who Am I? (STS)

The sanity check every AWS engineer runs constantly
Command
awslocal sts get-caller-identity
🤔
What is STS?

STS (Security Token Service) answers the question: "who am I right now, and what account will my commands affect?" Before running anything important, real engineers confirm their identity with this exact command.

Breaking down the command
sts
The service name for Security Token Service.
get-caller-identity
The action: "tell me who I am." Returns the UserId, Account, and Arn you're acting as.
Run it live
🔖
What is that "arn" thing?

An ARN (Amazon Resource Name) is the unique address of every resource in AWS. Pattern: arn:aws:service:region:account:resource. So arn:aws:iam::000000000000:root means "the root user of account 000000000000 in the IAM service." You'll see ARNs everywhere for the rest of the course — get comfortable with them now.

What does this tell us?

Lists every AWS Region worldwide, with its opt-in status. Some regions need you to explicitly enable them before using; others (like us-east-1) are available by default. It's a great way to see the whole planet of AWS data centers.

Breaking down the command
ec2
The service for Elastic Compute Cloud. Region listing lives under EC2's API because regions are a network/compute concept.
describe-regions
The action: "show me all regions." Pattern: describe-X = "show me X". (You'll see describe-vpcs, describe-instances and friends later.)
