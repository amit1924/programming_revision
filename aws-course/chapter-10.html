ECS — Run Containers in the Cloud

So far your app ran on EC2 VMs (Chapter 3). But shipping a whole OS just to run one service is heavy. Containers package just your app + its dependencies into a portable box that runs anywhere. ECS (Elastic Container Service) is AWS's service for running those containers at scale — and on Floci it actually launches real containers, so you'll see a live web server come up right on your machine.

Why Containers?

On an EC2 VM, your app sits inside a full operating system. A container is different — it's a package containing your code and everything it needs to run (runtime, libraries, config), sharing the host's OS kernel. Same app, same behavior, everywhere.

VM vs Container
   VIRTUAL MACHINE:                  CONTAINER:
   ┌───────────────┐                ┌─────────────┐
   │  your app     │                │ your app    │  ← only the app
   │  libs+binaries│                │ libs        │    + its deps
   │  GUEST OS     │  heavy         │             │  ← shares host OS
   ├───────────────┤                └─────────────┘
   │ HYPERVISOR    │                ┌─────────────┐
   └───────────────┘                │ HOST OS     │  ← one kernel
   Whole OS per app ⚠️              │ kernel      │    shared by all
                                    └─────────────┘
   slow to boot · big               tiny · boots in ms · portable
📦
Image = recipe, Container = running dish

A Docker image is a read-only file that describes your app (like a recipe or a blueprint). A container is one running instance of that image. You can run 1 container or 100 from the same image — identical every time. That's the "works on my machine" problem, solved forever.

Why do cloud teams love this? Same image runs on a laptop, a test server, and 10,000 production servers. Deployments are fast (start/stop containers instead of booting OSes), and apps are isolated — one crashing container doesn't take down its neighbors. ECS just runs these images for you in the cloud.

ECS Building Blocks

ECS (Elastic Container Service) orchestrates containers: it pulls your image, starts containers, keeps them alive, and scales them. Four words carry the whole mental model:

Cluster → Task → Container
   CLUSTER  (amit-cluster)
   ┌─────────────────────────────────────┐
   │  TASK  ──► [web container]  ← 1 instance of your app
   │  TASK  ──► [web container]  ← another copy
   │  TASK  ──► [web container]  ← more copies (scaling)
   │
   │  SERVICE watches over the tasks:
   │  "always keep exactly N running"     ← reconciliation
   └─────────────────────────────────────┘
PieceWhat it is
ClusterThe logical home for your containers — a namespace/grouping.
TaskOne unit of work: one or more containers running your app.
ContainerThe actual running process from your Docker image.
ServiceA supervisor that keeps a desired number of tasks running (scaling + self-healing).
Task definitionThe blueprint of a task — image, CPU, memory, ports (see below).
Task vs Service — say it once, own it forever run-task = "start one task, I'll handle it." create-service = "keep N tasks running forever." A service is a task plus an auto-healing manager. If a task dies, a service starts a replacement. That's the difference between a one-off job and your always-on website.

ECR — Your Image Warehouse

Your Docker images need to live somewhere ECS can pull them. That's ECR (Elastic Container Registry) — AWS's private Docker registry, the S3 of images.

🏬
Registry → repository → image

ECR hosts repositories (one per app, like amit-app). You docker build locally, docker push the image to your repository, and ECS later pulls it to start containers. Each image is tagged (e.g. latest, v1, or a git hash) so you can deploy a specific version.

The image pipeline
   docker build  (your code → image)
        │  docker tag 000000000000.dkr.ecr.us-east-1.localhost:5100/amit-app:latest
        ▼
   docker push  (image → ECR repository)
        │
        ▼
   ECS pulls it  (repository → running container)
Authentication Real AWS requires a login token to push (ecr get-login-password + docker login). On Floci the registry on port 5100 is open, so you can push straight away — convenient for learning, just know the real-world login step exists.

Fargate vs EC2 Launch

ECS can run your tasks on two kinds of infrastructure — this is the "where does the container physically run" question.

Fargate (serverless)EC2 launch type
Who manages servers?AWS — no servers to touch at allYou provision & manage EC2 instances
PricingPay per task (vCPU + memory used)Pay per EC2 instance (fixed)
ScalingAutomatic, fastYou must add/remove instances
Good forMost apps — the modern defaultLarge workloads / need control / GPUs
You pick by adding one flag Fargate is the default choice for beginners — --launch-type FARGATE. No instances, no autoscaling groups to babysit. The recipe here stays identical if you later switch to EC2 launch type.

Task Definitions — The Blueprint

Before ECS runs anything, it needs the task definition: a JSON-ish description of your task. Think of it as the "deployment config" — a versioned file you register and reference.

📋
What a task definition contains

Image (which container to run), CPU & memory (how much power each task gets), network mode (awsvpc = each task gets its own elastic network interface), port mappings (which container port is exposed), and optionally env vars, logging, and volumes. Every revision is versioned — amit-web:1, amit-web:2 — so you can roll back by pointing at an older revision.

Anatomy of a task definition
   family       = amit-web          (your app's name)
   networkMode  = awsvpc           (each task gets its own ENI)
   cpu          = 256              (¼ of a vCPU)
   memory       = 512              (MB)
   containerDefinitions = [
      { name: "web",
        image: "…/amit-app:latest",   ← from ECR
        portMappings: [{ containerPort: 3000 }] }
   ]
   ──────────────────────────────────────
   amit-web:1  = first revision · amit-web:2 = second
Why versioned? A task definition is immutable — you never edit revision 1, you register a new revision 2 and switch the service over. That gives you a perfect audit trail and instant rollback: point the service back at amit-web:1 and you're on the old version.

Services & Scaling

A service turns a task definition into an always-on workload with a desired count — the number of copies you want running.

Desired count = reconciliation
   desired count = 3          (what you WANT running)
   ─────────────────────────────────────────────
   a task crashes → ECS sees 2 running → starts a 3rd 🔁
   you set count to 5   → ECS starts 2 more     🔺 scale up
   you set count to 1   → ECS stops 4           🔻 scale down

   ECS constantly reconciles the real state toward
   your desired state. That self-healing is the whole
   point of a Service.
🚦
Traffic in front of a service

In production you put a load balancer (ALB) in front of a service: the ALB spreads requests across all running tasks and takes tasks in/out of rotation as they start and stop. On Floci the ALB integration isn't wired up, so we focus on the core mechanics — which all work live.

Scaling is just changing the number With a service, scaling = changing desiredCount (update-service --desired-count 5). ECS does the rest. On real AWS you can even set Application Auto Scaling so the count changes automatically with CPU/load (Chapter 6's CloudWatch metrics feed it).

Hands-On: Deploy the amit.com Web Tier with ECS

We'll containerize and deploy the www.amit.com web tier — and because Floci runs real containers, you'll see an actual web server come up. Command by command.

1

Create the Cluster

The logical home for all your tasks
Command
awslocal ecs create-cluster --cluster-name amit-cluster
🏠
What did this just do?

You created a cluster — the container "neighborhood" for your app. It starts empty (0 running tasks, 0 services). Think of it as the folder that will hold all of amit.com's containers. One cluster can host many services.

Run it live
Breaking down the command
ecs create-cluster
Creates the container home for your tasks.
--cluster-name amit-cluster
Your cluster's name — used in every later command.
status: ACTIVE
Ready to accept tasks and services.
One cluster per app (or env) Teams often make amit-dev-cluster and amit-prod-cluster to keep environments isolated. It's just a logical grouping — cheap and useful.
2

Create the ECR Repo & Push Your Image

Get your app's Docker image into the cloud registry
Commands
awslocal ecr create-repository --repository-name amit-app
docker build -t amit-app .
docker tag amit-app 000000000000.dkr.ecr.us-east-1.localhost:5100/amit-app:latest
docker push 000000000000.dkr.ecr.us-east-1.localhost:5100/amit-app:latest
🏬
What did this just do?

You created an ECR repository named amit-app, then built, tagged, and pushed your Docker image into it. The repositoryUri is the exact address ECS will pull from. On Floci the registry on port 5100 is real — the image physically lands there, so ECS can genuinely pull it next step.

Run it live
Breaking down the commands
ecr create-repository
Creates the private image repo (one per app).
docker build -t amit-app .
Builds an image from your Dockerfile.
docker tag ... :latest
Labels the image with the repo URI + a tag.
docker push ...
Uploads the image to your ECR repository.
Must-push before you run On real AWS (and Floci) a task fails if ECS can't pull the image. I tested this live: run-task with a repo URI that had no image returned STOPPED with a "failed to resolve reference" error. The order matters — build & push first, then run.
3

Register the Task Definition

The blueprint: image, CPU, memory, ports
Command
awslocal ecs register-task-definition --family amit-web --network-mode awsvpc --cpu 256 --memory 512 --requires-compatibilities FARGATE --container-definitions '[{"name":"web","image":"000000000000.dkr.ecr.us-east-1.localhost:5100/amit-app:latest","portMappings":[{"containerPort":3000,"protocol":"tcp"}]}]'
📋
What did this just do?

You registered the task definition amit-web:1 — the recipe for your app. It says: pull amit-app:latest from ECR, give each task 256 CPU + 512 MB, use awsvpc networking, and expose port 3000. Every time you change it, a new revision (:2, :3…) is created.

Run it live
Breaking down the command
ecs register-task-definition
Saves a task blueprint (immutable, versioned).
--family amit-web
The app's name — revisions accumulate under it.
--cpu 256 --memory 512
¼ vCPU + 512 MB per task (Fargate sizing).
--requires-compatibilities FARGATE
Serverless launch — no servers to manage.
--container-definitions '[...]'
JSON list: container name, ECR image, port 3000.
Revision 1 — but watch the single quotes The whole --container-definitions JSON is wrapped in single quotes, and the inner JSON uses double quotes. If your JSON has any single quotes they must be escaped — same lesson as Chapter 4's SQL and every sim in this course.
4

Run a Task — Watch a Real Container Start

Floci actually launches the container on your machine
Commands
awslocal ecs run-task --cluster amit-cluster --task-definition amit-web:1 --launch-type FARGATE --count 1
docker ps --filter "name=floci-ecs"  # ← see the real container
🚀
The best part of this whole course

run-task tells ECS to start one instance of your blueprint. On Floci, ECS genuinely pulls the image and launches a real Docker container — I verified it with docker ps (a live nginx server appeared, and curl inside it returned the real homepage!). The response shows the task's ARN and its lastStatus: RUNNING.

Run it live
Breaking down the commands
ecs run-task
Start one task right now (a one-off run).
--task-definition amit-web:1
Which blueprint to run (family:revision).
--count 1
How many copies to start.
docker ps --filter "name=floci-ecs"
Prove it's real — Floci names its task containers floci-ecs-<taskid>-<container>.
Verify with describe-tasks awslocal ecs list-tasks --cluster amit-cluster lists task ARNs, and awslocal ecs describe-tasks --cluster amit-cluster --tasks <id> shows full detail (status, launch type, created time). That's your "is it running?" toolkit — mirroring describe-instances from Chapter 3.
5

Create a Service — Make It Always-On

Auto-managed copies: ECS keeps N running forever
Commands
awslocal ecs create-service --cluster amit-cluster --service-name amit-web-svc --task-definition amit-web:1 --desired-count 2 --launch-type FARGATE --network-configuration '{"awsvpcConfiguration":{"subnets":["subnet-123"],"securityGroups":["sg-123"]}}'
awslocal ecs update-service --cluster amit-cluster --service amit-web-svc --desired-count 4  # scale up
🚦
From "one-off" to "always-on"

You created a service named amit-web-svc with desired count 2. ECS now reconciles toward 2 running copies — I verified live that Floci launched real containers for services too (same as run-task). Then update-service --desired-count 4 scales it up to 4 copies. That single command is your scaling mechanism.

Run it live
Breaking down the commands
ecs create-service
Registers an always-on workload.
--desired-count 2
The number of copies ECS must keep running.
--network-configuration '{"awsvpcConfiguration":...}'
VPC subnets + security groups the tasks join (Chapter 2).
update-service --desired-count 4
Scaling = changing this one number.
runningCount: 2
Real containers launched by Floci for the service.
Deleting a service needs --force ECS won't delete a service with active tasks unless you pass --force (or first set desired-count to 0). Same "safety rule" family as CloudFront's disable-before-delete. We'll use it in cleanup next.
6

Clean Up — Full Teardown

Scale to 0, stop tasks, delete in the right order
Commands
awslocal ecs update-service --cluster amit-cluster --service amit-web-svc --desired-count 0
awslocal ecs delete-service --cluster amit-cluster --service amit-web-svc --force
awslocal ecs delete-cluster --cluster amit-cluster
awslocal ecs deregister-task-definition --task-definition amit-web:1
awslocal ecr delete-repository --repository-name amit-app --force
🧹
The teardown rules

Cleanup must respect ECS's order: scale the service to 0 → delete the service → stop any stray tasks → delete the cluster → deregister task definitions → delete the ECR repo. Each layer depends on the one above being empty. ECS enforces this: I hit ClusterContainsTasksException live when trying to delete a cluster with a task still running.

Run it live
Breaking down the cleanup
update-service --desired-count 0
Drain the service first.
delete-service --force
Delete the supervisor (force because it tracks tasks).
stop-task --task <id>
Stop any one-off task still running.
delete-cluster
Only succeeds when the cluster is empty — ClusterContainsTasksException otherwise.
deregister-task-definition
Retire the blueprint (status → INACTIVE).
ecr delete-repository --force
Removes the image registry.
ClusterContainsTasksException — expect it once Trying to delete a cluster with running tasks returns ClusterContainsTasksException. It's AWS protecting you from accidentally deleting a running app. Stop the tasks, then delete. Same discipline as Route 53's HostedZoneNotEmpty and CloudFront's disable-before-delete.
Complete ECS flow — copy & paste 
# 1. Create the cluster (the container home)
awslocal ecs create-cluster --cluster-name amit-cluster

# 2. Create the ECR repo and push your image
awslocal ecr create-repository --repository-name amit-app
docker build -t amit-app .
docker tag amit-app 000000000000.dkr.ecr.us-east-1.localhost:5100/amit-app:latest
docker push 000000000000.dkr.ecr.us-east-1.localhost:5100/amit-app:latest

# 3. Register the task definition (the blueprint)
awslocal ecs register-task-definition --family amit-web --network-mode awsvpc --cpu 256 --memory 512 --requires-compatibilities FARGATE --container-definitions '[{"name":"web","image":"000000000000.dkr.ecr.us-east-1.localhost:5100/amit-app:latest","portMappings":[{"containerPort":3000,"protocol":"tcp"}]}]'

# 4. Run a one-off task (real container!)
awslocal ecs run-task --cluster amit-cluster --task-definition amit-web:1 --launch-type FARGATE --count 1
awslocal ecs list-tasks --cluster amit-cluster

# 5. Create an always-on service and scale it
awslocal ecs create-service --cluster amit-cluster --service-name amit-web-svc --task-definition amit-web:1 --desired-count 2 --launch-type FARGATE --network-configuration '{"awsvpcConfiguration":{"subnets":["subnet-123"],"securityGroups":["sg-123"]}}'
awslocal ecs update-service --cluster amit-cluster --service amit-web-svc --desired-count 4

# 6. Clean up (scale 0 → delete service → stop tasks → delete cluster → deregister → delete repo)
awslocal ecs update-service --cluster amit-cluster --service amit-web-svc --desired-count 0
awslocal ecs delete-service --cluster amit-cluster --service amit-web-svc --force
awslocal ecs delete-cluster --cluster amit-cluster
awslocal ecs deregister-task-definition --task-definition amit-web:1
awslocal ecr delete-repository --repository-name amit-app --force
Final mental model — ECS in one picture
ECS = the container orchestrator for your apps.

   Cluster       = the home (amit-cluster)
   ECR           = the image warehouse (docker push)
   Task def     = the blueprint (image + cpu + memory + ports)
   Task         = one running copy of the blueprint
   Service      = "keep N copies running" (self-healing + scaling)
   Fargate      = no servers to manage

   Build image → push to ECR → register task def →
   run task / create service → ECS launches real containers.
Honest note — what Floci does & doesn't support This is the most real chapter in the course: I tested every command live and ECS on Floci launches actual Docker containers — run-task and create-service both started real web servers I could see in docker ps and curl. ECR's registry on port 5100 accepts real docker pushes. Quirks to know: ecr describe-images returns empty output (like CloudFront's list-distributions quirk) even though the push works; the awslogs driver doesn't ship container logs to CloudWatch Logs (use docker logs <container> instead); load-balancer (ALB) wiring isn't emulated; and tasks must reference a pullable image or they stop with a pull error. Everything else — clusters, repos, task definitions, run-task, services, scaling, and the cleanup chain — behaves exactly like real AWS.

Glossary — Chapter 10

Container

A running instance of an image — your app + its dependencies, sharing the host OS.

Docker image

A read-only blueprint of your app that containers are created from.

ECS

Elastic Container Service — AWS's container orchestrator.

Cluster

The logical home for your ECS tasks and services.

Task

One unit of work — one or more containers running your app.

Task definition

The versioned blueprint: image, CPU, memory, ports, env.

Service

A supervisor that keeps a desired number of task copies running.

Desired count

The number of task copies a service should keep running.

ECR

Elastic Container Registry — AWS's private Docker image registry.

Repository (ECR)

Per-app storage for your pushed images.

Fargate

Serverless ECS launch type — no servers to manage.

awsvpc

Network mode where each task gets its own elastic network interface.

Reconciliation

ECS constantly matching real task count to your desired count.
