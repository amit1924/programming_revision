CloudFront — Content Delivery Network

Your images live in S3 (Chapter 8) — but what if a user in Mumbai and a user in New York both open www.amit.com? Fetching every file from one US region is slow for faraway visitors. CloudFront is AWS's CDN: it copies your content to edge locations all over the world, so everyone downloads from somewhere close.

Why a CDN?

Think about the journey of a photo from Chapter 8. A user in Mumbai asks for product-photo.jpg stored in us-east-1. The request crosses an ocean, S3 answers, the bytes travel all the way back. That's hundreds of milliseconds of lag — and it happens for every user, every time.

Without vs with a CDN
   WITHOUT:                         WITH:
   Mumbai user ────🌊────► S3 us-east   Mumbai user ──► 🛰️ Mumbai edge ◄── cached
   (every request                  (first request 🌊 to S3,
    crosses an ocean)               then served from nearby!)
⚡
CDN = content delivered from near you

A CDN (Content Delivery Network) is a worldwide network of edge locations that hold copies of your content. When a user requests a file, CloudFront answers from the nearest edge — not from your distant S3 bucket. Result: faster loads, lower cost, and fewer requests hitting your origin.

Why "CloudFront"? CloudFront = "the front door to your cloud." All visitor traffic enters through CloudFront's global edge network, so AWS can serve it from the closest point. It's the standard way to make any AWS website fast worldwide.

How CloudFront Works

CloudFront is a distribution — a configured pipeline between viewers (users) and an origin (your content's home). The flow:

The distribution pipeline
   Viewer (user in Mumbai)
        │  1. GET d3x.cloudfront.net/product.jpg
        ▼
   Nearest edge location  (Mumbai edge)
        │  2. cached?  yes → serve instantly 🎉
        │             no  → fetch from origin
        ▼
   Origin  (your S3 bucket / EC2 / ALB)
        │  3. returns the file + caches a copy at the edge
        ▼
   back to the viewer (and next time it's instant)
PieceWhat it is
DistributionThe whole CloudFront setup: origins + cache behaviors + settings.
OriginWhere CloudFront fetches content — S3, EC2, ALB, or an external website.
Edge locationOne of hundreds of worldwide POPs holding cached copies.
Cache behaviorRules saying how a path (/*, /images/*) should be cached & served.
Domain nameEvery distribution gets xxxxx.cloudfront.net — put your custom domain on top.

Edge Locations & Caching

The magic of a CDN is caching at the edge. Files that don't change (images, JS, CSS) are copied once to an edge and served from there until they expire.

Cache hit vs miss
   CACHE HIT  user asks, edge has it → instant (fast, free)
   CACHE MISS edge doesn't have it → fetch from origin (slow, costs)

   Caching works because you set TTL / cache-control:
     logo.png      → cache for 1 year (never changes)
     index.html    → cache for 30 seconds (changes often)
🗓️
TTL decides freshness vs speed

The Time-to-Live says how long an edge keeps a copy. Long TTL = super fast but stale. Short TTL = fresh but more origin traffic. Static assets (images, fonts) get long TTLs; HTML and dynamic data get short ones. CloudFront respects your origin's Cache-Control headers.

One bucket, whole world This is the popular S3 + CloudFront architecture: you upload files to one S3 bucket (Chapter 8), put CloudFront in front, and users everywhere fetch from a nearby edge. No servers to manage, tiny cost, fast everywhere. Exactly how www.amit.com should ship its static content.

Origins & Origin Access Identity

A distribution needs an origin — the real home of the content. For your S3 bucket, there's a special security trick called the OAI.

🔐
OAI — let CloudFront in, keep the world out

An Origin Access Identity (OAI) is a special CloudFront identity. You give only the OAI permission to read your S3 bucket. Now users can't hit the bucket directly (it stays private) — they must go through CloudFront. This is why your site is fast and your origin is protected from abuse.

OAI in one picture
   Users ──► CloudFront ──OAI──► S3 bucket
   (public)      (edge + cache)    (only OAI can read)

   Direct bucket access → ❌ denied (private bucket policy)
   Through CloudFront  → ✅ served (OAI is authorized)
Origins can be anything S3 is the classic origin, but CloudFront also fronts EC2 instances, ALBs, API Gateways, Lambda@Edge, and even external URLs. The "origin" is just wherever your real content lives. OAI applies when the origin is S3.

Invalidation & Cache Behaviors

You deployed a fix, but the edge is still serving the old file from cache. Enter invalidation.

🧹
Invalidation = "forget the cached copy now"

Invalidation tells CloudFront to drop specific cached objects (usually by path like /* or /images/*) so the next request refetches fresh content. Use it sparingly — it's meant for emergencies, not routine updates (long TTLs + new filenames are the normal pattern). Cache behaviors are the per-path rules that control all of this.

Lifecycle of a cached file
   deploy v1 → edge caches it (TTL 3600s)
   deploy v2 → users still get v1 😕 (old copy at edge)
   invalidate "/*" → edge drops everything
   next request → refetches v2 ✅ fresh for everyone
File-naming trick beats invalidation Pros avoid invalidation by versioning filenames: app-v1.css, app-v2.css. Old files keep their long cache, new files start fresh, no invalidation needed. Reserve create-invalidation for when you must force-refresh something immediately.

Hands-On: Put a CDN in Front of amit.com

Let's build the CloudFront distribution for www.amit.com — command by command. We'll create the OAI, the distribution for your S3 bucket, invalidate a stale file, and clean up.

1

Create the Origin Access Identity

The special CloudFront identity that reads S3
Command
awslocal cloudfront create-cloud-front-origin-access-identity --cloud-front-origin-access-identity-config '{"CallerReference":"oai-001","Comment":"amit site OAI"}'
🪪
What did this just do?

You created an OAI — an identity that belongs to CloudFront. You'll wire it into the distribution as the "door pass" for your S3 bucket. The CallerReference is a unique label so AWS can dedupe requests (same idea as Route 53's caller-reference in Chapter 7). The returned Id is what you use everywhere.

Run it live
Breaking down the command
cloudfront create-cloud-front-origin-access-identity
Creates the special CloudFront S3-reader identity.
--cloud-front-origin-access-identity-config '{"CallerReference":"oai-001",...}'
Config JSON — unique CallerReference + a Comment.
Id: ETBSZS55X8OK03
The OAI's ID — referenced as origin-access-identity/cloudfront/<id>.
2

Create the Distribution

Point CloudFront at your S3 bucket
Command
awslocal cloudfront create-distribution --distribution-config '{"CallerReference":"dist-001","Comment":"amit-photos CDN","DefaultRootObject":"index.html","Enabled":true,"Origins":{"Quantity":1,"Items":[{"Id":"amit-photos-origin","DomainName":"amit-photos.s3.amazonaws.com","S3OriginConfig":{"OriginAccessIdentity":"origin-access-identity/cloudfront/ETBSZS55X8OK03"}}]},"DefaultCacheBehavior":{"TargetOriginId":"amit-photos-origin","ViewerProtocolPolicy":"redirect-to-https","MinTTL":0,"ForwardedValues":{"QueryString":false,"Cookies":{"Forward":"none"},"Headers":{"Quantity":0,"Items":[]}},"TrustedSigners":{"Enabled":false,"Quantity":0},"AllowedMethods":{"Quantity":2,"Items":["GET","HEAD"]}}}'
🚀
What did this just do?

You created the distribution — the whole pipeline. It says: origin is the S3 bucket amit-photos accessed via the OAI, index.html is the default page, HTTPS is enforced, and the default behavior serves GET/HEAD requests. AWS replies with a cloudfront.net domain — the address users will hit.

Run it live
Breaking down the command
cloudfront create-distribution
Creates the whole distribution pipeline.
Origins[].DomainName: amit-photos.s3.amazonaws.com
Where content lives — your S3 bucket endpoint.
S3OriginConfig.OriginAccessIdentity
The OAI ID from Step 1 — CloudFront's key to the bucket.
DefaultRootObject: index.html
What / serves.
Enabled: true
Distribution is live (must be false to delete).
DomainName: xxx.cloudfront.net
The public URL — point your custom domain here (Route 53).
In real AWS it takes a few minutes On real AWS a new distribution enters Deployed status after ~5-10 minutes (propagation worldwide). On Floci it's instant — convenient for learning, but know the real-world delay. Your custom domain (Route 53) is pointed at this domain name in production.
3

Verify the Distribution

Check status, domain, and config
Command
awslocal cloudfront get-distribution --id E22B7FHSRWMVWX --query "Distribution.[Id,Status,DomainName]"
🔍
Check what you built

get-distribution returns the distribution plus an ETag — required for updates and deletes (like IAM's if-match pattern). This is your verification command for everything: status, domain, current config.

Run it live
Breaking down the command
cloudfront get-distribution --id E22B7FHSRWMVWX
Fetch a distribution's details + its ETag.
Status: Deployed
Ready to serve traffic.
DomainName
The URL your users (or custom domain) will use.
4

Invalidate Stale Content

Force the edges to forget old copies
Command
awslocal cloudfront create-invalidation --distribution-id E22B7FHSRWMVWX --invalidation-batch '{"Paths":{"Quantity":1,"Items":["/*"]},"CallerReference":"inv-001"}'
🧹
What did this just do?

You told CloudFront: "drop the cached copies of everything (/*)." The next request for any file will refetch from the S3 origin — so a just-deployed update reaches users immediately. The result includes an invalidation ID and status (Completed on Floci, InProgress on real AWS for a bit).

Run it live
Breaking down the command
cloudfront create-invalidation
Asks CloudFront to drop cached objects.
Paths.Items: ["/*"]
Which paths to forget — /* = everything, or /images/* for a subset.
CallerReference: inv-001
Unique label to dedupe invalidations.
Use it for emergencies, not routine Invalidations are charged per path on real AWS. The pro workflow is versioned filenames (app-v2.css) so new files get new cache keys. Reserve invalidation for "oops, that must refresh now."
5

Update & Disable (Pre-Delete)

You can't delete a live distribution
Commands
awslocal cloudfront get-distribution --id E22B7FHSRWMVWX --query "ETag"
awslocal cloudfront update-distribution --id E22B7FHSRWMVWX --if-match "<etag>" --distribution-config '{... Enabled:false ...}'
⏸️
Two rules before delete

Deleting a distribution requires it to be disabled first (like Route 53's "records before zone" rule). And update-distribution needs the current ETag via --if-match — the same optimistic-locking you saw with IAM and S3. Update to Enabled: false, wait for Deployed, then delete.

Run it live
Breaking down the commands
get-distribution --query "ETag"
Fetch the current version tag for optimistic locking.
update-distribution --if-match <etag>
Apply changes only if the config hasn't changed since you read it.
Enabled: false
Disables the distribution — a required step before deletion.
6

Clean Up — Delete the CDN

Disabled → delete distribution → delete OAI
Commands
awslocal cloudfront delete-distribution --id E22B7FHSRWMVWX --if-match "<new-etag>"
awslocal cloudfront delete-cloud-front-origin-access-identity --id ETBSZS55X8OK03 --if-match "<oai-etag>"
🧹
The full teardown

Distribution first (now that it's disabled), then the OAI. Both need their current ETags. Same create → use → delete discipline — on real AWS, distributions are a tiny monthly fee and OAIs are free, but the cleanup habit keeps your account tidy and predictable.

Run it live
Breaking down the cleanup
delete-distribution --id ... --if-match <etag>
Deletes the distribution — must be disabled first.
get-cloud-front-origin-access-identity
Fetch the OAI's ETag for its own delete.
delete-cloud-front-origin-access-identity
Removes the OAI last.
DistributionNotDisabled — expect it once Trying to delete a live distribution returns DistributionNotDisabled. That's AWS protecting you — you must disable (Step 5) and wait for Deployed first. Same family of "must do it in order" rules as Route 53's HostedZoneNotEmpty and S3's non-empty bucket.
Complete CloudFront flow — copy & paste 
# 1. Create the OAI (the S3 door pass)
awslocal cloudfront create-cloud-front-origin-access-identity --cloud-front-origin-access-identity-config '{"CallerReference":"oai-001","Comment":"amit site OAI"}'
#   → note the OAI Id, e.g. ETBSZS55X8OK03

# 2. Create the distribution for your S3 bucket
awslocal cloudfront create-distribution --distribution-config '{"CallerReference":"dist-001","Comment":"amit-photos CDN","DefaultRootObject":"index.html","Enabled":true,"Origins":{"Quantity":1,"Items":[{"Id":"amit-photos-origin","DomainName":"amit-photos.s3.amazonaws.com","S3OriginConfig":{"OriginAccessIdentity":"origin-access-identity/cloudfront/ETBSZS55X8OK03"}}]},"DefaultCacheBehavior":{"TargetOriginId":"amit-photos-origin","ViewerProtocolPolicy":"redirect-to-https","MinTTL":0,"ForwardedValues":{"QueryString":false,"Cookies":{"Forward":"none"},"Headers":{"Quantity":0,"Items":[]}},"TrustedSigners":{"Enabled":false,"Quantity":0},"AllowedMethods":{"Quantity":2,"Items":["GET","HEAD"]}}}'

# 3. Verify it deployed
awslocal cloudfront get-distribution --id E22B7FHSRWMVWX --query "Distribution.[Id,Status,DomainName]"

# 4. Force-refresh stale cache
awslocal cloudfront create-invalidation --distribution-id E22B7FHSRWMVWX --invalidation-batch '{"Paths":{"Quantity":1,"Items":["/*"]},"CallerReference":"inv-001"}'

# 5. Disable before delete (needs current ETag)
ETAG=$(awslocal cloudfront get-distribution --id E22B7FHSRWMVWX --query "ETag" --output text)
awslocal cloudfront update-distribution --id E22B7FHSRWMVWX --if-match "$ETAG" --distribution-config '{... Enabled:false ...}'

# 6. Clean up (disabled distribution → OAI)
ETAG=$(awslocal cloudfront get-distribution --id E22B7FHSRWMVWX --query "ETag" --output text)
awslocal cloudfront delete-distribution --id E22B7FHSRWMVWX --if-match "$ETAG"
OAI_ETAG=$(awslocal cloudfront get-cloud-front-origin-access-identity --id ETBSZS55X8OK03 --query "ETag" --output text)
awslocal cloudfront delete-cloud-front-origin-access-identity --id ETBSZS55X8OK03 --if-match "$OAI_ETAG"
Final mental model — CloudFront in one picture
CloudFront = the worldwide fast-delivery network for your content.

   Distribution = the pipeline (viewers → edges → origin)
   Origin       = where the real content lives (S3 / EC2 / ALB)
   Edge location= a nearby copy for fast serving
   OAI         = the S3 key that lets CloudFront in (private bucket!)
   TTL / cache  = how long edges keep copies
   Invalidation= force-drop stale cache now

   S3 stores it, CloudFront delivers it, users see it fast.
Honest note — what Floci does & doesn't support I tested this live. CloudFront on Floci supports OAI creation, distribution create/get/update/delete, and invalidations — every command above ran against the emulator (status came back Deployed, invalidation Completed). Quirks to know: list-distributions / list-cloud-front-origin-access-identities return empty output on Floci, distributions deploy instantly (real AWS takes ~5-10 min), and since there's no public internet, the .cloudfront.net URL won't actually serve content offline. The S3-origin + OAI pattern and all commands are 100% accurate for real AWS.

Glossary — Chapter 9

CDN

Content Delivery Network — a worldwide network of servers that deliver content from near the user.

CloudFront

AWS's CDN service.

Distribution

The full CloudFront setup: origins, cache behaviors, and settings.

Origin

Where CloudFront fetches content — S3, EC2, ALB, or an external URL.

Edge location

A worldwide POP holding cached copies of your content.

Cache behavior

Rules for how a URL path is cached and served.

OAI

Origin Access Identity — CloudFront's identity for reading a private S3 bucket.

TTL

Time-to-live — how long an edge keeps a cached copy.

Cache hit

Edge already has the file → instant serve.

Cache miss

Edge fetches the file from the origin first.

Invalidation

Asking CloudFront to drop cached objects so they refetch.

ETag

A version tag required for distribution updates/deletes.
