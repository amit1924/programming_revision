Why a Database?

You learned to launch servers in Chapter 3. But a server alone is useless for an app like a shop or a social network — where does the data live? Users, orders, posts, payments: all of it needs to be stored, searched, and updated safely. That's a database's job.

🗄️
Relational databases = tables + relationships

A relational database stores data in tables (like spreadsheets) with rows and columns, and links tables by keys. This is the classic SQL model — Structured Query Language — and it's been the backbone of software for 50 years.

A tiny relational database
users
+----+--------+------------------+
| id | name   | email            |
+----+--------+------------------+
| 1  | Amit   | amit@example.com |
| 2  | Maria  | maria@example.com|
+----+--------+------------------+

orders  →  references users by user_id  (the "relation")
+----+---------+---------+
| id | user_id | amount  |
+----+---------+---------+
| 1  | 2       | 49.99   |
+----+---------+---------+

You could install a database yourself on an EC2 instance (that's what Chapter 3 taught you how to do). But for production, that means you're on call for backups, patches, failover, and tuning. AWS's answer is RDS.

RDS vs Running Your Own Database

RDS (Relational Database Service) is a managed database: AWS runs the database software for you and handles the boring, critical stuff. Compare the two worlds:

ConcernDatabase on EC2 (DIY)RDS (managed)
Install & configYou install the DB software yourselfAWS does it — pick engine, done
BackupsYou write the cron jobs & test themAutomatic, built-in
PatchesYou schedule & test OS/DB updatesAWS maintains the engine version
FailoverYou build a whole HA setupMulti-AZ failover is one checkbox
MonitoringYou wire up metrics yourselfCloudWatch metrics out of the box
ControlFull root access to the machineNo OS access — managed by design
CostCheaper compute, expensive your-timeIncludes the management premium
The rule of thumb RDS is the default choice for any real app. Run your own DB on EC2 only when you truly need OS-level control or a special engine. RDS = "buy the managed pizza, not the recipe." That's the shared-responsibility model from Chapter 1: AWS runs of the database, you run in it (your data, schemas, credentials).

The Database Engines RDS Offers

RDS doesn't force one database on you — it manages six different engines. You pick the engine when you create the instance, exactly like picking the AMI for EC2.

PostgreSQL

The open-source darling — powerful, standard-compliant, loved by developers. Our chapter's choice.

MySQL

The classic LAMP-stack database. Huge ecosystem, runs almost everywhere.

Aurora

AWS's own engine — MySQL/Postgres-compatible but cloud-optimized. Auto-scales, massively fast.

MariaDB

A community fork of MySQL — drop-in compatible, extra features.

Oracle

Enterprise heavyweight — used where licensing/legacy demands it.

Microsoft SQL Server

The Windows-ecosystem database, for .NET shops.

Which should you learn? PostgreSQL. It's free, standard, and the one AWS pushes hardest (even Aurora is built on it). If you know PostgreSQL, MySQL is a small hop. On Floci, the emulator literally runs a real PostgreSQL 16 server for you — so we use it.

Create a Database — Command by Command

Creating a database is a single CLI call. Let me show you the exact command, then break down every flag — exactly like Chapter 3's EC2 launch.

1

Create the Database Instance

One command = a fully managed database
Command
awslocal rds create-db-instance --db-instance-identifier mydb --db-instance-class db.t3.micro --engine postgres --master-username admin --master-user-password adminpass123 --allocated-storage 20
🤔
What did this just do?

You asked AWS (via Floci) to provision a database. Behind the scenes it started a real PostgreSQL server, created a master user, and set aside disk. On Floci that means an actual postgres:16 container appears — you'll connect to it for real in a few steps.

Run it live
Breaking down the command
rds create-db-instance
The service + action: "provision a new managed database."
--db-instance-identifier mydb
A friendly name for the database (like your EC2 key-name).
--db-instance-class db.t3.micro
The size of the database machine — same family naming as EC2 (t3.micro = small/free-tier).
--engine postgres
Which database software to run (postgres / mysql / mariadb / aurora / oracle / sqlserver).
--master-username admin
The superuser name RDS creates for you to log in with.
--master-user-password adminpass123
That user's password. (In real AWS, never hardcode this in a command — use secrets management. We do it here for learning.)
--allocated-storage 20
Disk space in gigabytes (20 GB for us).
Two commands to know by heart create-db-instance = make a database. describe-db-instances = check on your databases (like describe-instances for EC2). You'll use this pair constantly.
2

Check Your Database Is Ready

Watch it go from "creating" to "available"
Command
awslocal rds describe-db-instances --query "DBInstances[].[DBInstanceIdentifier,Engine,DBInstanceStatus]" --output table
⏳
Databases take a moment

Unlike a simple key pair, a database has to actually boot a database engine. It goes creating → available. The describe command is how you watch it — a real operator's habit.

Run it live
Breaking down the command
rds describe-db-instances
Lists all your RDS databases with full details.
--query "DBInstances[].[DBInstanceIdentifier,Engine,DBInstanceStatus]"
Shows only 3 columns: ID, engine, status — a clean table instead of a wall of JSON.
--output table
Pretty-prints the result as an ASCII table.
3

Grab the Endpoint — Your Database's Address

Every app connects to a database via its endpoint
Command
awslocal rds describe-db-instances --query "DBInstances[].Endpoint" --output json
📍
What is an endpoint?

A database is a service, so your app doesn't type an IP — it connects to a host:port called the endpoint. RDS gives every database one automatically. On Floci it's the address+port of the real postgres container it spun up for you.

Run it live
Breaking down the command
describe-db-instances --query "DBInstances[].Endpoint"
Extracts the Endpoint object (address + port) from each database.
--output json
Prints it as JSON so you can copy the exact host and port.
How an app connects
Your app ──────────→ 172.17.0.2:7001 (endpoint)
                                │
                                ▼
                          PostgreSQL 16 (RDS-managed)
                         user=admin  db=postgres
4

Run Real SQL Against Your Database

The coolest part — it's a REAL postgres server
Connect & run SQL
PGPASSWORD=adminpass123 psql -h 172.17.0.2 -p 7001 -U admin -d postgres

CREATE TABLE users (id serial PRIMARY KEY, name text, email text);
INSERT INTO users (name, email) VALUES ('Amit', 'amit@example.com');
SELECT * FROM users;
🎯
Why this is a big deal

This is not a simulation. Floci starts a real PostgreSQL container, so when you run these SQL commands you're talking to an actual database. You can create tables, insert rows, query — the exact skills you'd use on real AWS, for free, locally.

Run it live
Breaking down the connection string
psql
The PostgreSQL command-line client.
-h 172.17.0.2 -p 7001
Host and port — the endpoint you grabbed in Step 3.
-U admin -d postgres
Log in as user admin, into the postgres database.
PGPASSWORD=...
Passes the password without typing it at the prompt.
Need psql? Here's how On Linux: sudo apt install postgresql-client. On macOS: brew install libpq. If you don't have it, don't worry — the sim above shows the full flow, and the SQL concepts are identical in any tool.
5

Delete the Database

Release it — remember, every running thing costs money
Command
awslocal rds delete-db-instance --db-instance-identifier mydb --skip-final-snapshot
🧹
Why skip the final snapshot?

By default, RDS takes a final backup before deleting (so you can restore later). We pass --skip-final-snapshot because this is a throwaway test database — no backup needed. Same habit as terminate-instances in Chapter 3: create → use → delete.

Run it live
Breaking down the command
delete-db-instance --db-instance-identifier mydb
Deletes the database named mydb.
--skip-final-snapshot
Don't take a final backup — we want it fully gone.
Complete RDS flow — copy & paste 
# 1. Create a PostgreSQL database
awslocal rds create-db-instance --db-instance-identifier mydb --db-instance-class db.t3.micro --engine postgres --master-username admin --master-user-password adminpass123 --allocated-storage 20

# 2. Watch it become available
awslocal rds describe-db-instances --query "DBInstances[].[DBInstanceIdentifier,Engine,DBInstanceStatus]" --output table

# 3. Grab the endpoint (address:port)
awslocal rds describe-db-instances --query "DBInstances[].Endpoint" --output json

# 4. Connect and run real SQL (replace host:port with your endpoint)
PGPASSWORD=adminpass123 psql -h 172.17.0.2 -p 7001 -U admin -d postgres
#   then inside psql:
#   CREATE TABLE users (id serial PRIMARY KEY, name text, email text);
#   INSERT INTO users (name, email) VALUES ('Amit', 'amit@example.com');
#   SELECT * FROM users;

# 5. Clean up
awslocal rds delete-db-instance --db-instance-identifier mydb --skip-final-snapshot
Final mental model — RDS in one picture
RDS = a database hotel, not a database tool shed.

   You bring:   the data, the schema, the SQL, the users
   AWS brings:  the engine, patches, backups, failover, monitoring

   create-db-instance   → check in (pick engine + size)
   describe-db-instances → peek at the front desk (status/endpoint)
   Endpoint            → your room key (host:port)
   psql                → actually using the room (SQL)
   delete-db-instance  → check out

Multi-AZ & Read Replicas — Availability

Two RDS features you'll hear constantly. They solve two different problems:

Multi-AZ — survive a disaster

AWS runs a synchronous standby copy in a second Availability Zone. If the main database fails, AWS fails over automatically — your app keeps working, you do nothing. One checkbox at creation.

Read Replicas — scale reads

Copy the data to more instances for read-only traffic (reports, analytics, dashboards). The main database stays focused on writes. Spreads load and improves performance.

Multi-AZ failover
                us-east-1a              us-east-1b
                 ┌──────────┐          ┌──────────┐
                 │  PRIMARY │          │ STANDBY  │
                 │  (writes)│ ────────→ │ (sync)   │
                 └──────────┘  replica  └──────────┘
                      │                      │
                      └──── 💥 fails ────────┘
                                   │
                                   ▼
              AWS auto-fails-over → standby becomes primary
              Your app never noticed.
Note for our course On Floci, read replicas and snapshots aren't implemented (I tested them). They work on real AWS exactly as described — but the core create/connect/SQL flow we practiced is 100% live here. Don't let the missing bonus features slow you down.

Backups & Snapshots

Data loss is the scariest thing in software. RDS protects you two ways:

FeatureWhat it isAutomatic?
Automated backupsDaily snapshots + transaction logs for point-in-time recovery (restore to any second)Yes, on by default (7 days retention by default)
DB snapshotsA manual, full backup you trigger yourselfYou run it (create-db-snapshot)
🛟
Why this matters

A database is your source of truth — you can rebuild servers (Chapter 3), but you can't rebuild lost customer data. RDS's automatic backups mean a "oops I deleted the wrong row" moment is recoverable. On real AWS, always keep them on.

Glossary — Chapter 4

RDS

Relational Database Service — AWS's managed relational database offering.

Relational database

Stores data in tables with rows/columns, linked by keys, queried with SQL.

SQL

Structured Query Language — the language used to talk to relational databases.

DB instance

A single managed database ("mydb"), like an EC2 instance but for data.

Endpoint

The host:port your app uses to connect to the database.

Engine

The database software: postgres, mysql, mariadb, aurora, oracle, sqlserver.

Multi-AZ

Synchronous standby in another AZ with automatic failover (availability).

Read replica

A read-only copy to spread read traffic and scale.

Snapshot

A manual, full backup you can restore from.

Aurora

AWS's cloud-native database engine, MySQL/Postgres compatible.

Master user

The superuser account RDS creates when you provision the database.
