Lambda — Serverless Functions

ECS (Chapter 10) still needs containers running somewhere. Lambda removes even that: you upload a function, and AWS runs it only when an event happens — then scales it out to thousands of copies automatically, and you pay only for the milliseconds it actually runs. On Floci it genuinely executes your Python code, so you'll write a function, call it, and read its real return value.

Why Serverless?

With EC2 you rent servers. With ECS you rent containers running on servers. With serverless you rent executions — you never think about servers at all. The "server" is invisible: AWS runs your code on demand and disappears when done.

The evolution of "where does my code run?"
   EC2     rent a VM → you manage the OS (patch, secure, scale)
   ECS     run containers → AWS runs them, you pick the size
   LAMBDA   run a function → AWS runs it only when called 🔥

   No EC2           → no servers to patch or secure
   No ECS cluster   → nothing running when idle (pay $0)
   Still scales     → 1 call or 1 million, AWS handles it
⚡
Event-driven = code that only exists when needed

Lambda runs your function in response to an event: an S3 upload (Chapter 8), an HTTP request, a database change, a message in a queue. The function executes, returns a result, and its container goes away. Idle time costs nothing, and a traffic spike just means AWS starts more copies — automatically, in milliseconds.

"Serverless" doesn't mean no servers It means you don't manage any. AWS has thousands of servers running your functions; you just never see them. The trade-off: no control over the runtime, and a per-request billing model instead of a flat rate.

What Is Lambda?

AWS Lambda is the serverless function service. You upload code, tell Lambda which language runtime to use and how much memory to give it, and AWS takes care of everything else.

The Lambda lifecycle
   Event arrives (S3 upload / HTTP request / queue message)
        │
        ▼
   Lambda finds a free container with your code (or cold-starts one)
        │  calls handler(event, context)
        ▼
   Your function runs → returns a result
        │
        ▼
   container reused for next event, then recycled when idle
PieceWhat it is
FunctionYour code + its configuration (runtime, memory, timeout).
RuntimeThe language Lambda runs — Python, Node, Java, Go, etc.
HandlerThe entry point Lambda calls, e.g. index.handler.
EventThe JSON input that triggers the function.
InvocationOne execution of the function in response to an event.
Execution roleIAM role giving the function permissions (S3, DynamoDB…).
Lambda = the "glue" of AWS Lambda is how AWS services talk to each other in code: an S3 upload triggers a Lambda that resizes an image, an API Gateway request triggers a Lambda that queries DynamoDB. It's small, focused functions wired to events — the backbone of modern serverless apps.

Anatomy of a Function

Every Lambda function is defined by a handful of settings. The three that matter most on day one:

Your code + three settings
   CODE        index.py  →  def handler(event, context)
   RUNTIME     python3.12        (which language)
   ROLE        arn:aws:iam::…:role/lambda-exec  (what it may touch)
   MEMORY/TIME 128 MB · 3s      (how big, how patient)
🎛️
Handler = the function Lambda calls

--handler index.handler means "in file index.py, call the function named handler." Lambda passes it an event (the input JSON) and a context object (request ID, timeout, etc.). Whatever the handler returns becomes the invocation's response.

Memory ≠ RAM only — it sets CPU too Higher memory gives more CPU and more network bandwidth (and costs proportionally more). 128 MB is the floor; bumping to 256/512 MB often makes a function finish faster than raising only the timeout would. Lambda is "serverless," but configuration still matters.

Triggers & Events

A Lambda alone does nothing — it needs something to fire it. That "something" is a trigger (event source). Each trigger delivers an event with a different JSON shape.

TriggerWhen it firesEvent contains
S3File uploaded/deletedBucket name, object key, size
API GatewayHTTP requestHTTP method, path, headers, body
DynamoDB StreamsTable row changesNew/old values of changed records
SQS / SNSMessage arrivesThe message body & metadata
Scheduled (EventBridge)On a cron/rateTimestamp of the schedule
Wire them with event-source mappings
   S3 upload ──► event-source mapping ──► your Lambda
   queue msg ─► event-source mapping ──► your Lambda

   The mapping tells Lambda "watch this source, run my
   function for every event" (a create-event-source-mapping).
Real triggers fire automatically; Floci's are limited On real AWS, a trigger invokes your function by itself (upload to S3 → function runs, no manual call). Floci supports create-event-source-mapping only for SQS, Kinesis, and DynamoDB Streams — S3 triggers are rejected — and the mapping doesn't auto-fire events the way real AWS does. So on Floci we invoke manually to see our code run, which is exactly how you'd test a function on real AWS anyway.

Pricing & Limits

Lambda's billing is the purest expression of serverless: you pay for executions, not for idle capacity.

💰
Two meters: requests × time

You're charged per request (first 1 million/month are free) and per compute time — the milliseconds your code runs, priced by your chosen memory. A function that runs 100 ms and then sleeps forever costs almost nothing. A constant-load EC2 instance would bill for every idle hour by comparison.

What makes the bill bigger
   more requests      → more per-request charges
   more memory        → higher per-ms rate
   longer timeouts    → more compute seconds per call

   free tier (real AWS): 1M requests + 400,000 GB-seconds / month
   idle time           → $0 (nothing is running!)
Quick mental math A 128 MB function handling 1M short requests a month is comfortably inside the free tier on real AWS. That's the "serverless is cheap when idle" story — perfect for small projects, cron-like jobs, and event glue.

Hands-On: Build & Run Your First Lambda

We'll write a Python function, upload it, and — the exciting part — actually execute it against Floci and read its real return value. Command by command.

1

Create the Function

Zip your code, upload it with a runtime & handler
Commands
# index.py — your handler
def handler(event, context):
    name = event.get("name", "world")
    return {"statusCode": 200, "body": f'{{"message": "Hello, {name}!"}}'}
# zip it up and upload
zip function.zip index.py
awslocal lambda create-function --function-name amit-hello --runtime python3.12 --role arn:aws:iam::000000000000:role/lambda-exec --handler index.handler --zip-file fileb://function.zip
📦
What did this just do?

You told Lambda: "here's my code (zipped), run it with Python 3.12, call index.handler as the entry point, and use this IAM role." The response confirms the function is Active — created and waiting for its first event. Code must be packaged as a zip (the fileb:// prefix tells the CLI it's a binary file).

Run it live
Breaking down the command
lambda create-function
Creates the serverless function.
--runtime python3.12
The language runtime (Python/Node/Java/Go…).
--role arn:aws:iam::…:role/lambda-exec
IAM execution role — what the function may touch (Chapter 5).
--handler index.handler
Entry point: index.py → function handler.
--zip-file fileb://function.zip
Your packaged code (binary file upload).
Handler vs runtime — same idea as ECS task defs The handler is like the CMD/entrypoint of a container, and the runtime is like the base image. Lambda packages those two ideas more tightly: one runtime + one handler per function.
2

Invoke It — Watch Your Code Really Run

Send an event, get a real return value
Commands
awslocal lambda invoke --function-name amit-hello --cli-binary-format raw-in-base64-out --payload '{"name":"Amit"}' /tmp/out.json
cat /tmp/out.json
🚀
The payoff of the whole course

invoke triggers the function with an event — here {"name":"Amit"}. Floci genuinely executes your Python code: the handler reads the event, builds the message, and the function's return value lands in /tmp/out.json. I verified it live — the file contained the real Hello, Amit! response. StatusCode 200 = success.

Run it live
Breaking down the commands
lambda invoke --function-name amit-hello
Triggers the function (synchronous by default).
--cli-binary-format raw-in-base64-out
Sends the payload correctly — this is the AWS CLI v2 default; without it Floci fails to read the event.
--payload '{"name":"Amit"}'
The JSON event delivered to your handler.
/tmp/out.json
The response file — your function's return value.
cat /tmp/out.json
Prints the actual result: Hello, Amit!
Floci quirk: keep the --cli-binary-format flag The AWS CLI v2 already defaults to raw-in-base64-out, so this command is identical on real AWS. But on Floci, dropping the flag makes invoke fail with "Unable to unmarshal input" — I hit that live. Include it explicitly and the exact same command works everywhere.
3

Inspect & Tune the Function

Read its config, then bump memory & timeout
Commands
awslocal lambda get-function-configuration --function-name amit-hello
awslocal lambda update-function-configuration --function-name amit-hello --memory-size 256 --timeout 10
🎛️
Configuration is versionless — code is versioned

get-function-configuration shows the current runtime, handler, memory, timeout. update-function-configuration changes settings without touching your code. The classic serverless tuning loop: bump memory (which adds CPU) until the function runs fast enough, and raise the timeout so long jobs don't get killed.

Run it live
Breaking down the commands
get-function-configuration
Show current runtime, handler, memory, timeout.
update-function-configuration
Change settings without redeploying code.
--memory-size 256
Double the RAM (also more CPU).
--timeout 10
Allow up to 10s per invocation.
4

Redeploy New Code

Change the handler, re-zip, update-function-code
Commands
# new index.py
def handler(event, context):
    return {"statusCode": 200, "body": "Hello from the new version!"}
zip function.zip index.py
awslocal lambda update-function-code --function-name amit-hello --zip-file fileb://function.zip
🔄
Deploying a fix = uploading new code

update-function-code replaces the function's code while keeping its configuration. Re-invoking afterwards runs the new version. (Real AWS gives every deploy a version number like :1, :2 and lets you point aliases at them — same versioning idea as ECS task definitions in Chapter 10.)

Run it live
Breaking down the commands
update-function-code --zip-file
Replace the function's code (config unchanged).
CodeSha256
A checksum of the uploaded code — proof it changed.
invoke --payload '{}'
Re-run with an empty event — now returns the new message.
5

Watch the Logs

Lambda auto-logs to CloudWatch — inspect the errors
Commands
awslocal logs describe-log-groups --query "logGroups[].logGroupName"
awslocal logs filter-log-events --log-group-name /aws/lambda/amit-hello --query "events[0].message"
📜
Every Lambda logs to CloudWatch automatically

Lambda writes to a log group named /aws/lambda/<function> — no setup needed (the execution role gets Logs permission). On Floci this works too: creating and invoking the function created the group, and my earlier "bad payload" invocations left real Runtime.UnmarshalError traces in the log events (Chapter 6's CloudWatch skills pay off here).

Run it live
Breaking down the commands
logs describe-log-groups
Lists CloudWatch log groups — Lambda\u2019s group appears.
logs filter-log-events --log-group-name /aws/lambda/amit-hello
Reads the function's log messages.
Runtime.UnmarshalError
Real error from an invoke — proof logs flow end-to-end.
print() is your debugger On real AWS, every print() inside your handler appears in this log group — the first place you look when a function misbehaves. Monitoring (Chapter 6) + Lambda logs = serverless debugging.
6

Clean Up

Delete the function and confirm it's gone
Commands
awslocal lambda delete-function --function-name amit-hello
awslocal lambda list-functions
🧹
One command, no dangling servers

Unlike EC2 and ECS, Lambda cleanup is trivial — there are no servers or clusters to stop. delete-function removes the code and config instantly (204 No Content), and list-functions confirms an empty list. The log group remains until you delete it, which is fine — that's the only trace left.

Run it live
Breaking down the cleanup
lambda delete-function
Removes code + config (204 No Content).
lambda list-functions
Confirms nothing remains.
Compare the cleanup Lambda's one-command teardown is the polar opposite of ECS's five-step chain (scale → delete service → stop tasks → delete cluster). That contrast is the serverless story: no infrastructure to dismantle, because there was no infrastructure to begin with.

# index.py — your handler
def handler(event, context):
    name = event.get("name", "world")

# 3. Inspect and tune
awslocal lambda get-function-configuration --function-name amit-hello

# 4. Redeploy new code
zip function.zip index.py

Final mental model — Lambda in one picture
Lambda = code that runs only when an event fires.

   Function   = code + runtime + handler + role + memory/timeout
   Event      = JSON input (from S3, API, queue, schedule…)
   Invoke     = one execution → real return value
   Logs       = /aws/lambda/<fn> in CloudWatch, automatic
   Scaling    = 1 call or 1M calls, AWS handles it
   Billing    = requests + compute ms — nothing when idle

   Write a function → zip → create-function → invoke → done.
   No servers, no clusters, pay only for what runs.
Honest note — what Floci does & doesn't support The big win: I verified live that Floci genuinely executes Lambda functions — create-function with Python 3.12, real invoke returning the handler's actual output (Hello, Amit!), config updates, code redeploys, and automatic CloudWatch Logs (the /aws/lambda/amit-hello group appeared by itself and recorded real Runtime.UnmarshalError traces — unlike ECS, Lambda-to-Logs works here). Quirks to know: plain --payload '{"x":1}' fails on Floci unless you include --cli-binary-format raw-in-base64-out (the AWS CLI v2 default, so the same command works on real AWS); create-event-source-mapping only accepts SQS/Kinesis/DynamoDB streams (no S3 triggers) and mappings don't auto-fire events; and there's no API Gateway emulation, so triggers must be simulated with manual invokes. All commands above are 100% accurate for real AWS.

Glossary — Chapter 11

Serverless

Running code without managing servers — pay per execution, not per server.

Lambda

AWS's serverless function service.

Function

Your code plus its configuration (runtime, memory, timeout, role).

Runtime

The language Lambda runs your code in (Python, Node, Java, Go…).

Handler

The entry point Lambda calls, e.g. index.handler.

Event

The JSON input delivered to your function when it's triggered.

Invocation

One execution of the function in response to an event.

Execution role

The IAM role granting your function permissions (Chapter 5).

Trigger / event source

Something that fires your function (S3 upload, API call, queue message).

Event-source mapping

The wiring that connects a trigger source to your Lambda.

Cold start

The delay when Lambda spins up a fresh container for a new invocation.

CodeSha256

A checksum proving which version of your code is deployed.
