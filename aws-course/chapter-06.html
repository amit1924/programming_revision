CloudWatch — Monitoring & Observability

You've built the office (VPC), the computer (EC2), the record room (RDS), and the ID cards (IAM). Now the scary question: how do you know it's alive at 3 AM? This chapter is about observability — metrics, alarms, and logs — so you find out about problems before your users do.

Why Monitor?

Continue the story of www.amit.com. It's 2:47 AM. Your server has been fine for months. Then, quietly, the database starts answering slower and slower. At 3 AM the site dies. Nobody is watching.

The two realities
      WITHOUT monitoring          WITH monitoring
   ┌───────────────────────┐   ┌───────────────────────┐
   │ 3 AM: site dies       │   │ 9 PM: CPU climbs 90%  │
   │ 9 AM: users complain  │   │ 9:01 PM: ALARM 🔔     │
   │ you find out LAST     │   │ you fix it while      │
   │ 😱 angry customers    │   │ sleeping is an option │
   └───────────────────────┘   └───────────────────────┘
📡
Observability = knowing what your cloud is doing

AWS gives you CloudWatch (pronounced "cloud-watch") for exactly this. It collects metrics (numbers like CPU, latency), stores logs (the text your app prints), fires alarms (notifications when things break), and — together with CloudTrail — records who did what. It's free tier friendly, and it's how every AWS engineer stays calm.

The engineer's motto "If you can't measure it, you can't fix it." You already built the infrastructure in Chapters 3-5. Now you give it eyes and ears. Monitoring is not a bonus feature — it's how you sleep.

Metrics — The Numbers

A metric is a number measured over time. Think of a car dashboard: speed, fuel, temperature. CloudWatch metrics are the same — CPU %, memory, latency, error counts.

ConceptWhat it means
NamespaceThe "folder" a metric lives in. AWS services use AWS/EC2, AWS/RDS... your own app can use anything (e.g. AmitSite).
Metric nameWhat the number measures — CPUUtilization, PageViews, LatencyMs.
DimensionsOptional labels that slice a metric — e.g. InstanceId=i-123 or Page=/home.
StatisticHow you summarize a period: Average, Maximum, Minimum, Sum, p99.
PeriodThe time bucket (in seconds) each statistic covers — 60s, 300s, 3600s.
Namespace → Metric → Data points
   Namespace: AmitSite   (the dashboard)
     └─ PageViews   ──► [150, 210, 178, 320, ...]  (data points)
     └─ LatencyMs  ──► [82,  95,  60,  120, ...]
     └─ Errors    ──► [0,   0,   1,   0,   ...]
Free stuff first AWS gives you basic metrics (CPU, disk, network) for EC2/RDS for free every minute-ish. Custom metrics you push yourself (PageViews, latency) cost a tiny amount on real AWS — free here on Floci. The most important metric in the world? Latency and error rate. Users forgive slowness but never forgive errors.

Alarms — Wake You Up

A metric is just a number. An alarm turns that number into an action: "if this metric crosses this threshold, do something." Like a smoke detector: it watches silently, then screams.

Alarm anatomy
   LatencyMs average > 100   (metric + threshold)
        │  for 1 period
        ▼
   ALARM state  ──►  send SNS email / SMS / stop EC2
        ▲
        │  falls back below
        ▼
   OK state      (all clear, alarm cools down)
🚨
Alarm states

An alarm lives in one of three states: OK (all good), ALARM (threshold breached — your notification fires), or INSUFFICIENT_DATA (not enough numbers yet to decide). That third state is what you'll see right after creating an alarm on Floci — it needs a few data points before it can judge.

Alarms are only as smart as you make them One bad alarm is worse than none — it trains you to ignore the noise. Start with a handful of meaningful alarms: high CPU, high latency, error rate above zero, disk nearly full. Then make them actually do something (an SNS notification to your phone).

Logs — The Story

Metrics tell you something is wrong ("CPU 95%!"). Logs tell you why. Every app prints text — errors, requests, warnings. CloudWatch Logs collects that text in one searchable place.

Log structure
   Log group  = a named collection   (e.g. /amitsite/app)
      └─ Log stream = one source inside it (e.g. web-1)
           └─ Log events = the actual lines
              "Rahul visited /home"
              "ERROR connection refused on DB"
PieceReal-life analogy
Log groupA filing cabinet for one app (one group per app/service).
Log streamA drawer per server/instance (each EC2 instance has its own stream).
Log eventA single entry with a timestamp + message — the actual paperwork.
Filter patternA search term (ERROR, Exception) to find trouble fast.
Search is the superpower In real life you grep a log file on a server. CloudWatch Logs does the same but for every server at once, from one console/CLI. Your app prints ERROR, you search filter-pattern "ERROR", and you see every error across the whole fleet. Debugging becomes minutes, not hours.

Hands-On: Observe Your App on Floci

Let's give www.amit.com eyes and ears — command by command, exactly like Chapters 3-5. We'll push metrics, create an alarm, and write + search logs.

1

Push Custom Metrics

Report numbers from your app to CloudWatch
Command
awslocal cloudwatch put-metric-data --namespace AmitSite --metric-name PageViews --value 150 --unit Count
📈
What did this just do?

Your app (or you, for practice) just told CloudWatch: "the PageViews metric in the AmitSite namespace just had value 150." That's exactly what your website's code calls every time someone loads a page. On real AWS you'd send dozens of these per minute; here we send a few by hand to learn the plumbing.

Run it live
Breaking down the command
cloudwatch put-metric-data
Service + action: "report a data point."
--namespace AmitSite
Your app's folder for metrics. AWS uses AWS/EC2 etc.; you choose yours.
--metric-name PageViews
The name of the number you're reporting.
--value 150
The actual number for this data point.
--unit Count
The unit — Count, Milliseconds, Percent, Bytes, etc.
2

Read Metrics Back

List what you've got and grab statistics
Commands
awslocal cloudwatch list-metrics --namespace AmitSite
awslocal cloudwatch get-metric-statistics --namespace AmitSite --metric-name PageViews --start-time 2026-08-07T00:00:00Z --end-time 2026-08-09T00:00:00Z --period 3600 --statistics Maximum
🔍
list vs get statistics

list-metrics shows which metrics exist (the names). get-metric-statistics does the real math — it buckets the data points by a period and returns a statistic (here: the Maximum PageViews in each hour). This is the query behind every CloudWatch graph.

Run it live
Breaking down the commands
cloudwatch list-metrics --namespace AmitSite
Shows which metrics exist in a namespace.
cloudwatch get-metric-statistics
Computes statistics from stored data points.
--start-time / --end-time
The time window to analyze.
--period 3600
Bucket size in seconds (3600 = hourly buckets).
--statistics Maximum
Which summary per bucket — Max / Min / Average / Sum / pXX.
3

Create an Alarm

Turn a metric into a smoke detector
Command
awslocal cloudwatch put-metric-alarm --alarm-name HighLatency --metric-name LatencyMs --namespace AmitSite --statistic Average --period 60 --evaluation-periods 1 --threshold 100 --comparison-operator GreaterThanThreshold
🚨
Read the alarm like a sentence

"If the average LatencyMs in AmitSite, over a 60s period, is greater than 100 for 1 period — fire the alarm." Once it fires, on real AWS you'd attach an SNS notification so your phone buzzes. On Floci we'll just watch it enter ALARM state.

Run it live
Breaking down the command
cloudwatch put-metric-alarm
Creates (or updates) an alarm.
--alarm-name HighLatency
A name you'll recognize later.
--statistic Average --period 60
Evaluate the average over 60-second buckets.
--evaluation-periods 1
How many consecutive bad buckets before firing (1 = instant).
--threshold 100 --comparison-operator GreaterThanThreshold
Fire when the value is > 100ms.
describe-alarms
Check an alarm's current state — your verification tool.
INSUFFICIENT_DATA is normal An alarm starts life unsure — it hasn't seen enough data points to decide. Give it real traffic (or a few more put-metric-data calls) and it'll flip to OK or ALARM. Don't panic when you see this state on a fresh alarm.
4

Create a Log Group & Stream

The filing cabinet for your app's story
Commands
awslocal logs create-log-group --log-group-name /amitsite/app
awslocal logs create-log-stream --log-group-name /amitsite/app --log-stream-name web-1
🗂️
Group first, then stream

The log group is the app's cabinet (/amitsite/app — the slash-prefixed path is convention, not required). Inside it you create log streams, one per source — here web-1, your first web server. When you add a second server later, you add another stream, not another group.

Run it live
Breaking down the commands
logs create-log-group --log-group-name /amitsite/app
Creates the app's log group.
logs create-log-stream --log-stream-name web-1
Adds a stream (a server/source) inside that group.
logs describe-log-groups
Lists your groups — verification.
5

Write Log Events

The lines your app prints, stored in the cloud
Command
awslocal logs put-log-events --log-group-name /amitsite/app --log-stream-name web-1 --log-events timestamp=$(date +%s000),message='Rahul visited /home'
✍️
What did this just do?

You wrote one log event — the line "Rahul visited /home" — with a timestamp, into the web-1 stream. In a real app, your code does this on every request (the CloudWatch agent or SDK handles it automatically). On Floci you type it by hand to learn the plumbing. Note the timestamp must be in milliseconds — $(date +%s000) generates one.

Run it live
Breaking down the command
logs put-log-events
Writes one or more log events.
--log-group-name /amitsite/app --log-stream-name web-1
Where the events go — cabinet + drawer.
timestamp=... ,message='...'
Each event = a timestamp (ms) plus the message. Separate multiple events with a space.
nextSequenceToken
CloudWatch's ordering marker for the stream (auto-handled in real apps).
6

Search Your Logs

Find the errors without reading everything
Command
awslocal logs filter-log-events --log-group-name /amitsite/app --filter-pattern "ERROR"
🎯
This is the debugging superpower

Instead of scrolling thousands of lines, you search. filter-log-events with --filter-pattern "ERROR" returns only the events containing ERROR — across your whole app. Three-line debugging: something broke → search for ERROR → read the exact message.

Run it live
Breaking down the command
logs filter-log-events
Reads and filters events in a log group.
--filter-pattern "ERROR"
Only return events whose message matches this text.
--query "events[].message" --output text
Clean output — just the messages, no JSON wrapping.
From chaos to clarity
   # all events            # filtered: "ERROR"
   Rahul visited /home       ERROR connection refused on DB
   DB query took 250ms
   ERROR conn refused  ←-    (the one line you needed)
   Rahul visited /cart
7

Clean Up

Delete the alarm and logs — tidy account, safe account
Commands
awslocal cloudwatch delete-alarms --alarm-names HighLatency
awslocal logs delete-log-stream --log-group-name /amitsite/app --log-stream-name web-1
awslocal logs delete-log-group --log-group-name /amitsite/app
🧹
Same habit, one more time

Create → use → delete. Alarms and log groups are free here but the habit matters on real AWS (log storage costs money over time). Stream first, then group — and you're clean. (Custom metric data points expire on their own — no delete command needed.)

Run it live
Breaking down the cleanup
cloudwatch delete-alarms --alarm-names HighLatency
Removes the alarm.
logs delete-log-stream
Deletes the stream first (it lives inside the group).
logs delete-log-group
Deletes the whole cabinet last.
Complete CloudWatch flow — copy & paste 
# 1. Push custom metrics
awslocal cloudwatch put-metric-data --namespace AmitSite --metric-name PageViews --value 150 --unit Count
awslocal cloudwatch put-metric-data --namespace AmitSite --metric-name LatencyMs --value 82 --unit Milliseconds

# 2. Read them back
awslocal cloudwatch list-metrics --namespace AmitSite --output json
awslocal cloudwatch get-metric-statistics --namespace AmitSite --metric-name PageViews --start-time 2026-08-07T00:00:00Z --end-time 2026-08-09T00:00:00Z --period 3600 --statistics Maximum

# 3. Create an alarm (latency > 100ms)
awslocal cloudwatch put-metric-alarm --alarm-name HighLatency --metric-name LatencyMs --namespace AmitSite --statistic Average --period 60 --evaluation-periods 1 --threshold 100 --comparison-operator GreaterThanThreshold
awslocal cloudwatch describe-alarms --alarm-names HighLatency

# 4. Log group + stream
awslocal logs create-log-group --log-group-name /amitsite/app
awslocal logs create-log-stream --log-group-name /amitsite/app --log-stream-name web-1

# 5. Write log events (timestamp must be in milliseconds)
awslocal logs put-log-events --log-group-name /amitsite/app --log-stream-name web-1 --log-events timestamp=$(date +%s000),message='Rahul visited /home' timestamp=$(( $(date +%s000) + 1000 )),message='ERROR connection refused on DB'

# 6. Search logs
awslocal logs filter-log-events --log-group-name /amitsite/app --filter-pattern "ERROR" --query "events[].message" --output text

# 7. Clean up
awslocal cloudwatch delete-alarms --alarm-names HighLatency
awslocal logs delete-log-stream --log-group-name /amitsite/app --log-stream-name web-1
awslocal logs delete-log-group --log-group-name /amitsite/app

CloudWatch = the control room of your AWS company.

   Metrics  = the gauges   (CPU, latency, pageviews)
   Alarms   = the smoke detectors (threshold → notify)
   Logs     = the security camera footage (searchable text)

CloudTrail — The Audit Trail

CloudWatch answers "is it healthy?" CloudTrail answers "who did what?" It records every API call made in your account — the API call, the identity (remember IAM ARNs from Chapter 5?), the source IP, and the time.

CloudTrail in one line
   Who  (IAM user/role ARN)
   Did  (ec2:RunInstances, iam:CreateUser, ...)
   What (which resource)
   When (exact timestamp)
   From (IP address)
         ──────────────────────────────►  stored as JSON events
🕵️
Why you need it

A server misbehaves at 3 AM. CloudWatch shows the CPU spike; CloudTrail shows who changed the security group at 2:58. Security incident? CloudTrail is the forensic evidence. In real accounts, CloudTrail is enabled by default on the management events of all AWS services — you don't have to turn it on for the basics.

CloudWatch vs CloudTrail — don't mix them up CloudWatch = performance & logs (metrics, alarms, app output). CloudTrail = audit & security (who called which API). One watches the machinery, the other watches the people. Together they make your account fully observable.

Monitoring Best Practices

What a senior engineer actually does (boiled down):

PracticeWhy
Monitor the "golden signals"Latency, error rate, traffic, saturation (CPU/disk). These four tell you almost everything about a service.
Alarm on errors & latencyNot just CPU. If errors spike or latency climbs, users are affected — that's what matters.
Set alarms to actually notifyAn alarm that doesn't reach you (SNS → email/SMS) is just a number nobody reads.
Log everything, search the restHave a consistent log format (timestamps + request IDs) so filter-log-events actually works.
Keep CloudTrail onFree management-event logging is your audit trail for security and debugging.
Don't alert on every tiny thingAlert fatigue is real. Fewer, meaningful alarms beat 50 noisy ones.
Practice the cleanup habitDelete test alarms/log groups when done — tidy accounts are debuggable accounts.

Glossary — Chapter 6

CloudWatch

AWS's monitoring service: metrics, alarms, and logs.

Metric

A number measured over time (CPU%, latency, page views).

Namespace

The folder a metric lives in — AWS/EC2 or your own like AmitSite.

Dimension

A label that slices a metric, e.g. InstanceId or Page.

Statistic

How a period is summarized: Average, Maximum, Minimum, Sum, p99.

Period

The time bucket (seconds) each statistic covers.

Alarm

Watches a metric and fires when it crosses a threshold.

SNS

Simple Notification Service — how alarms send email/SMS. (Chapter 6 bonus.)

Log group

A named collection of log streams — the cabinet for one app.

Log stream

One source inside a group — typically one server/instance.

Log event

A single timestamped log line.

Filter pattern

A search term used to find matching log events.

CloudTrail

The audit trail of every API call — who did what, when, from where.
