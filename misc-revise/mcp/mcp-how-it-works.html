3 The Code Behind Each Piece

🧑‍💻 Step 1: Host — The AI Application

The Host is your app (Claude Desktop, VS Code, custom chatbot). It creates an MCP Client and decides when to call tools. The AI model tells the Host which tool to call based on the user's question.

// Host creates a client connected to a weather server const host = new McpHost({ serverCommand: "node weather-server.js" }); // AI model decides: "I should call get_weather" // Host tells the client to execute it const result = await host.callTool("get_weather", { city: "Mumbai" });
🧑‍💻 Host in action
1. User: "Weather in Mumbai?"
2. AI: I need get_weather(city="Mumbai")
3. Host → Client: callTool("get_weather", {city: "Mumbai"})

🔌 Step 2: MCP Client — The Messenger

The Client is a 1:1 connection from Host to Server. It takes the Host's intent and serializes it into a JSON-RPC message.

// Client receives callTool from Host // It builds a JSON-RPC 2.0 request const request = { "jsonrpc": "2.0", "id": 1, "method": "tools/call", "params": { "name": "get_weather", "arguments": { "city": "Mumbai" } } }; // Send over transport (stdio/SSE) await transport.send(request);
🔌 Client serializes to JSON-RPC
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": {
      "city": "Mumbai"
    }
  }
}
What the Client does: Takes what to do (call get_weather) and how (city=Mumbai) → wraps in JSON-RPC → sends over transport → waits for response → returns result to Host.

⚡ Step 3: MCP Server — The Tool Provider

The Server receives the JSON-RPC, finds the matching tool (get_weather), executes it, and returns the result.

// Weather MCP Server const server = new McpServer({ name: "Weather Server" }); // Register the tool server.tool( "get_weather", "Get current weather for a city", { city: z.string() }, async ({ city }) => { // Call the real Weather API const data = await fetch( `https://api.weather.com/v1/${city}` ); return { content: [{ type: "text", text: `${data.temp}°C, ${data.condition}` }] }; } );
⚡ Server processes the request
📥 Receives tools/call { name: "get_weather", city: "Mumbai" }
🔍 Matches tool "get_weather" in registry
🌐 Calls Weather API: GET /v1/Mumbai
📤 Returns: {"content": [{"type": "text", "text": "27°C, Sunny"}]}

5 What the Server Exposes

Before calling any tool, the AI first asks the Server: "What tools do you have?" via tools/list. Here's what our Weather Server advertises:

MethodDescriptionParameters
get_weather Get current weather for a city city (string, required)
get_forecast Get 7-day weather forecast city (string), days (number)
get_air_quality Get AQI data for a city city (string)
// tools/list response — what the Server advertises { "tools": [ { "name": "get_weather", "description": "Get current weather for a city", "inputSchema": { "type": "object", "properties": { "city": { "type": "string" } }, "required": ["city"] } } ] }
Why advertise? The AI reads this list and decides which tool fits the user's question. It sees get_weather with city parameter → knows it can use this for "Weather in Mumbai".

7 Visual Summary: The Full Journey

A user asks "What's the weather in Mumbai?" — here's every actor and message in order:

🧑 User → "Weather in Mumbai?"
🧑‍💻 Host → AI decides: call get_weather(city: "Mumbai")
🔌 Client → Sends tools/call JSON-RPC request
⚡ Server → Receives request, calls Weather API
🌤️ Weather API → Returns 27°C, Sunny
⚡ Server → Formats response as text content
🔌 Client → Returns result to Host
🧑‍💻 Host → AI: "It's 27°C and Sunny in Mumbai"
🧑 User ← Sees the answer! ✅
That's MCP in action. The AI gets real-time data through a clean, standardized pipeline. The Host never needs to know about the Weather API — it just talks to the Client. The Server handles the external API details. Clean separation of concerns.
