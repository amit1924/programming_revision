1 The 3-Layer Architecture

MCP is built on 3 distinct layers. Every MCP connection follows this pattern: Host spawns a Client (one per server) which communicates with the Server over a transport.

🧑‍💻

Host Layer

The application that initiates the connection. Examples: Claude Desktop, VS Code, your custom AI app. The host decides which servers to connect to.

Initiator Orchestrator
🔌

Client Layer

A 1:1 connection from host to a server. One host can have many clients — one for each server. The client sends the host's intent as JSON-RPC messages.

1:1 per server JSON-RPC
⚡

Server Layer

Provides context to the AI — tools, resources, prompts. Each server is a program that exposes capabilities via MCP. Can run locally (stdio) or remotely (HTTP+SSE).

Context provider Tools / Resources
Key insight: One Host → many Clients → many Servers. Each server gets its own dedicated client. A host can talk to 10 different MCP servers simultaneously through 10 separate clients.

3 Architecture Benefits: Before vs After

❌ Without MCP Architecture

  • Each AI app writes custom connectors
  • Each tool needs its own protocol
  • No standard lifecycle management
  • Auth, transport, error handling all bespoke
  • Hard to reuse tools across AI apps

✅ With MCP Architecture

  • Host/client/server separation of concerns
  • Standard JSON-RPC protocol everywhere
  • Clear lifecycle: init → operate → shutdown
  • Shared transport, auth, error patterns
  • Any MCP server works with any MCP host
4 Connection Lifecycle

Every MCP connection goes through 3 phases: Initialize → Operate → Shutdown. Click each phase to see details.

Phase 1: Initialize
Client sends initialize request. Client and Server exchange capabilities and protocol versions. Both must agree on version.
Client → Server: { method: "initialize", params: { protocolVersion: "2025-03-26", capabilities: {tools, resources} } }
Server → Client: { result: { protocolVersion: "2025-03-26", capabilities: {tools: {}, resources: {}} } }
Phase 2: Operate
Normal operation. Client sends requests (tools/call, resources/read) and notifications (notifications/initialized). Server responds.
Client → Server: { method: "tools/list" }
Server → Client: { result: { tools: [{ name: "get_weather", ... }] } }
Phase 3: Shutdown
Connection terminates. Client disconnects, server process exits (for stdio) or closes the SSE stream (for HTTP). Cleanup happens.
Client → Server: (close transport / terminate process)

5 Capabilities (What Servers Expose)

During initialization, server and client advertise their capabilities. These determine what the server can do and what the client supports.

🔧

Tools

Actions the AI can call. Each tool has a name, description, and JSON Schema for parameters.

Action
📄

Resources

Data the AI can read. Like files or API responses. Each has a URI and MIME type.

Data
📝

Prompts

Pre-built templates the AI can use. Helpful for common tasks like "summarize this" or "analyze that".

Template
🌿

Roots

Filesystem directories the server can access. Host tells the server which directories are available.

Directory
🎯

Sampling

Server can request the AI to generate responses (server → AI). Useful for agentic patterns.

Generation
// Server advertises its capabilities during init { "capabilities": { "tools": {}, // Supports tools/list and tools/call "resources": {}, // Supports resources/read, resources/list "prompts": {}, // Supports prompts/get "logging": {} // Supports server-side logging } }
6 Transport Layer Deep Dive

MCP defines 2 transport types for communication. Each serves different use cases.

📦 stdio Transport

Client spawns server as a subprocess. Messages flow over stdin/stdout.

Client
stdin → ← stdout
Server
# Client launches server process $ node my-mcp-server.js # stdin stdout (JSON-RPC on each line) > {"jsonrpc":"2.0","id":1,"method":"tools/list"} < {"jsonrpc":"2.0","id":1,"result":{"tools":[]}}
Local only Fast (no HTTP overhead) Simple auth (local)

🌐 HTTP + SSE Transport

Client connects via HTTP POST for requests, SSE stream for responses.

Client
HTTP POST → ← SSE
Server
POST /mcp HTTP/1.1 Content-Type: application/json {"jsonrpc":"2.0","id":1,"method":"tools/list"} // Server responds over SSE: event: message data: {"jsonrpc":"2.0","id":1,"result":{...}}
Remote access Streaming responses Standard auth (Bearer, etc.)
Try it: 📦 stdio
7 JSON-RPC Message Format

All MCP communication uses JSON-RPC 2.0. There are 4 message types: Request, Response, Notification, Error.

✅ Request

{
"jsonrpc": "2.0",
"id": 1,
"method": "tools/call",
"params": {
"name": "get_weather",
"arguments": {
"city": "Mumbai"
}
}
}
Has id + method

✅ Response

{
"jsonrpc": "2.0",
"id": 1,
"result": {
"content": [{
"type": "text",
"text": "27°C, Sunny"
}]
}
}
Same id as request

🔔 Notification

{
"jsonrpc": "2.0",
"method": "notifications/initialized",
"params": {}
// No "id" field!
}
No id — fire and forget

❌ Error

{
"jsonrpc": "2.0",
"id": 1,
"error": {
"code": -32603,
"message": "Internal error",
"data": "API key expired"
}
}
Error instead of result
Message TypeHas id?Has method?Has result?Has error?
Request✅ Yes✅ Yes❌ No❌ No
Response✅ Yes❌ No✅ Yes❌ No
Notification❌ No✅ Yes❌ No❌ No
Error✅ Yes❌ No❌ No✅ Yes
