1. The 6 Phaseslibuv · one iteration

Node.js uses libuv's event loop with six distinct phases. Each phase has a FIFO queue of callbacks. The loop enters each phase, executes all callbacks in that queue (up to a limit), then moves to the next.

2. process.nextTickhighest priority · deep dive

process.nextTick is not part of the event loop phases. It has its own queue that is drained after every single phase — before moving to the next phase, and before microtasks.

process.nextTick(fn)
Schedules fn to run after the current phase, before any other phase. Higher priority than any other callback.
⚠️ Starvation risk
If nextTick recursively queues more nextTick callbacks, the event loop will never reach the I/O, timers, or check phases. This is why Node docs warn about it.
vs Promise microtasks
In Node.js, process.nextTick queue is drained before the microtask queue. So nextTick runs before Promise.then on the same phase boundary.
vs setImmediate
nextTick runs between phases. setImmediate runs in the Check phase (phase 4). nextTick is always first.

Node.js docs explicitly warn: "process.nextTick is not a simple alias for setTimeout(fn, 0). It is far more efficient, but also far more aggressive." Use setImmediate for deferring to the next iteration; use nextTick only when you need to ensure code runs before the next phase (e.g., error handling, cleanup).

3. Poll PhaseI/O events · blocking · watchers

The Poll phase is the most important: it retrieves new I/O events, executes their callbacks, and decides what to do next. libuv uses platform-specific polling mechanisms (epoll on Linux, kqueue on macOS, IOCP on Windows).

📥 Poll step 1: Calculate timeout
Looks at the earliest timer. If timers are pending, poll timeout = 0 (don't block). If setImmediate is pending, timeout = 0. Otherwise, no pending timers or check → block indefinitely.
📡 Poll step 2: Watch for I/O
libuv blocks waiting for I/O events (socket data, file reads, etc.) up to the calculated timeout. New events are queued as callbacks in the poll queue.
⚡ Poll step 3: Execute callbacks
Runs all I/O callbacks in the poll queue (up to a system limit). After each callback, the process.nextTick + microtask queues are drained.
🔀 Poll step 4: Check for next phase
After the poll queue is empty (or hits the limit), if setImmediate callbacks are pending → proceeds to Check phase. If timers are due → loops back to Timers.
// Pseudocode: Poll phase decision
if (pendingTimers.length > 0 || pendingImmediates.length > 0) {
  timeout = 0;  // don't block, check immediately
} else if (no I/O watchers) {
  timeout = 0;  // nothing to wait for
} else {
  timeout = nextTimer - now;  // block until next timer
}
events = poll(timeout);  // blocking call (epoll/kqueue/IOCP)
runCallbacks(events);    // execute I/O callbacks
// After each callback: drain nextTick, drain microtasks

4. setImmediate vs setTimeoutthe classic Node.js question

Outside I/O (main module)
setTimeout(fn, 0) and setImmediate(fn) have unpredictable order. Timer phase runs first, but the 0ms timer may not have expired yet depending on system load. Neither is guaranteed to win.
Inside I/O callback (e.g., fs.readFile)
setImmediate(fn) always wins. The Poll phase (phase 3) queues the I/O callback. After it runs, the Check phase (phase 4) comes next — setImmediate fires before the next Timer phase.
// In I/O callback — setImmediate ALWAYS wins
fs.readFile('file.txt', () => {
  setTimeout(() => console.log('timer'), 0);   // 2nd
  setImmediate(() => console.log('immediate'));  // 1st ✅
});
