1 What Is a Closure?

A closure is a function that "remembers" the variables from its outer (lexical) scope even after the outer function has finished executing. The inner function "closes over" the variables it needs.

function outer(x) { // x is a local variable of outer function inner(y) { // inner "closes over" x return x + y; // x is from outer! } return inner; // return the closure } const add5 = outer(5); console.log(add5(3)); // 8 // add5 still "remembers" x=5 // even though outer() finished!
GLOBAL
add5 = [Function: inner]
CLOSURE 🌟
x = 5 // preserved!
↑ This is the closure — x survives because inner references it

2 The Scope Chain

When a function is called, JavaScript creates a scope chain — a linked list of variable environments. The inner function can access variables from all outer scopes.

const globalVar = 'GLOBAL'; function outer(a) { const b = 'OUTER'; function inner(c) { const d = 'INNER'; // inner can access: d, c, b, a, globalVar // 5 levels of scope! console.log(globalVar, a, b, c, d); } return inner; }
└ inner(c) has access to:
← inner's local: d ("INNER")
← inner's params: c
← outer's scope: a, b ("OUTER")
← global scope: globalVar ("GLOBAL")
ⓘ Every function "remembers" its chain: All functions have [[Environment]] (internal property) pointing to their outer scope. Closures are not magic — they're how JS works by default.

4 Private Variables (Encapsulation)

Closures enable true private state in JavaScript. The variable balance below is inaccessible from outside — it can only be changed through the returned methods.

function createBank(initial) { let balance = initial; // balance is PRIVATE — cannot access from outside! return { deposit(amount) { if (amount > 0) balance += amount; return balance; }, withdraw(amount) { if (amount > 0 && balance >= amount) balance -= amount; return balance; }, getBalance() { return balance; } }; }

5 The Classic Loop Problem

This is one of the most famous closure bugs. Compare var vs let in a loop:

// BAD: var — all closures share the SAME i for (var i = 0; i < 3; i++) { setTimeout(function() { console.log('var ' + i); // Prints: 3, 3, 3 // By the time timeout fires, i=3! }, i * 200); }

Click to see: all show 3

// 3, 3, 3
// GOOD: let — each iteration gets its OWN i for (let i = 0; i < 3; i++) { setTimeout(function() { console.log('let ' + i); // Prints: 0, 1, 2 // Each closure captures a DIFFERENT i! }, i * 200); }

Click to see: each shows its own value

// 0, 1, 2
⚠ Why var breaks: var is function-scoped, not block-scoped. There is only ONE i variable shared across all iterations. By the time the timeout fires, the loop has finished and i is 3.
✓ Why let fixes it: let is block-scoped. Each loop iteration creates a new binding for i. Each closure captures a different i (0, 1, 2).
6 Fixing the Loop · IIFE Pattern

Before let existed, the fix was an IIFE (Immediately Invoked Function Expression) — creating a new closure per iteration.

// Classic fix: IIFE wrapper for (var i = 0; i < 3; i++) { (function(j) { // j is a new variable per iteration setTimeout(function() { console.log('IIFE ' + j); // 0, 1, 2 }, j * 200); })(i); // pass i as argument }
// 0, 1, 2
Why IIFE works:
Iteration 0
j = 0
Iteration 1
j = 1
Iteration 2
j = 2
Each IIFE creates a new scope with its own j
7 Practical: Memoization

Closures are ideal for caching. The cache object lives in the closure — invisible to the outside, but persists across calls.

function memoize(fn) { const cache = {}; // PRIVATE cache return function(n) { if (cache[n] !== undefined) { console.log('CACHE HIT for', n); return cache[n]; } console.log('COMPUTE for', n); const result = fn(n); cache[n] = result; return result; }; } // Expensive function: function fib(x) { if (x <= 1) return x; return fib(x - 1) + fib(x - 2); } const fastFib = memoize(fib);

8 Memory & Garbage Collection

Closures keep variables alive. As long as a closure is referenced, all variables it captures stay in memory — they cannot be garbage collected.

function heavy() { const bigData = new Array(1000000).fill('data'); return function() { console.log('I only need this log, not bigData!'); // ⚠ BUT bigData is captured anyway! }; } // The closure keeps bigData alive — waste!

Best practices:

  • Only capture what you need
  • Null out large references if closure outlives their need
  • Closures in DOM event listeners can prevent elements from being GC'd
  • Modern JS engines optimize — they only capture variables actually referenced
// Good: only what's needed function createLogger(prefix) { // Only 'prefix' is captured return (msg) => console.log(`[${prefix}]`, msg); }
