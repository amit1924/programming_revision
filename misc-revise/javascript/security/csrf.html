1 What is CSRF?

Cross-Site Request Forgery (CSRF) tricks an authenticated user into executing unintended actions on a trusted site. The attack exploits the fact that browsers automatically send cookies with every request to a domain.

👤 Victim (logged into bank.com)
→
😈 Evil.com
→
🏦 Bank.com (auto-sends cookie)

Key insight: The attacker never sees the cookie or response. They just trigger a request — the browser does the rest.

  • ❌ Cookie sent automatically
  • ❌ Server sees valid session = trusts request
  • ❌ Attacker doesn't need the cookie value
  • ✓ Fix: CSRF tokens + SameSite cookies

3 How a CSRF Attack Works
1
Victim logs into bank.com
Server sets a session cookie. Browser stores it.
2
Victim visits evil.com (in another tab)
Attacker page loads — bank.com cookie is still valid.
3
Evil.com auto-submits a form to bank.com
Hidden form: <form action="https://bank.com/transfer" method="POST">
4
Browser auto-attaches the cookie
Cookie for bank.com is sent automatically with the request.
5
Bank.com sees valid session → executes transfer
Server thinks the victim authorized the transfer. Money is gone!
4 The Malicious Form

😈 The hidden form on evil.com

<!-- Victim never sees this --> <form action="https://bank.com/transfer" method="POST" id="csrf-form"> <input name="toAccount" value="attacker-123"> <input name="amount" value="1000"> <input type="hidden"> </form> <script> document.getElementById('csrf-form').submit(); </script>

The form auto-submits when the page loads. The victim just sees an innocent-looking page.

5 Prevention · The Defenses

1. CSRF Tokens

Server embeds a unique, unpredictable token in the page/form. Server validates the token on every state-changing request.

// Server sends token in form: <input type="hidden" name="_csrf" value="aB3dF9..."> // Server validates: if (req.body._csrf !== session.csrf) { throw 'CSRF attack!'; }

2. SameSite Cookies

Browser tells whether to send cookies with cross-site requests.

Set-Cookie: session=abc; SameSite=Strict // Cookie NOT sent for POST from evil.com // (cross-site request) Set-Cookie: session=abc; SameSite=Lax // Sent for top-level GET navigations // NOT sent for POST forms

3. Referer / Origin Header

Check the Origin or Referer header to confirm the request came from your site.

const origin = req.headers.origin; if (origin !== 'https://bank.com') { return res.status(403); } // Blocks requests from evil.com

7 CSRF Token Flow
1. Server generates token
→
2. Embeds in HTML form
→
3. User submits form
→
4. Server validates token
→
5. Match → execute action

With CSRF token:

// POST /transfer (with valid token) POST /transfer HTTP/1.1 Cookie: session=abc Content-Type: application/x-www-form-urlencoded toAccount=attacker-123&amount=1000 &_csrf=ab3dF9kL2z ✓ Server validates
✓ Request passes — token matched!

Without CSRF token (evil.com):

// POST /transfer (no token, from evil.com) POST /transfer HTTP/1.1 Cookie: session=abc Origin: https://evil.com toAccount=attacker-123&amount=1000 // No _csrf token!
✗ Request rejected — missing CSRF token!

9 CSRF Prevention Checklist

✓ Must Do

  • Use CSRF tokens for all state-changing requests (POST, PUT, DELETE)
  • Set SameSite=Lax or SameSite=Strict on session cookies
  • Use custom request headers for AJAX (not auto-sent cross-origin)
  • Validate Origin/Referer headers server-side
  • Use POST for state changes (not GET)

✗ Common Mistakes

  • Relying only on POST (attacker can submit forms)
  • Using GET for state-changing actions
  • Disabling SameSite without understanding the risk
  • No CSRF token on login forms (attacker can log you in)
  • Accepting requests without Origin check
