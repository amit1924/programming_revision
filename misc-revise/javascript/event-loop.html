Event Loop

How JavaScript's single thread handles async — call stack, queues, and the eternal cycle

1. The Big Picturesingle thread, async magic

JavaScript is single-threaded — one call stack, one thing at a time. The event loop is what makes async possible. It constantly checks: "is the stack empty? if so, push the next waiting task."

The event loop has one simple job: monitor the call stack and the task queues. When the stack is empty, it takes the oldest task from a queue and pushes it onto the stack.

The Golden Rule: Microtasks are drained completely after every macrotask, before rendering. A macrotask queue iteration picks one task. The microtask queue is drained until empty.

3. Call Stack in ActionLIFO · stack frames · overflow

The call stack is a LIFO (Last In, First Out) data structure. Each function call creates a stack frame. When a function returns, its frame is popped. The stack has a finite size (~10k frames) — exceeding it causes a stack overflow.

4. Microtasks vs Macrotasksthe key to understanding async

Microtasks
Promise.then / catch / finally, queueMicrotask, MutationObserver
Drained completely after each macrotask, before rendering. Can starve the macrotask queue if they keep adding more microtasks.
Macrotasks
setTimeout, setInterval, I/O, UI events, postMessage, setImmediate
Picked one at a time per event loop iteration. The browser may group rendering between macrotasks.
requestAnimationFrame
runs before the next paint, after microtasks, before render
Scheduled by the browser at ~60fps. Not a task queue — runs in the render phase.
Rendering
style recalc → layout → paint → compositing
Happens after all microtasks are drained. Not guaranteed between every macrotask — the browser optimizes.
⏱️ See the ordering — microtasks always win over macrotasks

Key insight: Promise.resolve().then(() => ...) runs before setTimeout(() => ..., 0) — even though both are queued at the same time. Microtasks interrupt macrotasks.

5. Blocking the Event Looplong tasks · UI freeze · 50ms

A task that takes too long (>50ms) is a Long Task — it blocks rendering, freezes the UI, and degrades user experience. The browser's Interation to Next Paint (INP) metric tracks this.

6. requestAnimationFrame & Render PipelinerAF · style · layout · paint

requestAnimationFrame schedules a callback before the next browser paint. It's ideal for animations — the browser coordinates it with the display refresh rate.

// Render pipeline order (one frame):
Tasks → Microtasks → requestAnimationFrame → Style + Layout + Paint
// rAF runs AFTER microtasks but BEFORE the actual paint
requestAnimationFrame(fn)
Schedules fn to run before the next paint. Passes a high-precision timestamp. Automatically pauses in background tabs.
vs setTimeout(fn, 16)
setTimeout may jitter, throttle in background, or miss frames. rAF synchronizes with the display refresh cycle.

7. Common Pitfallsstarvation · blocking · deadlocks

Microtask Starvation
A microtask that keeps queueing more microtasks prevents macrotasks and rendering from ever running. Example: Promise.resolve().then(() => Promise.resolve().then(...)) recursively.
Long Tasks
Sync while loops or heavy computation blocks the stack. No microtasks, no rendering — the page freezes.
setTimeout(fn, 0) delay
Not actually 0ms. Minimum delay is 4ms after nesting level 5 (HTML spec). Plus, all pending microtasks run first.
Zalgo
A function that's sometimes sync, sometimes async. Bad practice — always use Promise.resolve().then() or queueMicrotask for consistent async.
