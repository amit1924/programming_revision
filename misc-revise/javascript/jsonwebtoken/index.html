0 What is a JWT?

A JSON Web Token (JWT) is a compact, URL-safe string that carries claims between parties. It is self-contained — the server does not need a database session lookup because all the info is inside the token. The server only needs to verify the signature.

Anatomy

● Header ● Payload ● Signature

Key properties

✓ Stateless — no server-side session
✓ Compact — URL-safe, works in HTTP headers
✓ Self-contained — carries user data
✗ Not encrypted — just Base64-encoded!
⚠ Must verify — trust only the signature
1 JWT Structure · Three Parts

Header Algorithm

Contains the signing algorithm and token type.

{ "alg": "HS256", "typ": "JWT" }
Common algorithms:
HS256 HMAC + SHA-256 (symmetric)
RS256 RSA + SHA-256 (asymmetric)
ES256 ECDSA + SHA-256

Payload Claims

The data you want to transmit — NEVER put secrets here.

{ "sub": "123456", "name": "Alice", "iat": 1700000000, "exp": 1700003600 }
Registered claims:
iss issuer   sub subject   iat issued at   exp expiration   aud audience

Signature Verification

Cryptographic proof — prevents tampering.

HMACSHA256( base64Url(header) + "." + base64Url(payload), secret )
✓ If signature matches → token is valid
✗ If not → token was tampered with

4 Where to Store? · Cookies vs localStorage

localStorage XSS vulnerable

Simple but dangerous. Any injected script can steal your token.

// Save localStorage.setItem('token', token); // Send (manual) fetch(url, { headers: { 'Authorization': 'Bearer ' + localStorage.getItem('token') } });
XSS: any script reads it
CSRF: not vulnerable (manual send)
Must send manually every request

HTTP-Only Cookie XSS immune

Browser sends automatically. Cannot be read by JavaScript.

// Cookie set by server: Set-Cookie: token=eyJ...; HttpOnly; Secure; SameSite=Strict // Frontend: nothing to do! // Browser auto-sends on every request fetch(url); // cookie goes with it
XSS: immune (JS cannot access)
CSRF: mitigate with SameSite
Auto-sent by browser

⚠ The Golden Rule

If you must store the token in the browser, use HTTP-Only cookies. localStorage is convenient but one XSS bug = all tokens stolen. If you use cookies, set SameSite=Strict to prevent CSRF and use CSRF tokens for extra safety.

5 Sending Token to Server · Bearer vs Cookie

Bearer Token Authorization header

// Request GET /api/protected HTTP/1.1 Host: example.com Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
How it works:
  1. Frontend manually reads token from storage
  2. Attaches as Authorization: Bearer <token>
  3. Server extracts and verifies

Cookie Token Automatic

// Request (cookie auto-sent) GET /api/protected HTTP/1.1 Host: example.com Cookie: token=eyJhbGciOiJIUzI1NiIs...
How it works:
  1. Browser automatically attaches cookie
  2. Server reads from req.cookies.token
  3. No frontend code needed

7 Verification Deep Dive · How JWT.verify() Works

▶ Step-by-Step Verification

What actually happens when you call jwt.verify(token, secret)?

1. Split the token

Split by . into 3 parts: header, payload, signature.

const parts = token.split('.'); // parts[0] = base64Header // parts[1] = base64Payload // parts[2] = base64Signature

2. Base64url-decode header

Read the algorithm from the header (e.g., "alg": "HS256"). Security: you must validate the algorithm — never accept "none"!

⚠ Algorithm confusion attack: If attacker changes alg from HS256 to none, some libraries skip verification! Always check the algorithm server-side.

3. Recompute the signature

Take parts[0] + "." + parts[1] and sign it with your secret using the algorithm from the header.

const data = parts[0] + '.' + parts[1]; const expectedSig = HMAC(data, secret); // expectedSig must === parts[2]

4. Compare signatures

If the recomputed signature matches the token's signature, the token is authentic — it was signed by someone who knows the secret. If they differ, the token was tampered with.

✓ Match → Valid token
✗ Mismatch → Reject (401)

5. Validate claims

Check exp (expiration), nbf (not before), iss (issuer), aud (audience) if configured.

// Automatic in jwt.verify(): if (decoded.exp && decoded.exp < Math.floor(Date.now()/1000)) { throw new Error('Token expired'); }

6. Return decoded payload

Everything passes. Return the payload (not the whole token) — now you know who the user is.

// jwt.verify() returns: { sub: 'user_42', name: 'Alice', role: 'user', iat: 1700000000, exp: 1700086400 }

ⓘ How HMAC works: The data and secret are:
  1. XORed with padded keys
  2. Hashed with SHA-256 (or chosen algorithm)
  3. Result is Base64url-encoded to form the JWT signature
Even changing one bit in the input produces a completely different hash (avalanche effect).
9 Bearer Authorization · In Depth

▶ The Bearer Scheme

The Authorization: Bearer <token> header is defined in RFC 6750. "Bearer" means "bearer of this token gets access."

// Request with Bearer token GET /api/users HTTP/1.1 Host: example.com Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWI... // How Express reads it: const auth = req.headers.authorization; const token = auth && auth.startsWith('Bearer ') ? auth.slice(7) // Remove "Bearer " : null;

▶ Why "Bearer"?

Anyone who bears (possesses) the token can use it. It's like a key — whoever holds it gets access. This is why protecting the token is critical.

🔑
Bearer token = physical key
If someone steals your key, they can open the door. Same with a Bearer token — anyone with the string can access the API.

10 Security Checklist

✓ Do

  • Use HTTP-Only + Secure + SameSite=Strict cookies
  • Set short expiration (15min–24h)
  • Use refresh tokens for long-lived access
  • Validate algorithm server-side (never trust header)
  • Use RS256 for third-party verification
  • Use CSRF tokens alongside cookies
  • Validate aud (audience) and iss (issuer)

✗ Don't

  • Store secrets in the payload (it's just Base64!)
  • Accept alg: "none" (algorithm confusion)
  • Store JWT in localStorage without XSS protection
  • Use the same secret for signing and encryption
  • Ignore the exp claim
  • Log or expose tokens in URLs/error messages
  • Use tokens without HTTPS transmission
