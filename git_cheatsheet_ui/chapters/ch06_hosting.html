What is a Forge?

Remote Repository Hosting

A Git repository hosted on a remote server is just a bare repo — you can push, pull, and fetch. But a forge wraps that repo in a full project-hosting platform with collaboration, automation, and management features.

Forge = Repo + Features

A forge turns a bare repository into a complete project hub with an issue tracker, pull/merge requests, CI/CD pipelines, package registries, wikis, and an API for tooling integration.

GitHub (SAAS)

The most popular forge. Fully hosted on github.com. Offers public and private repos, Actions (CI/CD), GitHub Pages, Packages, Discussions, and a vast marketplace. The reference for open-source.

github.com SAAS only

GitLab (SAAS + Self-Hosted)

Available as SAAS at gitlab.com or as an open-source self-hosted instance. Offers similar features: CI/CD pipelines (.gitlab-ci.yml), container registry, built-in Docker/K8s integration, and fine-grained permissions.

gitlab.com Self-host

What a Forge Provides

A forge combines version control with project-management tooling. Here are the core services most forges offer:

Git Repository

Remote bare repo accepting push/pull/fetch with access control.

Bug Tracker (Issues)

Track work items, bugs, features. Each gets a unique #id.

Pull / Merge Requests

Propose changes via branches. Code review with inline comments.

CI / CD

Automate builds, tests, and deployments on every push.

Package Registries

Host Maven, npm, Docker images, PyPI packages, etc.

Wiki / Static Pages

Host documentation sites or project wikis directly.

Web Editor

Edit files directly in the browser without cloning.

REST / GraphQL API

Integrate external tools, bots, and automation.

Access Control

Fine-grained permissions: read, triage, write, maintain, admin.

Bug Tracker — Issues

What is an Issue?

  • Each work item is an issue with a unique #id.
  • Contains a text description + threaded discussion.
  • Grouped by labels (tags) and/or milestones (releases/sprints).
  • Assigned to a developer or team for ownership.
  • Can be subdivided into smaller sub-issues or checklists.
  • Auto-close: mention Fix #id or Close #id in a commit or PR description — the issue closes automatically when merged.

Example: Creating & Managing an Issue

# Typical issue lifecycle on GitHub / GitLab

1. Create issue              # Title + description + labels
2. Assign to dev             # @developer takes ownership
3. Label as "bug" / "enhancement"
4. Add to milestone "v2.0"
5. Create branch from issue  # GitHub: "Create a branch" button
6. Work, commit, push
7. Open PR referencing issue # "Fixes #42" in PR description
8. Merge PR                  # Issue auto-closes 🎉

Auto-Close Magic

When your commit message or PR description contains a phrase like Fixes #123 or Closes #42, the forge automatically closes the referenced issue once the branch is merged. This keeps your workflow clean without manual triage.

Fixes #123 Closes #42 Resolves #7

Pull / Merge Requests

Overview

  • GitHub: Pull Request (#id)
  • GitLab: Merge Request (!id)
  • Refers to a source branch to merge into a target branch
  • Text description + threaded discussion
  • Code review diff display: global, per-commit, and per-update
  • Closed by merging (accepted) or without merging (rejected)
  • Can reference issues with auto-close keywords

Example: Creating a PR

# 1. Create a feature branch locally
git checkout -b feature/user-auth
git add .
git commit -m "Add user authentication module"

# 2. Push branch to remote forges
git push origin feature/user-auth

# 3. On GitHub, you will see a banner:
#   "feature/user-auth had recent pushes"
#   [Compare & pull request]

# 4. Click the button, write description:
#   Title: "Add user authentication module"
#   Description: "Implements login/register via JWT. Closes #15"

# 5. Submit — now reviewers can comment on diff lines

Code Review Diff Display

The forge shows a unified diff of all changes in the PR/MR. Reviewers can:

Global View

See the entire diff across all files at once

Per-Commit

Review changes introduced by each commit

Per-Update

See what changed after each force-push

Reviewers can comment on individual lines or on the overall PR. Once approved, the PR is merged (merge commit, squash, or rebase).

CI / CD

How it Works

CI/CD is scripted in YAML configuration files committed to the repository:

  • GitHub: .github/workflows/*.yml
  • GitLab: .gitlab-ci.yml in repo root
Continuous Integration

Build the project and run tests on every push / PR.

Continuous Deployment

Publish artifacts (JARs, Docker images), deploy services, update websites.

Runners

CI jobs run on runners — machines that execute the pipeline:

  • Dedicated runners — private infrastructure you manage
  • Shared runners — provided by the forge (e.g., ubuntu-latest)
  • Same job can run on multiple platforms (Linux, macOS, Windows) via a matrix strategy
  • Failure notification — email alert when a pipeline fails

Example: Simple CI Workflow (GitHub Actions)

# .github/workflows/ci.yml
name: CI
on: [push, pull_request]

jobs:
  build:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node: ['18', '20', '22']

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
      - run: npm ci
      - run: npm test
      - run: npm run build
Runs on every push Tests on Node 18, 20, 22 Fails fast on errors

Example: Simple CI (GitLab CI)

# .gitlab-ci.yml
stages:
  - build
  - test
  - deploy

build-job:
  stage: build
  image: node:20-alpine
  script:
    - npm ci
    - npm run build

test-job:
  stage: test
  image: node:20-alpine
  script:
    - npm ci
    - npm test

deploy-job:
  stage: deploy
  image: alpine:latest
  script:
    - apk add --no-cache rsync openssh
    - rsync -avz ./dist/ user@server:/var/www/
  only:
    - main

CI/CD — Security Considerations

Risks

Running CI/CD on repositories that accept external contributions can be dangerous:

  • A malicious PR could execute arbitrary code on your runner
  • If the job has CD credentials (deploy keys, cloud tokens), the attacker could compromise production
  • Especially dangerous with external contributors you don't know

Mitigations

  • Use proper isolation: run external PRs in a sandboxed environment
  • Separate project: keep CI/CD for forked PRs in a different project from CD
  • Use a separate runner for CD jobs — never share credentials with PR pipelines
  • Require approval before running pipelines on first-time contributors

Horror Story Reference

In 2021, an attacker submitted a seemingly innocent PR to a popular open-source project. The CI job ran on a shared runner that had access to production deployment keys. The PR's malicious code exfiltrated the keys and the attacker deployed a cryptominer to production infrastructure. The incident caused $200K+ in cloud costs before detection.

Lesson: Never run untrusted code on runners with production access. Isolate, sandbox, and review.

CI/CD Security Checklist

  • Use read-only tokens for PR pipelines
  • Separate CI runners from CD runners
  • Require approval for external contributors
  • Never store secrets in plaintext in YAML
  • Use forge secret vault (GitHub Secrets / GitLab CI Variables)
  • Pin runner versions (e.g., ubuntu-22.04 not ubuntu-latest)
  • Enable pipeline audit logs
