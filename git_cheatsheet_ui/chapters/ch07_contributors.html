Common Workflows

A workflow is a standardised way of using Git to collaborate on a project. The choice depends on team size, release cadence, and access control. Atlassian reference

Centralised

Single branch (master). All developers push directly. Simple but no isolation.

Use case: Small teams, linear history.

Feature Branch

Each feature gets its own branch. Merged via pull request after review.

Use case: Most GitHub/GitLab projects.

Gitflow

Strict branching model: master, develop, release branches, hotfixes.

Use case: Release-cycle projects with versions.

Forking

Every developer forks the official repo. Changes submitted via PR from fork.

Use case: Open source with external contributors.

About 3rd Party Contributions

Third-party contributors are developers who cannot push directly to the official repository. They must submit changes through an intermediate process.

Sending Patches

Traditional method. Contributor generates patch files (e.g. via git format-patch) and emails them to maintainers. Maintainer applies with git am.

Pull / Merge Request

Modern method. Contributor publishes their own repository (fork), then requests the official repo to merge their branch. Used on GitHub (PR), GitLab (MR), Bitbucket.

Explicit Push / Pull

Git can work with any arbitrary repository by its URL, without needing a named remote. This is useful for one-off interactions with a contributor's repository.

Push by URL

$ git push git@github.com:contributor/repo.git ref [ref...]

# Push local master to contributor's repo with a different name
$ git push git@github.com:contributor/repo.git master:my-feature
Enumerating objects: 5, done.
Writing objects: 100% (3/3), 412 bytes | 412.00 KiB/s, done.
To github.com:contributor/repo.git
* [new branch] master -> my-feature

Pull by URL

$ git pull git@github.com:contributor/repo.git feature-branch
From github.com:contributor/repo
* branch feature-branch -> FETCH_HEAD
Already up to date.

Decentralised Workflow

In a truly decentralised model, there are multiple repositories and multiple maintainers. No single central repository holds all authority.

Linux Kernel Development (Lieutenants Model)

Linus
Maintains the official kernel tree. Merges from lieutenants.
Lieutenants
Subsystem maintainers (networking, drivers, etc.). Each has their own tree.
Contributors
Send patches to lieutenants or mailing lists.

Reviewing a Remote Branch Before Merging

Running git pull immediately merges the fetched commits into your current branch. Sometimes you want to inspect the code first.

Use git fetch instead — it downloads the data but stores it in FETCH_HEAD, a temporary reference that you can inspect before deciding to merge.

Example: Fetch, Review, Then Merge

$ git fetch git://git.raoul-duke.org/helloworld.git master From git://git.raoul-duke.org/helloworld.git * branch master -> FETCH_HEAD
# Review the fetched commits visually $ gitk FETCH_HEAD
# Review with log $ git log --oneline FETCH_HEAD a1b2c3d Add new feature X e4f5g6h Fix bug in module Y
# Only merge when satisfied $ git merge FETCH_HEAD Updating abc123..def456 Fast-forward

Generating Patches

Legacy: git diff

Produces a plain diff. No metadata — just line changes. Hard for maintainers to apply cleanly.

$ git diff origin/master > my-changes.patch

Modern: git format-patch

Converts commits into patch files — one per commit. Records author, date, message, and other metadata. The maintainer can apply them while preserving full authorship.

Does not preserve merge history — only works for linear history.

Usage

# Generate patches for all commits since origin/master $ git format-patch origin/master 0001-added-foo.patch 0002-removed-bar.patch
# Generate patches for a specific range (rev_origin[..rev_final]) $ git format-patch abc123..def456 0001-updated-readme.patch

Applying Patches

git am — Apply Mailbox

Applies patches generated by git format-patch. Each patch file becomes one commit. Preserves authorship — distinguishes the author (who wrote the patch) from the committer (who applied it).

$ git am 0001-added-foo.patch 0002-removed-bar.patch Applying: added foo Applying: removed bar

Author vs Committer

# After applying, the commit stores both: $ git log --format=full commit abc123def456... Author: Alice <alice@contributor.org> # The original patch author Commit: Bob <bob@maintainer.org> # The person who ran git am added foo

Exercises

Work through these steps with a real GitLab project (e.g., helloforge) to practice the full third-party contribution workflow.

  1. 1
    Look up a helloforge project on GitLab.com to use as a target.
  2. 2
    Clone the repository (prefer SSH for authenticated operations).
  3. 3
    Create commits locally, then try pushing to master — it should fail because master is protected.
  4. 4
    Push with a different name to bypass protection:
    $ git push origin master:my_new_branch_name * [new branch] master -> my_new_branch_name
  5. 5
    Create a Merge Request on GitLab from my_new_branch_name into master.
  6. 6
    Browse the details, approve the MR, and merge it into master.
  7. 7
    Run git pull locally to fetch the merged changes, then check the history with gitk.
  8. 8
    Repeat the entire workflow with a forked repository (fork the project first, then clone your fork, commit, push, and create an MR from the fork).
