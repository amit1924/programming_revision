What is a Version Control System?

A Version Control System (VCS) is a tool that manages changes to documents, computer programs, websites, and other collections of information.

  • Each change is identified by a revision number
  • Each revision has a timestamp and the person who made it
  • Revisions can be compared, restored, and merged
# Example: two revisions of a simple "hello.py" file

# revision 1 — initial set
def greet():
    print("Hello")

# revision 2 — first change (added a parameter)
def greet(name):
    print(f"Hello, {name}")

Use Case 1: Keeping History

A VCS allows you to travel back in time through your project's development.

Revert

Not happy with your latest changes? Just revert to a previous revision!

Browseable History

Inspect any revision of your project at any point in time.

Track Changes

When, who, what changed, why, and in what context.

Deleted Content

Deleted content remains accessible in the repository history forever.

# Check what changed between two revisions
git diff abc123..def456

# Go back to an earlier revision
git checkout abc123

# View the full log
git log --oneline --graph

Use Case 2: Working with Others

A VCS enables seamless collaboration between multiple developers.

  • Share files with your entire team
  • Merge changes from other users without losing work
  • Nothing is accidentally overwritten
  • Know who to blame when something breaks

Scenario: Team of 5 working on the same codebase

Each developer works on their own copy. Alice adds a login feature, Bob fixes a bug, Charlie refactors the database layer. The VCS keeps track of every change and enables the team to merge all contributions together safely.

# Alice pushes her feature
git push origin feature-login

# Bob pulls the latest changes before starting work
git pull origin main

# Charlie merges all completed features into main
git checkout main && git merge feature-login

Use Case 3: Branching

A VCS supports multiple variants of the same software as separate branches.

main

The stable, production-ready line.

maintenance

Bug fixes for the currently released version (e.g. v1.0).

development

New features for the next major version (e.g. v2.0).

release

Release candidates before going to production.

Scenario: v1.0 maintenance vs v2.0 development

The v1.0 maintenance branch receives critical bugfixes while the development branch continues building v2.0 features. Fixed bugs from v1.0 can be cherry-picked or merged into v2.0 so both versions benefit.

# Create and switch to a maintenance branch for v1.0
git checkout -b maintenance-v1.0

# Fix a critical bug on maintenance branch
git commit -am "fix: security patch for v1.0"

# Merge the fix into the development branch too
git checkout dev-v2.0 && git merge maintenance-v1.0

Use Case 4: External Contributors

A VCS enables collaboration with contributors outside your immediate team.

  • Visibility — anyone can see project activity
  • Submit changes — contributors can send patches or open pull requests
  • Fork & merge — anyone can fork the repository, develop features, and merge back

Scenario: Open source contributor submits a new feature

Alice forks the project on GitHub, adds a dark-mode theme toggle, and opens a pull request. The maintainer reviews her changes, suggests improvements, and merges it. Alice is now a contributor to the project.

# Contributor forks the repo and clones their copy
git clone https://github.com/alice/project.git

# Make changes, commit, and push to their fork
git add . && git commit -m "feat: add dark mode toggle"
git push origin feature-dark-mode

# Maintainer pulls the contributor's branch
git pull https://github.com/alice/project.git feature-dark-mode

Taxonomy of Version Control Systems

VCS tools can be categorised along several axes:

Architecture

Centralised (CVS, SVN, Perforce) Decentralised (Git, Mercurial)

Centralised: single server holds all history. Decentralised: every clone is a full repository.

Concurrency

Lock-before-edit (SCCS, RCS) Merge-after-edit (CVS, Git, SVN)

Lock-before-edit: one person locks a file, others cannot edit it. Merge-after-edit: multiple people edit, conflicts resolved at merge time.

History Layout

Tree / Linear (CVS, SVN) DAG — Directed Acyclic Graph (Git, Mercurial)

Tree: merges not recorded, history is linear. DAG: merges are first-class citizens, branches fully represented.

Atomicity Scope

File-level (CVS, RCS) Repository-level / whole-tree (SVN, Git)

File-level: each file has its own revision number. Whole-tree: one revision applies to the entire repository atomically.

Feature CVS SVN Git
Architecture Centralised Centralised Decentralised
Concurrency Merge-after-edit Merge-after-edit Merge-after-edit
History Tree (linear) Tree (linear) DAG
Atomicity File-level Whole-tree Whole-tree
Offline work No No Yes (full local repo)

Other Technical Aspects

Space Efficiency

Older VCS tools use delta compression — they store the initial version and then only the differences (deltas) for each subsequent revision.

Git uses a different approach called object packing: it stores complete snapshots of changed files and periodically packs them into binary packfiles (with delta compression applied inside the packfile). This makes Git operations very fast.

# Git packfile compression in action
git gc # manually trigger garbage collection / packing
git count-objects -v # see packfile statistics

Access Methods

Git supports multiple protocols for accessing remote repositories:

What to Store in a Repository

DO Store

  • Source files (`.py`, `.js`, `.java`, `.c`, `.ts`, etc.)
  • Build scripts (`Makefile`, `build.xml`, `Dockerfile`)
  • Documentation (`README.md`, docs/)
  • Resource files (templates, configs, icons)
  • Test files and test fixtures

DON'T Store

  • Object files (`.o`, `.a`, `.so`)
  • Compiled libraries (`.dll`, `.class`, `.jar`)
  • Executables (`.exe`)
  • Generated PDFs or binaries
  • Build output directories (`node_modules/`, `target/`, `build/`)

Guidelines for Committing

  • 1
    Commit often. Small, frequent commits make history easier to navigate and bugs easier to track down.
  • 2
    Commit independent changes separately. A bugfix and a feature addition should be two different commits.
  • 3
    Describe the rationale. The commit message should explain why a change was made — often more important than the change itself.

Good Commit Message

fix: prevent null pointer crash when user profile is empty

When a user signs up without completing their profile,
the dashboard page was throwing a NullPointerException
because it assumed profile.bio is always set.

Closes: #142

Bad Commit Message

fixed bug

Vague, no context, impossible to understand what was fixed or why.

History of Version Control Systems

1st Generation — Single-file, Local-only (1972–1985)

SCCS (1972) RCS (1982) PVCS (1985)

Operated on a single file at a time. No networking — local machine only. Used the lock-before-edit model: you had to lock a file before editing it, preventing others from working on it simultaneously.

2nd Generation — Client-Server (1986–1994)

CVS (1986) ClearCase (1992) SourceSafe (1994)

Introduced the client-server architecture. Used merge-before-commit — multiple developers could edit the same file and changes were merged when committing. However, atomicity was at the file level, not the whole repository.

3rd Generation — Repository-Level Atomicity (1995–2000)

Perforce (1995) Subversion / SVN (2000)

Still centralised but introduced repository-level atomic commits — either the entire commit succeeds or nothing changes. Subversion became hugely popular as a "better CVS".

Decentralised Tools (2005–present)

Git (2005) Mercurial (2005) Bazaar (2005)

Every clone is a full repository with complete history. Enables offline work, flexible branching, and distributed collaboration. Git, created by Linus Torvalds for Linux kernel development, has become the dominant VCS.

Exercises

Test your understanding of version control concepts:

1

What is a Version Control System?

Define VCS in your own words and list three things it tracks for each revision.

A VCS manages changes to files over time. Each revision tracks: (1) a revision number, (2) a timestamp, (3) the person who made the change.
2

Why keep history?

List three benefits of having a browseable project history.

(1) Revert to any previous state, (2) inspect who changed what and when, (3) deleted content remains accessible.
3

Team collaboration scenario

Describe how a team of 5 developers can work on the same codebase without overwriting each other's work.

Each developer works on their own branch or copy. They pull the latest changes, make their edits, commit, push, and merge. The VCS detects conflicts and requires manual resolution before merging.
4

Branching use case

Explain why you might need a maintenance branch alongside a development branch.

The maintenance branch receives critical bugfixes for the released version (e.g. v1.0) while the development branch continues with new features for v2.0. Bugfixes can be merged forward.
5

External contributors workflow

How does a VCS help with open-source contributions from people outside your organisation?

External contributors can fork the project, make changes in their own copy, and submit patches or pull requests. Maintainers review and merge accepted changes back into the main project.
6

Scaling with VCS

Give approximate numbers for the Linux kernel development scale (changesets and contributors per release).

~10,000 changesets per version (released every 2-3 months), with 1,000+ unique contributors.
7

Centralised vs Decentralised

What is the key difference between a centralised and a decentralised VCS?

Centralised: a single server holds all history, clients only have a working copy. Decentralised: every clone is a full repository with complete history, enabling offline work.
8

What to store?

List three things you should store in a version control repository and three you should not.

Store: source files, build scripts, documentation. Don't store: object files (.o, .a, .so), executables (.exe), generated PDFs.
9

Good commit messages

What makes a good commit message? Provide an example of a good one and a bad one.

A good commit message explains why the change was made. Good: "fix: prevent null pointer crash when user profile is empty — Closes #142". Bad: "fixed bug" (too vague).
10

History of VCS timeline

List the four generations of VCS with one example tool per generation.

(1) 1st gen — SCCS (1972), (2) 2nd gen — CVS (1986), (3) 3rd gen — SVN (2000), (4) Decentralised — Git (2005).
