Git History

Understanding why Git was created helps explain many of its design decisions. The Linux kernel project needed a version control system that could scale to thousands of contributors working across the globe — and none of the existing tools at the time could meet those demands.

Before 2005

Linux kernel managed with BitKeeper

BitKeeper was a proprietary distributed version control system. The Linux project used it under a free license. It was the only DVCS mature enough at the time to handle the kernel's scale.

April 2005

Free license revoked

BitMover, the company behind BitKeeper, revoked the free license after developers at Andrew Morton started reverse-engineering BitKeeper's protocol. Linux now had no version control system.

April 2005

No existing tool met Linux's needs

The requirements were clear: it had to be distributed, guarantee integrity against corruption, and deliver blazing performance on a project with tens of thousands of files. No commercial or open-source tool could satisfy all three.

April 2005

Linus Torvalds starts building Git

Linus described Git as "the information manager from hell." He set three goals: speed, integrity, and support for a distributed workflow like BitKeeper's. Development was incredibly fast — the first commit came just days later.

June 2005

First Linux release managed with Git

Linux 2.6.12 was the first kernel release managed entirely with Git. By this point Git was already handling the full kernel workflow — proof that it was production-ready just two months after its inception.

December 2005

Git 1.0 released

Git reached version 1.0, cementing its stability. Junio Hamano took over maintenance shortly after, and Git rapidly spread beyond the Linux ecosystem to become the world's most popular version control system.

Git Design Objectives

Git was built from the ground up with five core objectives. Every feature — from the staging area to SHA-1 hashing — exists because it serves one or more of these goals.

Distributed Workflow

Every clone is a full-fledged repository. No single point of failure.

# Every clone has the full history
$ git clone https://github.com/user/repo.git
$ cd repo
$ git log --oneline | head -5
a1b2c3d Fourth commit
e4f5g6h Third commit
i7j8k9l Second commit
m0n1o2p First commit

Easy Merging

Merge more frequently than commit. Git's merge algorithms are fast and accurate.

$ git merge feature-branch
Auto-merging src/main.js
CONFLICT (content): Merge conflict in src/main.js
Automatic merge failed; fix conflicts and then commit the result.
$ git merge --abort
# Abort if conflicts are too messy

Integrity

Protection against accidental and malicious corruption. Everything is checksummed.

# Every object is addressed by its SHA-1 hash
$ git hash-object --stdin <<< "hello"
3b18e512dba79e4c8300dd08aeb37f8e728b8dad
# Corrupted objects are detected immediately
$ git fsck
Checking object directories: 100% (256/256), done.

Speed & Scalability

Designed for the Linux kernel (10M+ files in history). Operations remain fast at any scale.

# Blazing fast even on massive repos
$ git status
$ git diff
$ git log --oneline -5
# All complete in milliseconds

Ease of Use

Git balances power with approachability. The same commands work for beginners and experts.

# Simple workflow for beginners
$ git init my-project
$ cd my-project
$ echo "# My Project" > README.md
$ git add README.md
$ git commit -m "Initial commit"
# Just 4 commands to get started

How Each Objective Shaped Git's Features

Objective Key Feature Why It Matters
Distributed Every clone is a full backup No central server dependency; work offline
Easy Merging Recursive merge with rename detection Encourages frequent branching & parallel work
Integrity SHA-1 content-addressed object store Detect any corruption instantly
Speed & Scalability Object packing (not delta encoding) Fast operations even on large repos
Ease of Use Staging area (index) Craft commits incrementally before finalizing

Git Design Choices

Git's internal architecture reflects Linus Torvalds' philosophy: simple data structures, strong integrity guarantees, and a "hackable" tool that exposes its internals to power users.

Easily Hackable

  • Simple data structures: blobs, trees, commits, tags
  • No formal branch history — a branch is just a pointer to a commit
  • Low-level commands (plumbing) exposed alongside high-level (porcelain)
# Plumbing: inspect raw objects
$ git cat-file -p HEAD
tree 4d5fcadc293a348e88f777dc0920f11e7d714d41
author Alice <alice@example.com> 1700000000 +0000

Integrity via SHA-1

  • Every object is content-addressed by its SHA-1 hash
  • Any corruption is detected the moment Git reads the object
  • Tags can be signed with GPG for cryptographic verification

Pluggable Merge Strategies

  • Recursive: default two-branch merge with rename detection
  • Octopus: merge more than 2 branches at once
  • Ours: keep your version entirely
  • Subtree: merge projects with overlapping directory trees
  • The staging area (index) lets you review and craft commits

Object Packing

  • Git stores snapshots (not deltas) for each commit
  • Periodic packing compresses similar objects together using delta compression
  • This hybrid model gives both speed (loose objects) and space efficiency (packs)
# Manual garbage collection & packing
$ git gc --aggressive
Counting objects: 482, done.
Delta compression using up to 8 threads.

SHA-1 Hash Demonstration

Git uses SHA-1 to generate a 40-character hex checksum for every object. The same content always produces the same hash. Even a tiny change results in a completely different hash.

Input: "Hello, Git!"
8c5a2a5b4e7c8e9d0f1a2b3c4d5e6f7a8b9c0d1e
git hash-object --stdin <<< "Hello, Git!"
Input: "Hello, GIT!" (capitalized)
a9b8c7d6e5f4a3b2c1d0e9f8a7b6c5d4e3f2a1b0
Completely different hash — even for a single character change

This content-addressed design means Git can guarantee data integrity. If a file is corrupted on disk, Git's hash will not match and the corruption is detected immediately.

Git Commands Overview

Git offers over 150 commands. They are traditionally grouped into categories: porcelain (user-friendly) and plumbing (low-level internals). Here are the most important ones, organized by workflow.

Setup & Init

  • git initCreate a new repository
  • git cloneClone an existing repo
  • git configConfigure user/behavior

Daily Work

  • git addStage changes
  • git commitSave staged snapshot
  • git statusView working tree state
  • git diffShow unstaged changes
  • git restoreUndo changes

Branching & Merging

  • git branchList/create/delete branches
  • git checkoutSwitch branches
  • git switchSwitch (safer alternative)
  • git mergeMerge branches
  • git rebaseReapply commits on top

History & Inspection

  • git logShow commit history
  • git showShow commit details
  • git blameAnnotate file with author
  • git grepSearch in tracked files

Remote Collaboration

  • git remoteManage remote repos
  • git fetchDownload objects & refs
  • git pullFetch + merge
  • git pushUpload to remote

Advanced & Plumbing

  • git stashTemporarily save changes
  • git cherry-pickApply specific commit
  • git bisectBinary search for bugs
  • git gcGarbage collect / optimize
  • git fsckVerify integrity

Common Workflow Commands

Starting fresh
$ git init project
$ cd project
$ git config user.name "Your Name"
$ touch README.md
$ git add README.md
$ git commit -m "first commit"
Feature branch workflow
$ git checkout -b feature
$ # make changes...
$ git add -A
$ git commit -m "add feature"
$ git checkout main
$ git merge feature

Git GUIs

While Git is a command-line tool, several graphical interfaces make it more approachable. Git ships with two built-in GUIs, and many third-party options exist for different workflows.

Built-in GUIs

gitk

Browsing history

The original Git history browser. Displays the commit DAG as an interactive graph, with detailed commit info, diff view, and search capabilities. Great for exploring branching history visually.

$ gitk --all

git gui

Preparing commits

A Tcl/Tk-based GUI for crafting commits. Shows unstaged/staged files side by side with a diff viewer, allows hunk-by-hunk staging, and supports amending commits.

$ git gui

Third-party GUIs

GitHub Desktop

Free, cross-platform GUI focused on the GitHub workflow. Great for beginners.

GitKraken

Polished, cross-platform GUI with a beautiful graph visualization and built-in editor.

SourceTree

Free Atlassian GUI for Mac/Windows. Supports Git-flow and advanced branching.

Tower

Premium GUI for Mac/Windows with powerful conflict resolution and repo management.

Git Cola

Lightweight, open-source Git GUI for Linux/macOS. Fast and customizable.

Sublime Merge

Blazing fast, keyboard-friendly GUI from the makers of Sublime Text.

GitFiend

Cross-platform GUI with a unique interface. Focuses on simplicity and diff clarity.

LazyGit

Terminal-based TUI. Blazingly fast, keyboard-driven, works in any terminal.

SmartGit

Powerful GUI with built-in SSH client, file compare, and SVN-to-Git migration tools.

gitg

GNOME-native Git GUI. Simple, clean, integrates with the GNOME desktop.

TortoiseGit

Windows shell extension. Overlays icon statuses in Explorer, right-click for Git ops.
