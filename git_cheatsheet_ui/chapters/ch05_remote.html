Interacting with a Remote Repository

Sharing code, collaborating, and synchronising with remotes

1. Simple Centralised Workflow

In a centralised version control system, all developers connect to a single central server that holds the canonical repository. Each user checks out a working copy, makes changes, and commits back to the server.

Central Repository
Dev 1
Dev 2
Dev 3
All history on one server
Simple to understand
Single point of failure

2. Team Workflow

Multiple developers each clone the shared repository, work independently on their own branches, and synchronise by pulling the latest changes and pushing their own back to the shared remote.

Shared Remote Repository
Dev A
pull → push
Dev B
pull → push
Dev C
pull → push

Everyone starts their day with git pull, makes commits locally, and ends with git push. If the push is rejected (someone else pushed first), they pull again, resolve any conflicts, then push.

3. How Git Handles Remote Repositories

Git supports working with multiple remote repositories. Each remote is identified by a local alias (a short name you choose). The default alias after cloning is origin.

Remote branches are mirrored locally under the namespace remote/<name>/<branch>. This keeps your local branches separate from the remote tracking branches.

Local Branches
  • master
  • feature-x
  • bugfix-42
Remote Tracking Branches
  • remote/origin/master
  • remote/origin/feature-x
  • remote/upstream/release
$ git branch --all
* master
  feature-x
  remotes/origin/master
  remotes/origin/feature-x
  remotes/upstream/release

You can not directly check out a remote tracking branch and start editing. You must create a local branch first. Git does this automatically when you run git checkout on a branch name that matches a remote one.

4. Adding a Remote Repository

git remote add <name> <url>

This registers a remote alias so you don't have to type the full URL every time. The name is arbitrary, but by convention the main remote is called origin.

Using a Local Path
$ git remote add origin /tmp/helloworld.git

Useful for testing with a bare repository on the same machine.

Using SSH
$ git remote add origin ssh://username@scm.gforge.inria.fr/gitroot/helloworld.git

SSH provides authenticated, encrypted access to the remote.

Using HTTPS (GitHub example)
$ git remote add origin https://github.com/user/repo.git

HTTPS is the most common protocol for public repositories.

View your configured remotes: git remote -v

5. Pushing Changes to Remote

git push

When you run git push with no arguments, Git pushes the current branch — but only if it has been configured to track an upstream branch on a remote. If no tracking is set up, nothing is sent: local branches remain private by default.

Push fails with no upstream
$ git push
fatal: The current branch master has no upstream branch.
To push the current branch and set the remote as upstream, use

    git push --set-upstream origin master
Push fails on conflict
$ git push
To /tmp/helloworld.git/
 ! [rejected]        master -> master (fetch first)
error: failed to push some refs to '/tmp/helloworld.git/'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing
hint: to the same ref. You may want to first integrate the remote changes
hint: (e.g., 'git pull ...') before pushing again.

Solution: git pull first to integrate remote changes, then push again.

6. Pushing a New Branch

git push -u <remote> <ref> [<ref>...]

Use the -u (or --set-upstream) flag to push a branch and configure it to track the remote branch. After this, a plain git push will know where to send your changes. 

$ git push -u origin master
To /tmp/helloworld.git/
 * [new branch]      master -> master
Branch master set up to track remote branch master from origin.

You can also push multiple refs at once: 

$ git push -u origin master feature-x
 * [new branch]      master -> master
 * [new branch]      feature-x -> feature-x
-u / --set-upstream

Sets upstream tracking for the branch

git branch -vv

View tracking relationships of all branches

7. Fetching Changes from Remote

git fetch [<remote>]

git fetch downloads new commits and updates your local mirror of the remote — but it does not merge anything into your working branch. Your local work remains untouched.

Remote
git fetch
remote/origin/*
$ git fetch origin
remote: Enumerating objects: 5, done.
remote: Counting objects: 100% (5/5), done.
remote: Compressing objects: 100% (3/3), done.
remote: Total 3 (delta 2), reused 0 (delta 0), pack-reused 0
Unpacking objects: 100% (3/3), 1.02 KiB | 1024 bytes each, done.
From /tmp/helloworld.git
   a1b2c3d..e4f5g6h  master     -> origin/master

After fetching, origin/master is updated but your local master branch and working directory are unchanged. You still need to merge or rebase.

8. Merging Remote Changes Locally

After a git fetch, you integrate the remote changes into your local branch:

$ git merge origin/master
origin/master master (local)
Shortcut
git pull

git pull is a shortcut for git fetch followed by git merge. It downloads and integrates changes in one step. 

# These two commands are equivalent to:
$ git pull origin master

# Running these steps manually:
$ git fetch origin
$ git merge origin/master

9. Importing a New Remote Branch

When a collaborator pushes a new branch, you can list all branches (including remote ones) with git branch --all and then check it out. Git automatically creates a local tracking branch. 

$ git branch --all
* master
  remotes/origin/new-fancy-feature

$ git checkout new-fancy-feature
Branch new-fancy-feature set up to track remote branch new-fancy-feature from origin.
Switched to a new branch 'new-fancy-feature'

After this, your local branch new-fancy-feature tracks origin/new-fancy-feature, so a plain git push or git pull will work without extra arguments.

git branch -a

List all local and remote branches

git branch -r

List only remote tracking branches

git checkout -b <local> <remote>/<branch>

Explicitly create local branch from remote

git branch -vv

Show tracking relationships

10. Cloning a Repository

git clone <url> [<directory>]

git clone is the most common way to get a local copy of an existing repository. It is a shorthand for four commands in one:

git clone
  1. git init
  2. git remote add origin <url>
  3. git fetch origin
  4. git checkout master
In Practice

You almost never use git init + git remote add + git fetch + git checkout manually. Just use git clone and then git pull to stay up to date. 

$ git clone https://github.com/user/helloworld.git
Cloning into 'helloworld'...
remote: Enumerating objects: 42, done.
remote: Total 42 (delta 0), reused 0 (delta 0), pack-reused 42
Receiving objects: 100% (42/42), done.
Resolving deltas: 100% (14/14), done.
# Clone into a custom directory name
$ git clone https://github.com/user/helloworld.git my-project

11. Typical Daily Workflow Summary

The daily cycle for collaborating with a remote repository is straightforward:

1 Pull latest

git pull — Get the latest changes from your teammates.

2 Make commits

git add + git commit — Work locally, commit often.

3 Push changes

git push — Share your commits with the team.

# Start of day
$ git pull

# Work, work, work...
$ git add file1.py file2.py
$ git commit -m "Add feature X"

# More work...
$ git add .
$ git commit -m "Finish feature X"

# Share with team
$ git push
If push is rejected:

Someone else pushed before you. Run git pull again to merge their changes, resolve any conflicts, then git push.

12. Exercises

These exercises require at least two participants (or two terminals on the same machine using a bare repository). Work through them in order.

1

Clone a Repository

Clone the shared repository to your local machine.

$ git clone /tmp/shared-repo.git my-clone
$ cd my-clone
2

Use gitk --all

Open the history visualisation tool to see all branches.

$ gitk --all
3

Make Commits and Sync

Create a file, commit it, pull any remote changes, then push your commit.

$ echo "hello" > greeting.txt
$ git add greeting.txt && git commit -m "Add greeting"
$ git pull
$ git push
4

Experience and Resolve a Conflict

Let two participants edit the same line of the same file. The second person to push will get a rejection. Pull, resolve the conflict, commit the merge, and push again. 

$ git pull
# Conflict markers appear in the file
# Edit to resolve, then:
$ git add resolved-file.txt
$ git commit -m "Resolve merge conflict"
$ git push
5

Use git fetch to Review Before Merging

Instead of pulling, fetch first, inspect the incoming changes with git log or git diff, then merge manually. 

$ git fetch origin
$ git log origin/master --oneline
$ git diff master origin/master
$ git merge origin/master
6

Create a Branch, Commit, and Publish

Create a new local branch, make a commit, and push it to the remote with upstream tracking. 

$ git checkout -b my-feature
$ echo "feature work" > feature.txt
$ git add feature.txt && git commit -m "Work on feature"
$ git push -u origin my-feature
7

Checkout a Branch Created by Another Participant

List all branches, find your teammate's branch, fetch it, and check it out. 

$ git fetch origin
$ git branch --all
$ git checkout their-feature
