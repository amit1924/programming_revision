Chapter 7: Services

NodePort · ClusterIP · LoadBalancer — Connecting PODs to the Outside World

1. What are Services?

In Kubernetes, Services are an abstraction that enables communication between various components inside and outside of your application. They connect groups of PODs together, and they connect users to PODs.

  • Connect PODs to users — e.g., a user on a laptop talks to a web app running inside a POD.
  • Connect microservices — e.g., a front-end POD talks to a back-end POD. Services enable loose coupling.
  • Provide a stable endpoint — Even if PODs die and get recreated (new IPs), the Service IP stays the same.
Key Insight: PODs are ephemeral — they come and go. A Service gives you a stable, permanent IP and DNS name to reach your PODs, regardless of how many there are or which node they run on.
NodePort
External access via node IP + port
ClusterIP
Internal communication (default)
LoadBalancer
Cloud load balancer (GCP, AWS, Azure)

2. The External Access Problem

Imagine your Kubernetes cluster has a Node with IP 192.168.1.2. Inside that node, a POD is running your application. The POD has its own internal IP — something like 10.244.0.2.

You are on your laptop with IP 192.168.1.10. Can you curl 10.244.0.2 from your laptop?

Network Boundaries
Your Laptop
192.168.1.10
❌ Cannot reach POD
K8s Node
192.168.1.2
📦 POD IP: 10.244.0.2
Laptop and POD are on different networks. PODs live on an internal cluster network (10.x.x.x). You cannot curl 10.244.0.2 from your laptop.

What about SSH into the node? Yes, you could SSH into 192.168.1.2 and then curl from inside the node — but that's not what users want. Users need a URL or IP they can hit from their browser.

The Solution: A Service maps a port on the Node (accessible from outside) to a port on the POD. Now you can hit curl http://192.168.1.2:30008 and reach your app.

3. NodePort Service

A NodePort Service listens on a port on the Node and forwards traffic to a port on the POD. Three ports are involved:

TargetPort
80
Port on the POD where the app is running (e.g., nginx listens on 80).
Port
80
Port on the Service itself (the virtual IP inside the cluster).
NodePort
30008
Port on the Node itself. Range: 30000–32767. This is how external users connect.
Traffic Flow: NodePort Service
User (curl 192.168.1.2:30008)

      |  // step 1 — hits Node on port 30008
      ▼
┌─────────────────────────────────┐
│  Node  (192.168.1.2)          │
│  ┌───────────────────────────┐  │
│  │  NodePort: 30008           │  │
│  └──────────┬────────────────┘  │
│             │                   │
│             ▼                   │
│  ┌───────────────────────────┐  │
│  │  Service Port: 80          │  │  // step 2 — Service forwards
│  └──────────┬────────────────┘  │
│             │                   │
│             ▼                   │
│  ┌───────────────────────────┐  │
│  │  TargetPort: 80 (on POD)    │  │  // step 3 — reaches POD
│  │  POD IP: 10.244.0.2        │  │
│  └───────────────────────────┘  │
└─────────────────────────────────┘

NodePort Service YAML

# service-definition.yml
apiVersion: v1
kind: Service
metadata:
  name: myapp-service
spec:
  type: NodePort
  ports:
  - targetPort: 80
    port: 80
    nodePort: 30008
  selector:
    app: myapp
    type: front-end

Mandatory: Only port (service port) is required.

Defaults: targetPort defaults to the value of port. nodePort is auto-assigned from the 30000–32767 range if omitted.

Selector: Links the Service to PODs. Any POD with matching labels (app: myapp AND type: front-end) gets traffic.

Commands

$ kubectl get services

4. NodePort with Multiple PODs

What happens when you have multiple PODs running your application — for example, three replicas of your web server?

Service as a Built-In Load Balancer
          External User
                │
                ▼
        ┌───────────────┐
        │  NodePort: 30008  │
        └───────┬───────┘
                │
        ┌───────▼───────┐
        │  Service         │  // random algorithm
        │  (load balancer)  │
        └──┬─────┬─────┬┘
           │     │     │
           ▼     ▼     ▼
        ┌────┐ ┌────┐ ┌────┐
        │POD1│ │POD2│ │POD3│  // all match selector labels
        │app  │ │app  │ │app  │
        └────┘ └────┘ └────┘
  • The Service automatically discovers all PODs whose labels match the selector in the YAML.
  • The Service acts as a built-in load balancer, distributing incoming traffic across all matching PODs.
  • The algorithm is random (not round-robin). No additional configuration is needed.
Simple: A single Service definition distributes traffic to all PODs that match the selector. If you scale your ReplicaSet from 1 to 5 PODs, the Service automatically includes all 5. 
# Check the endpoints that the Service is forwarding to
$ kubectl describe service myapp-service | grep -i endpoints
Endpoints:                10.244.0.2:80, 10.244.0.3:80, 10.244.0.4:80
# Three PODs, all receiving traffic from one Service

5. NodePort Across Multiple Nodes

In a real cluster, you have multiple Nodes. A Service spans all Nodes in the cluster automatically. The same NodePort is opened on every single node.

Service Across a 3-Node Cluster
         User
           │
    ┌──────┼──────────────┐
    │      │              │
    ▼      ▼              ▼
┌────────┐ ┌────────┐ ┌────────┐
│Node 1 │ │Node 2 │ │Node 3 │
│10.0.0.1│ │10.0.0.2│ │10.0.0.3│
└───┬────┘ └───┬────┘ └───┬────┘
    │         │          │
    ▼         ▼          ▼
30008        30008       30008     // same port on ALL nodes
    │         │          │
    ▼         ▼          ▼
┌────────┐ ┌────────┐ ┌────────┐
│POD A  │ │POD B  │ │POD C  │
└────────┘ └────────┘ └────────┘

  // Hitting any node IP + 30008 reaches one of the PODs
  • Same port on every node: If you set nodePort: 30008, port 30008 is opened on every node in the cluster.
  • Any node works: You can access your app using the IP of any node, and the Service will forward to a POD (even one running on a different node).
  • No extra config: Kubernetes handles multi-node routing automatically. One YAML file is all you need.
Simple: One Service works across the entire cluster. Submit one YAML file and every node — regardless of which node the PODs are running on — can receive traffic for those PODs. 
$ kubectl get nodes -o wide
NAME       STATUS   ROLES    INTERNAL-IP
node-01    Ready    <none>   192.168.1.2
node-02    Ready    <none>   192.168.1.3
node-03    Ready    <none>   192.168.1.4

# Any of these work — all reach the same Service
$ curl http://192.168.1.2:30008
$ curl http://192.168.1.3:30008
$ curl http://192.168.1.4:30008

6. ClusterIP Service (Internal Communication)

A ClusterIP Service creates a virtual IP inside the cluster that other services and PODs can use to communicate. This is the default type of Service.

Think of a microservices application: you have a front-end POD that needs to talk to a back-end POD. The back-end PODs might be scaled up or down, and their IPs change. A ClusterIP Service gives the front-end a stable endpoint to reach the back-end.

ClusterIP: Front-End to Back-End
┌─────────────────────────────────────────────────┐
│  Kubernetes Cluster                            │
│                                                   │
│  ┌────────────┐        ┌──────────────────┐       │
│  │ Front-End   │ ─────► │ ClusterIP Service  │       │
│  │ POD          │        │ 10.103.123.5 / "back-end" │       │
│  └────────────┘        └────────┬─────────┘       │
│                                  │                  │
│                  ┌───────────────┼───────────────┐  │
│                  │               │               │  │
│                  ▼               ▼               ▼  │
│             ┌────────┐    ┌────────┐    ┌────────┐ │
│             │Backend │    │Backend │    │Backend │ │
│             │POD 1   │    │POD 2   │    │POD 3   │ │
│             └────────┘    └────────┘    └────────┘ │
└─────────────────────────────────────────────────┘

ClusterIP YAML

# back-end-service.yml
apiVersion: v1
kind: Service
metadata:
  name: back-end
spec:
  type: ClusterIP
  ports:
  - targetPort: 80
    port: 80
  selector:
    app: myapp
    type: back-end

Since ClusterIP is the default type, you could even omit the type field entirely.

Other PODs access this Service using the cluster IP or the service name (Kubernetes DNS resolves the service name to the cluster IP).

# Create the Service
$ kubectl create -f back-end-service.yml
service/back-end created

# View the Service
$ kubectl get service back-end
NAME       TYPE        CLUSTER-IP      PORT(S)   AGE
back-end   ClusterIP   10.103.123.5    80/TCP    5s

# From another POD, access the back-end using service name
$ kubectl exec front-end-pod -- curl http://back-end:80
# or using cluster IP
$ kubectl exec front-end-pod -- curl http://10.103.123.5:80
<!DOCTYPE html>
<html>
...
Kubernetes DNS: When you create a Service, Kubernetes automatically creates a DNS record. Any other POD in the same namespace can reach it via http://back-end:80 — no need to hardcode IPs.

7. LoadBalancer Service

A LoadBalancer Service provisions a native cloud load balancer (e.g., GCP HTTP(S) Load Balancer, AWS ELB, Azure Load Balancer). This gives you a single, public IP or DNS name that end users can hit.

LoadBalancer on a Cloud Platform
              End Users
                   │
                   ▼
          ┌─────────────────┐
          │  Cloud Load Balancer  │  // GCP / AWS / Azure
          │  Public IP: 35.xxx.xxx.xxx │
          └────────┬────────┘
                   │
          ┌────────▼────────┐
          │  Service (port 80)   │
          └──┬─────┬─────┬──┘
             │     │     │
             ▼     ▼     ▼
          ┌────┐ ┌────┐ ┌────┐
          │POD1│ │POD2│ │POD3│
          └────┘ └────┘ └────┘

LoadBalancer YAML

# front-end-service.yml
apiVersion: v1
kind: Service
metadata:
  name: front-end
spec:
  type: LoadBalancer
  ports:
  - targetPort: 80
    port: 80
  selector:
    app: myapp
    type: front-end
$ kubectl create -f front-end-service.yml
service/front-end created

$ kubectl get service front-end
NAME        TYPE           CLUSTER-IP      EXTERNAL-IP   PORT(S)        AGE
front-end   LoadBalancer   10.103.123.6    <pending>     80:30009/TCP   10s

# After cloud LB provisions (may take a minute or two):
$ kubectl get service front-end
NAME        TYPE           CLUSTER-IP      EXTERNAL-IP     PORT(S)        AGE
front-end   LoadBalancer   10.103.123.6    35.202.45.178   80:30009/TCP   90s

# Now hit the public IP!
$ curl http://35.202.45.178:80
<!DOCTYPE html>
...

On Cloud Platforms

GCP, AWS, Azure provision a real load balancer. The EXTERNAL-IP field changes from <pending> to a real IP.

On Unsupported Platforms

Minikube, VirtualBox, bare metal: LoadBalancer type behaves the same as NodePort. The EXTERNAL-IP stays <pending>.

8. Quick Command Reference

Create a Service

kubectl create -f service.yml

List all Services

kubectl get services

Describe a Service

kubectl describe service <name>

Delete a Service

kubectl delete service <name>
