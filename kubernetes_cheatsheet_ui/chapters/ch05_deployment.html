What is a Deployment?

A Deployment is a higher-level Kubernetes object that sits above PODs and ReplicaSets. Think of it as the "manager's manager" — it manages ReplicaSets, which in turn manage PODs. You almost never work with bare PODs in production; you use Deployments.

The Hierarchy

Deployment ReplicaSet PODs Containers

Rolling Updates

Rollback

Analogy: A Deployment is like a fleet manager. You tell the manager "I want 5 cars with engine v2.0". The manager replaces old cars one by one so you never have zero cars on the road.

Why Deployments?

A bare POD or even a ReplicaSet is not enough for production. Real-world apps need:

Multiple Instances (HA)

Run many POD replicas so your app stays up even if a node fails.

Seamless Upgrades

Rolling updates — upgrade instances one-by-one without downtime.

Instant Rollback

Bad deploy? Rollback to the previous revision with one command.

Pause / Resume

Apply multiple changes at once — pause the rollout, batch changes, then resume.

A Deployment provides ALL of these out of the box. A ReplicaSet alone cannot do rolling updates or rollbacks.

Deployment YAML

A Deployment YAML is identical to a ReplicaSet YAML with one key difference: the kind is Deployment instead of ReplicaSet. 

apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-deployment
  labels:
    app: myapp
    type: front-end
spec:
  template:
    metadata:
      name: myapp-pod
      labels:
        app: myapp
        type: front-end
    spec:
      containers:
      - name: nginx-container
        image: nginx
  replicas: 3
  selector:
    matchLabels:
      type: front-end

apiVersion: apps/v1

kind: Deployment

metadata: name + labels

spec.template: POD definition

spec.replicas: how many PODs

spec.selector: labels to match

Run it

kubectl create -f deployment-definition.yml

Rollout & Versioning

When you create a Deployment for the first time, it triggers a Rollout — that's Revision 1. When you later update the image (e.g. nginx → nginx:1.9.1), a new Rollout starts — Revision 2.

Watch Rollout Progress

$ kubectl rollout status deployment/myapp-deployment
Waiting for deployment "myapp-deployment" rollout to finish: 0 of 3 updated replicas...
Waiting for deployment "myapp-deployment" rollout to finish: 1 of 3 updated replicas...
deployment "myapp-deployment" successfully rolled out

See Revision History

$ kubectl rollout history deployment/myapp-deployment 
deployment.apps/myapp-deployment
REVISION  CHANGE-CAUSE
1         <none>
2         <none>

Each revision stores the old ReplicaSet config — enabling rollback.

Analogy: Think of revisions like "save points" in a video game. Revision 1 is your first save. After an upgrade, Revision 2 is a new save. If you die (bug), reload Revision 1.

Deployment Strategies

Two strategies control how old PODs are replaced with new ones during an update.

Feature Recreate RollingUpdate (Default)
What happens? Destroy ALL old PODs, then create ALL new PODs Destroy old one-by-one, create new one-by-one
Downtime? YES — app goes DOWN NO — app stays UP
Speed Fast (all at once) Slow (gradual)
Use case Dev / non-critical Production (zero-downtime)
Default? YES

Recreate Strategy

Old v1 DOWN New v2

All old pods die → downtime → new pods created

RollingUpdate (Default)

v1 v1→v2 v2

Old pods replaced one at a time — app stays live

Analogy: Recreate = replace all tires at once (car on jacks, can't drive).
RollingUpdate = replace tires one at a time (car stays drivable).

Updating Deployments

Two ways to update a Deployment's container image:

Method 1 — Edit YAML & Apply

$ kubectl apply -f deployment-definition.yml

Best practice — YAML matches cluster state.
Version-control friendly.

Method 2 — Imperative Command

$ kubectl set image deployment/myapp-deployment \
  nginx=nginx:1.9.1

YAML file will NOT match the live state.
Use only for quick tests.

Tip: Always prefer kubectl apply with a YAML file stored in git. The imperative set image command can lead to "drift" between your YAML and live cluster.

How Upgrades Work (Behind the Scenes)

When you update a Deployment's image, Kubernetes does not modify the existing ReplicaSet. Instead, it creates a brand-new ReplicaSet with the new image, then gradually scales the old RS down while scaling the new RS up.

Before Update

RS: myapp-5d5b (v1) — 5 replicas RS: (none)

During Update

RS: myapp-5d5b (v1) — 3→0 RS: myapp-8c7d (v2) — 0→3

After Update

RS: myapp-5d5b (v1) — 0 RS: myapp-8c7d (v2) — 5

Check ReplicaSets after update

$ kubectl get replicasets 
NAME                         DESIRED   CURRENT   READY   AGE
myapp-deployment-5d5b...     0         0         0       10m     ← old RS (scaled to 0)
myapp-deployment-8c7d...     5         5         5       2m      ← new RS (running)

Old version PODs slowly replaced by new version — zero downtime.

Simple: Old version slowwwly replaced by new version. The old RS sticks around at 0 replicas so you can rollback instantly.

Rollback

Something wrong with v2? Just undo — Kubernetes destroys the new PODs and brings the old ones back up. It's the "Undo" button for deployments.

$ kubectl rollout undo deployment/myapp-deployment
deployment.apps/myapp-deployment rolled back

Before Rollback

RS-v1 (old): 0 desired RS-v2 (new): 5 desired ✅

After Rollback

RS-v1 (old): 5 desired ✅ RS-v2 (new): 0 desired

How it works: rollout undo flips the desired replica counts — scales up the old RS and scales down the new RS. The old ReplicaSet was always there (with 0 replicas), so the rollback is instant.

Analogy: Imagine two elevators — you pressed the wrong floor button. Instead of reprogramming, you just press "undo" and go back to where you were.

kubectl run — Creates a Deployment (Not a POD!)

A common surprise: kubectl run nginx --image=nginx does not create a bare POD — it creates a Deployment (and thus a ReplicaSet + PODs).

$ kubectl run nginx --image=nginx
deployment.apps/nginx created

Quick and easy for testing

But for production…

Use definition files (YAML) instead. They go into version control, are reproducible, and you can review changes before applying.

Remember: kubectl run = Deployment. If you want a bare POD, use kubectl run --restart=Never or write a YAML with kind: Pod.

The Golden Rule

Use definition files for everything you care about. kubectl apply -f ensures your YAML matches the cluster. The imperative commands (set image, kubectl run) are fine for quick experiments but cause configuration drift.
