Example Voting Application

A complete multi-tier microservices application that demonstrates how independent containers work together in a Kubernetes cluster. Users vote and see live results — all powered by containers.

┌──────────────┐ ┌──────────┐ ┌──────────┐ ┌──────────────┐ │ Voting App │───▶│ Redis │───▶│ Worker │───▶│ PostgreSQL │ │ (Python) │ │ (in-memory)│ │ (.NET) │ │ (DB) │ │ :3000 │ │ :6379 │ │ │ │ :5432 │ └──────────────┘ └──────────┘ └──────────┘ └──────┬───────┘ │ ┌──────────▼──────┐ │ Result App │ │ (NodeJS) │ │ :3001 │ └─────────────────┘

The Five Components

1 voting-app Python / Flask

A web frontend where users cast votes. Two buttons: Cats or Dogs. Runs on port :3000.

2 redis In-Memory DB

Temporarily stores incoming votes. Acts as a buffer between the voting app and the persistent database. Port :6379.

3 worker .NET

Background consumer. Reads votes from Redis and writes them to PostgreSQL. No external port — runs internally.

4 db PostgreSQL

Persistent database that stores the final vote counts. Port :5432. Retains data even if the container restarts.

5 result-app NodeJS

A web frontend that displays live election results. Reads from PostgreSQL. Shows a bar chart of cat vs dog votes. Port :3001.

Goals of This Exercise

  • Deploy containers — Get all five applications running as PODs in the cluster.
  • Enable connectivity — Make the right services talk to each other (e.g. voting-app → redis, worker → db).
  • Provide external access — Allow end users to reach voting-app and result-app from their browsers.

Deployment Workflow (High-Level)

Create PODs ClusterIP Services LoadBalancer Services Upgrade to Deployments

Initial Setup — Deploying with PODs

The simplest approach: create each component as a standalone POD. This works but doesn't scale or self-heal. We add Services to enable internal and external communication.

Service Strategy

ClusterIP Services Internal

Used for redis and db. These services need to be reachable only by other components inside the cluster (voting-app → redis, worker → db). No external access needed.

NodePort / LoadBalancer Services External

Used for voting-app and result-app. End users need to access these from outside the cluster via a browser.

Step 1: Create the PODs

voting-app POD

# voting-app-pod.yaml apiVersion: v1 kind: Pod metadata: name: voting-app-pod labels: name: voting-app-pod app: voting-app spec: containers: - name: voting-app image: kodekloud/examplevotingapp_vote:v1 ports: - containerPort: 80

redis POD

# redis-pod.yaml apiVersion: v1 kind: Pod metadata: name: redis-pod labels: name: redis-pod app: redis spec: containers: - name: redis image: redis:alpine ports: - containerPort: 6379

worker POD

# worker-pod.yaml apiVersion: v1 kind: Pod metadata: name: worker-pod labels: name: worker-pod app: worker spec: containers: - name: worker image: kodekloud/examplevotingapp_worker:v1

db POD (PostgreSQL)

# db-pod.yaml apiVersion: v1 kind: Pod metadata: name: db-pod labels: name: db-pod app: db spec: containers: - name: db image: postgres:alpine ports: - containerPort: 5432 env: - name: POSTGRES_USER value: postgres - name: POSTGRES_PASSWORD value: postgres

result-app POD

# result-app-pod.yaml apiVersion: v1 kind: Pod metadata: name: result-app-pod labels: name: result-app-pod app: result-app spec: containers: - name: result-app image: kodekloud/examplevotingapp_result:v1 ports: - containerPort: 80

Create the PODs

$ kubectl apply -f voting-app-pod.yaml $ kubectl apply -f redis-pod.yaml $ kubectl apply -f worker-pod.yaml $ kubectl apply -f db-pod.yaml $ kubectl apply -f result-app-pod.yaml # Verify all PODs are running $ kubectl get pods NAME READY STATUS RESTARTS voting-app-pod 1/1 Running 0 redis-pod 1/1 Running 0 worker-pod 1/1 Running 0 db-pod 1/1 Running 0 result-app-pod 1/1 Running 0

Problem: At this point, none of the components can talk to each other. PODs have internal IPs that change if they restart. We need Services to provide stable endpoints.

Step 2: Create ClusterIP Services (Internal Communication)

ClusterIP Services provide a stable internal IP and DNS name so that other PODs can reliably reach redis and db.

redis Service (ClusterIP)

# redis-service.yaml apiVersion: v1 kind: Service metadata: name: redis spec: selector: app: redis name: redis-pod ports: - port: 6379 targetPort: 6379

db Service (ClusterIP)

# db-service.yaml apiVersion: v1 kind: Service metadata: name: db spec: selector: app: db name: db-pod ports: - port: 5432 targetPort: 5432

Step 3: Create NodePort Services (External Access)

For the user-facing apps (voting-app, result-app), we need NodePort or LoadBalancer Services so external browsers can reach them.

voting-app Service (NodePort)

# voting-app-service.yaml apiVersion: v1 kind: Service metadata: name: voting-app-service spec: type: NodePort selector: app: voting-app name: voting-app-pod ports: - port: 80 targetPort: 80 nodePort: 30004

result-app Service (NodePort)

# result-app-service.yaml apiVersion: v1 kind: Service metadata: name: result-app-service spec: type: NodePort selector: app: result-app name: result-app-pod ports: - port: 80 targetPort: 80 nodePort: 30005

Create All Services

$ kubectl apply -f redis-service.yaml $ kubectl apply -f db-service.yaml $ kubectl apply -f voting-app-service.yaml $ kubectl apply -f result-app-service.yaml # List all services $ kubectl get services NAME TYPE CLUSTER-IP PORT(S) redis ClusterIP 10.99.143.178 6379/TCP db ClusterIP 10.108.56.45 5432/TCP voting-app-service NodePort 10.101.78.223 80:30004/TCP result-app-service NodePort 10.104.12.89 80:30005/TCP # Access voting app from browser (Minikube) $ minikube service voting-app-service

Note: This works but has a major limitation — if a POD crashes, it's gone forever. No automatic restart, no scaling, no rolling updates. That's why we need Deployments.

Improving with Deployments

Replace all PODs with Deployments. Deployments give us scaling, self-healing, and rolling updates — three essential features for production applications.

Deployment Hierarchy

Deployment ──▶ ReplicaSet ──▶ PODs (desired state) (replica mgmt) (actual containers)

Step 1: Convert PODs to Deployments

Each Deployment manages a ReplicaSet, which in turn manages the PODs. The same selector labels connect Services to PODs.

voting-app Deployment

# voting-app-deployment.yaml apiVersion: apps/v1 kind: Deployment metadata: name: voting-app-deployment spec: replicas: 3 selector: matchLabels: name: voting-app-pod app: voting-app template: metadata: labels: name: voting-app-pod app: voting-app spec: containers: - name: voting-app image: kodekloud/examplevotingapp_vote:v1 ports: - containerPort: 80

redis Deployment

# redis-deployment.yaml apiVersion: apps/v1 kind: Deployment metadata: name: redis-deployment spec: replicas: 1 selector: matchLabels: name: redis-pod app: redis template: metadata: labels: name: redis-pod app: redis spec: containers: - name: redis image: redis:alpine ports: - containerPort: 6379

worker Deployment

# worker-deployment.yaml apiVersion: apps/v1 kind: Deployment metadata: name: worker-deployment spec: replicas: 1 selector: matchLabels: name: worker-pod app: worker template: metadata: labels: name: worker-pod app: worker spec: containers: - name: worker image: kodekloud/examplevotingapp_worker:v1

db Deployment (PostgreSQL)

# db-deployment.yaml apiVersion: apps/v1 kind: Deployment metadata: name: db-deployment spec: replicas: 1 selector: matchLabels: name: db-pod app: db template: metadata: labels: name: db-pod app: db spec: containers: - name: db image: postgres:alpine ports: - containerPort: 5432 env: - name: POSTGRES_USER value: postgres - name: POSTGRES_PASSWORD value: postgres

result-app Deployment

# result-app-deployment.yaml apiVersion: apps/v1 kind: Deployment metadata: name: result-app-deployment spec: replicas: 3 selector: matchLabels: name: result-app-pod app: result-app template: metadata: labels: name: result-app-pod app: result-app spec: containers: - name: result-app image: kodekloud/examplevotingapp_result:v1 ports: - containerPort: 80

Deploy and Verify

# Delete old PODs (Deployments will recreate them) $ kubectl delete pod voting-app-pod redis-pod worker-pod db-pod result-app-pod # Create Deployments $ kubectl apply -f voting-app-deployment.yaml $ kubectl apply -f redis-deployment.yaml $ kubectl apply -f worker-deployment.yaml $ kubectl apply -f db-deployment.yaml $ kubectl apply -f result-app-deployment.yaml # Check Deployments $ kubectl get deployments NAME READY UP-TO-DATE AVAILABLE voting-app-deployment 3/3 3 3 redis-deployment 1/1 1 1 worker-deployment 1/1 1 1 db-deployment 1/1 1 1 result-app-deployment 3/3 3 3 # Check the PODs (notice the generated names) $ kubectl get pods NAME READY STATUS voting-app-deployment-7d8f9c4b6f-abc12 1/1 Running voting-app-deployment-7d8f9c4b6f-def34 1/1 Running voting-app-deployment-7d8f9c4b6f-ghi56 1/1 Running redis-deployment-5c6f7a8b9c-xyz78 1/1 Running worker-deployment-4b3c2d1e0f-uvw90 1/1 Running db-deployment-9a8b7c6d5e-rst12 1/1 Running result-app-deployment-2f3g4h5i6j-mn34 1/1 Running result-app-deployment-2f3g4h5i6j-op56 1/1 Running result-app-deployment-2f3g4h5i6j-qr78 1/1 Running

Scaling

Change replicas and re-apply. Or use kubectl scale deployment voting-app-deployment --replicas=5

Self-Healing

If a POD crashes, the ReplicaSet creates a new one automatically. No manual intervention needed.

Rolling Updates

Update image, re-apply. K8s gradually replaces PODs with zero downtime.

Key Insight: The Services remain exactly the same — their selector labels (app: voting-app) match the PODs created by the Deployment. No Service changes needed when switching from PODs to Deployments.

External Access Challenge

When running Kubernetes in a multi-node environment (e.g. VirtualBox with multiple VMs), providing a single external URL for users becomes surprisingly difficult.

The Problem

Multiple Nodes = Multiple IPs

In a 3-node cluster, a NodePort service creates the same port (e.g. 30004) on every node. Users can reach any node IP, but each has a different address:

  • http://192.168.1.10:30004
  • http://192.168.1.11:30004
  • http://192.168.1.12:30004
Users Need a Single URL

End users shouldn't have to pick a node. They need one stable URL. Without a load balancer, you'd have to tell users "try this IP, and if it's down, try that IP" — that's terrible UX.

Solution in VirtualBox: Manual Load Balancer VM

In an on-prem / VirtualBox setup, you need to manually create a dedicated Load Balancer VM running software like HAProxy or NGINX. This VM sits between users and the cluster nodes:

Users ──▶ Load Balancer VM ──▶ Node 1:30004 ──▶ Node 2:30004 ──▶ Node 3:30004

Drawback: Setting up and configuring HAProxy/NGINX is tedious. You have to manage the VM, update configuration when nodes change, handle TLS termination, and monitor the load balancer itself. It works, but it's a lot of manual work.

Cloud Load Balancer Solution

On supported cloud platforms (GCP, AWS, Azure), Kubernetes can provision a native cloud load balancer automatically — no manual VM setup needed.

How It Works

1 Set Service Type to LoadBalancer

Instead of type: NodePort, use type: LoadBalancer. K8s detects the cloud platform and communicates with its API.

2 Cloud Provisions LB Automatically

The cloud provider (GCP, AWS, Azure) creates a native load balancer resource — e.g. GCP HTTP(S) Load Balancer, AWS ELB/NLB, Azure LB.

3 Single External IP Assigned

The load balancer gets a public IP address. All traffic flows through this single entry point, then is distributed across cluster nodes.

4 DNS Points to LB

Create a DNS record (e.g. vote.myapp.com) pointing to the load balancer IP. End users access via this friendly URL.

LoadBalancer Service YAML

# voting-app-lb-service.yaml apiVersion: v1 kind: Service metadata: name: voting-app-service spec: type: LoadBalancer # ← Changed from NodePort selector: app: voting-app name: voting-app-pod ports: - port: 80 targetPort: 80

Create and Verify

$ kubectl apply -f voting-app-lb-service.yaml # Watch for the EXTERNAL-IP to be provisioned $ kubectl get services NAME TYPE CLUSTER-IP EXTERNAL-IP PORT(S) voting-app-service LoadBalancer 10.101.78.223 35.184.72.198 80:30004/TCP # Access the application via the cloud load balancer $ curl http://35.184.72.198

The Cloud Does the Heavy Lifting — No need to manually configure HAProxy or NGINX. The cloud provider's load balancer handles health checks, traffic distribution, TLS termination, and auto-scaling. Just set type: LoadBalancer and let K8s + cloud do the rest.

Service Type Comparison

Type Access Use Case Cloud Needed?
ClusterIP Internal only redis, db, worker No
NodePort Node IP + static port Dev / testing No
LoadBalancer Single external IP Production Yes (auto-provisions)

Conclusion & Recap

We've covered the full journey — from understanding containers to deploying a real-world multi-tier microservices application on Kubernetes. Here's everything we've learned across all chapters:

Containers & Docker

Packaging applications with dependencies into lightweight, portable containers. Running them locally with Docker.

Container Orchestration

Managing hundreds of containers across multiple machines. Scheduling, scaling, networking, and health monitoring.

K8s Setup Options

Minikube (local dev), kubeadm (multi-node), managed cloud (GKE, EKS, AKS). Choose based on your needs.

PODs

The smallest deployable unit. A POD wraps one or more containers with shared storage and network.

ReplicaSets

Ensures a specified number of POD replicas are running at all times. Foundation for high availability.

Deployments

Declarative updates for PODs and ReplicaSets. Supports scaling, self-healing, rolling updates, rollback.

Services

Stable networking for PODs. ClusterIP (internal), NodePort (external on each node), LoadBalancer (single cloud LB).

Networking

POD-to-POD communication across nodes. CNI plugins (Calico, Flannel, Weave) handle the overlay network.

kubectl Commands

The K8s CLI for managing clusters. get, apply, describe, delete, logs, exec, scale.

Deploying on Cloud

Replace NodePort with LoadBalancer, let the cloud provider provision a native load balancer, point DNS, and your app is live with a single URL. Production-ready.
