1. High Availability

What happens if a POD crashes? Users lose access. A Replication Controller ensures the specified number of PODs are running at all times. Even with just 1 POD: if it fails, a new one is created automatically.

Example: You set replicas: 3. If one POD dies, Kubernetes immediately creates a replacement POD to bring the count back to 3. Users never experience downtime.

With Replication
  • 3 PODs running
  • 1 crashes → replaced instantly
  • Users stay online
  • System self-heals
Without Replication
  • Single POD running
  • It crashes → service down
  • Users get errors
  • Manual intervention needed

2. Load Balancing & Scaling

Multiple PODs share the user load. When demand increases, deploy more PODs. When resources run out on one node, PODs are deployed on other nodes. The Replication Controller spans across multiple nodes in the cluster.

Analogy: More workers = faster work. One cashier handles 10 customers/hour. Need 100 customers/hour? Deploy 10 cashiers across multiple checkout lanes (nodes).

# What happens under the hood:
Node 1:  [POD-a] [POD-b]   ← 2 replicas here
Node 2:  [POD-c]              ← 1 replica here
Request → distributed across all 3 PODs

3. Replication Controller vs ReplicaSet

Replication Controller (RC) = older technology being replaced. ReplicaSet (RS) = the new, recommended way. Same purpose, different internals. This cheatsheet sticks with ReplicaSet going forward.

Feature ReplicationController ReplicaSet
apiVersion v1 apps/v1
kind ReplicationController ReplicaSet
Selector required? No (implicit) Yes (matchLabels)
Status Deprecated Recommended

4. Replication Controller YAML

The POD definition is nested inside spec.template. The replicas field sits alongside template.

rc-definition.yml

apiVersion: v1
kind: ReplicationController
metadata:
  name: myapp-rc
  labels:
    app: myapp
    type: front-end
spec:
  template:
    # POD definition goes here
    metadata:
      name: myapp-pod
      labels:
        app: myapp
        type: front-end
    spec:
      containers:
      - name: nginx-container
        image: nginx
  replicas: 3

Commands & Output

Create the RC:

$ kubectl create -f rc-definition.yml
replicationcontroller/myapp-rc created

List RCs:

$ kubectl get replicationcontroller
NAME       DESIRED   CURRENT   READY   AGE
myapp-rc   3         3         3       10s

List PODs (prefixed with RC name):

$ kubectl get pods
NAME             READY   STATUS    RESTARTS   AGE
myapp-rc-8d7k9   1/1     Running   0          10s
myapp-rc-9m2n4   1/1     Running   0          10s
myapp-rc-3p5r1   1/1     Running   0          10s

5. ReplicaSet YAML

Very similar to RC, but with three key differences:

  • apiVersion is apps/v1 (NOT v1!)
  • kind is ReplicaSet
  • Required: selector.matchLabels section to identify which PODs to monitor

replicaset-definition.yml

apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: myapp-replicaset
  labels:
    app: myapp
    type: front-end
spec:
  template:
    metadata:
      name: myapp-pod
      labels:
        app: myapp
        type: front-end
    spec:
      containers:
      - name: nginx-container
        image: nginx
  replicas: 3
  selector:
    matchLabels:
      type: front-end

Commands & Output

Create the ReplicaSet:

$ kubectl create -f replicaset-definition.yml
replicaset.apps/myapp-replicaset created

List ReplicaSets:

$ kubectl get replicaset
NAME               DESIRED   CURRENT   READY   AGE
myapp-replicaset   3         3         3       12s

Get detailed info:

$ kubectl describe replicaset myapp-replicaset
Name:         myapp-replicaset
Namespace:    default
Selector:     type=front-end
Labels:       app=myapp,type=front-end
Annotations:  <none>
Replicas:     3 current / 3 desired
Pods Status:  3 Running / 0 Waiting / 0 Succeeded / 0 Failed

6. Labels & Selectors Explained

Why labels? A ReplicaSet needs to know which PODs to monitor — there could be 100s of PODs in a cluster. Labels act as filters. The Selector matches those labels.

Analogy: Labels = nametags on people. Selector = "find all people wearing a 'VIP' nametag". The ReplicaSet only cares about PODs that match its selector.

How Selector Works

selector:
  matchLabels:
    type: front-end

This ReplicaSet will monitor all PODs with label type=front-end — even PODs it didn't create itself.

Visual: Labels on PODs

POD A | app=myapp type=front-end matched
POD B | app=myapp type=front-end matched
POD C | app=myapp type=back-end not matched

Only PODs where type=front-end are managed by this ReplicaSet.

Template Requirement

Even if PODs already exist with matching labels, the template is still required. Why? If an existing POD fails, the ReplicaSet needs the template to create a replacement. The template is the blueprint for new PODs.

Existing PODs with matching labels = adopted by RS
Template = blueprint for creating new PODs if needed

7. Scaling ReplicaSets

Three ways to scale. The kubectl scale command is a quick way, but it does not update the definition file!

Method 1: Update YAML file & apply

Edit replicas: 6 in your YAML, then run:

$ kubectl replace -f replicaset-definition.yml
replicaset.apps/myapp-replicaset replaced

Method 2: Scale using the definition file

$ kubectl scale --replicas=6 -f replicaset-definition.yml
replicaset.apps/myapp-replicaset scaled

The replicaset-definition.yml file is NOT updated!

Method 3: Scale by type/name

$ kubectl scale --replicas=6 replicaset myapp-replicaset
replicaset.apps/myapp-replicaset scaled

Verify scaling:

$ kubectl get pods
NAME                     READY   STATUS    RESTARTS   AGE
myapp-replicaset-7k9d2   1/1     Running   0          2m
myapp-replicaset-8m3n5   1/1     Running   0          2m
myapp-replicaset-9p4r1   1/1     Running   0          2m
myapp-replicaset-2j6k8   1/1     Running   0          5s    ← new
myapp-replicaset-4h7n9   1/1     Running   0          5s    ← new
myapp-replicaset-5t8v2   1/1     Running   0          5s    ← new

8. Commands Summary

Command Description
kubectl create -f replicaset-definition.yml Create ReplicaSet from YAML
kubectl get replicaset List all ReplicaSets (DESIRED, CURRENT, READY)
kubectl get replicaset -o wide Detailed list with container images
kubectl describe replicaset myapp-replicaset Detailed info (selector, events, POD status)
kubectl delete replicaset myapp-replicaset Delete RS and all underlying PODs
kubectl replace -f replicaset-definition.yml Update RS from modified YAML
kubectl scale --replicas=6 -f replicaset-definition.yml Scale (file-based, doesn't update file)
kubectl scale --replicas=6 replicaset myapp-replicaset Scale (name-based, doesn't update file)

Important: kubectl delete replicaset also deletes all PODs managed by that ReplicaSet! Use with care in production.

Pro tip: Always prefer ReplicaSet over ReplicationController. ReplicaSet is the future — it offers richer label selectors and is required by Deployments (Ch 5).
