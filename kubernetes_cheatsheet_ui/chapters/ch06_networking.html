1. POD Networking Basics

In Kubernetes, networking starts at the POD level. Here's how it works:

  • Node IP: The host machine (e.g., 192.168.1.2)
  • POD IP: Each POD gets its own IP (e.g., 10.244.0.2)
  • PODs communicate with each other via these internal IPs
  • Internal private network = 10.244.0.0

Unlike Docker (IP assigned to container), K8s assigns the IP to the POD. Containers inside the pod share that IP.

// POD Network Topology
Node (192.168.1.2)
├──
POD-A
└─ 10.244.0.2
├──
POD-B
└─ 10.244.0.3
└──
POD-C
└─ 10.244.0.4
// Think of it like:
Each POD = its own phone number
PODs call each other by IP

2. Single Node Networking

When using Minikube (single-node cluster), you have three distinct IP realms:

  • Your Laptop: 192.168.1.5 (host network)
  • Minikube VM: 192.168.99.100 (virtual machine IP)
  • POD inside VM: 10.244.0.2 (internal K8s network)

You cannot access the POD IP (10.244.0.2) directly from your laptop — they are on completely different networks.

Solution: Use a Service (NodePort / LoadBalancer) to expose the POD.

// Single-Node Network Layers
Laptop ── 192.168.1.5
└──
Minikube VM ── 192.168.99.100
└──
POD ── 10.244.0.2
// Access from laptop:
❌ curl 10.244.0.2
✅ kubectl port-forward ...
✅ kubectl expose ... (Service)

3. Cluster Networking Requirements

Kubernetes does NOT set up networking automatically. It expects YOU to provide a network that meets these rules:

Rule 1 — All containers/PODs can communicate with each other without NAT

No address translation needed between any PODs

Rule 2 — All nodes can communicate with all containers (and vice versa) without NAT

Nodes and PODs are directly reachable

Important: K8s does NOT implement this network itself. It just says: "Hey admin, make this work!"

// K8s Expectation Diagram
Node-1 (192.168.1.10)
├── POD-A (10.244.0.2)
└── POD-B (10.244.0.3)
Node-2 (192.168.1.11)
├── POD-C (10.244.1.2)
└── POD-D (10.244.1.3)
// All must reach all without NAT:
POD-A → POD-D ✅ (direct)
Node-1 → POD-C ✅ (direct)
POD-B → Node-2 ✅ (direct)

5. Multi-Node Cluster Networking

The problem without a networking solution:

Different nodes may use the same internal network (10.244.0.0) → IP conflicts!

The solution with Calico:

  • Calico assigns a different network range per node
  • Node 1: 10.244.1.0/24
  • Node 2: 10.244.2.0/24
  • Uses routing to enable cross-node POD communication
// Without Calico — IP Conflict!
Node-1: 10.244.0.0 network
Node-2: 10.244.0.0 network
PODs collide! ❌
// With Calico — Unique Per Node
Node-1 (192.168.1.10)
└── 10.244.1.0/24 (PODs: 10.244.1.2, 10.244.1.3)
Node-2 (192.168.1.11)
└── 10.244.2.0/24 (PODs: 10.244.2.2, 10.244.2.3)
// Cross-node POD-to-POD
10.244.1.2 → routes → 10.244.2.2 ✅

6. How Calico Works

Calico is a networking and network policy solution. Here's what it does:

  • Manages networks & IPs — assigns unique IPs across the entire cluster
  • Creates a virtual network — all PODs and nodes belong to one flat virtual network
  • Simple routing — enables POD-to-POD communication across different nodes
  • Result: All PODs can reach each other, no matter which node they're on

Think of Calico as the air traffic control for your cluster — it makes sure every POD knows exactly how to reach every other POD.

// Calico Virtual Network
Node-1 (192.168.1.10)
├── POD-A (10.244.1.2)
└── POD-B (10.244.1.3)
Node-2 (192.168.1.11)
├── POD-C (10.244.2.2)
└── POD-D (10.244.2.3)
All PODs ↔ All PODs ✅
// Calico also supports NetworkPolicies:
kubectl create -f policy.yaml

Quick Recap

POD IPs

Each POD gets its own internal IP (10.244.x.x). PODs talk via IP.

3 Network Layers

Laptop → VM/Node → POD. Not directly routable without Services.

K8s Expects

All PODs ↔ all PODs & all Nodes ↔ all PODs without NAT.

Plugins

Calico, Flannel, Cilium, Weave — pick one, install on cluster.

Calico

Assigns unique IP ranges per node. Routes cross-node traffic.

Flat Network

All PODs across all nodes see one single, flat, routable network.
