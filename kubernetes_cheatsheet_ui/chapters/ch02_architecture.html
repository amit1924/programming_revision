1. Nodes (formerly Minions)

A node is a machine — physical or virtual — with Kubernetes installed. This is the worker machine where your containers actually run. In older versions, nodes were called "Minions".

What it is

A node is like a single computer in a team. It provides the CPU, RAM, and storage to run your application containers.

Single node problem

If you have only one node and it fails, your app goes down. That's why you need multiple nodes.

Analogy: Nodes are like workers in a factory. One worker gets sick (fails) → production stops. Hire multiple workers → production continues even if one is absent.

2. Cluster

A cluster is a set of nodes grouped together. Even if one node fails, your app is still accessible from the other nodes. Multiple nodes also share the load so no single machine gets overwhelmed.

High Availability

One node crashes → other nodes keep serving. Users don't even notice.

Load Sharing

Work is distributed across nodes. No single node becomes a bottleneck.

Analogy: A single worker (node) vs a team of workers (cluster). One worker takes a break → the team keeps going. The team also splits the workload so nobody gets exhausted.

3. Master

The master is the brain of the cluster. It has Kubernetes installed and configured as the control plane. The master watches over all nodes and is responsible for orchestration.

Stores cluster info

Keeps track of every node, pod, and service in the cluster.

Monitors nodes

Constantly checks if nodes are healthy and running.

Moves workload

When a node fails, the master shifts its containers to healthy nodes.

Analogy: The master is the manager of the factory. The manager doesn't build products — they assign work, track progress, and reshuffle tasks when a worker is out sick.

4. Components of Kubernetes

When you install Kubernetes, these components get installed automatically. Each one has a specific job.

API Server

The front-end of Kubernetes. All users, management devices, and CLI tools talk to the API Server. It validates and processes every request before sending it to the cluster.

etcd (key-value store)

A distributed, reliable key-value store. It stores all the data needed to manage the cluster — configs, state, metadata. It also implements locks to prevent conflicts when multiple masters try to update the cluster at the same time.

Scheduler

Distributes work and containers across multiple nodes. Decides which node is best suited for each new container based on CPU, memory, and other constraints.

Controller Manager (the brain)

The brain behind orchestration. Controllers notice and respond when nodes, containers, or endpoints go down. They automatically bring up new containers to replace the failed ones.

Container Runtime

The actual software that runs your containers. Examples: Docker, CRI-O, containerd, Rocket. Think of it as the engine that powers each container.

kubelet (the node agent)

An agent running on every node. It ensures containers are running as expected and constantly reports back to the master. It's the bridge between the master and the worker nodes.

Simple view: API Server = reception desk, etcd = filing cabinet, Scheduler = dispatcher, Controller Manager = supervisor, Container Runtime = machinery, kubelet = floor manager.

5. Master vs Worker Nodes

Not all nodes are created equal. Masters manage, workers do the actual work.

Master Node
  • kube-apiserver — API front-end
  • etcd — cluster data store
  • Controller Manager — orchestration brain
  • Scheduler — workload distributor
Worker Node
  • kubelet — node agent
  • Container Runtime — runs containers (Docker, containerd, CRI-O)
  • kube-proxy — networking rules

Analogy: Master = manager (plans, assigns, monitors). Worker = employee (actually builds the product). Both are essential — a manager with no workers does nothing, and workers with no manager have no direction.

6. kubectl — The CLI Tool

kubectl (kube control) is the command-line tool you use to deploy and manage applications on a Kubernetes cluster. It talks to the API Server behind the scenes.

# Deploy an application kubectl run hello-minikube

Deploys an application called "hello-minikube" to the cluster.

# View cluster information kubectl cluster-info

Shows the cluster's API server address and dashboard URL.

# List all nodes in the cluster kubectl get nodes

Lists every node with its status, roles, and version.

# View all pods kubectl get pods

Lists all running pods in the default namespace.

# Get detailed info about a resource kubectl describe node worker-1

Shows detailed status, capacity, and events of a specific node.

Remember: kubectl is like your remote control for the entire cluster. Every command you type is sent to the API Server, which then instructs the cluster to make it happen.

7. Setup Options

There are several ways to set up Kubernetes — from simple single-node setups to full production-grade clusters.

Minikube

Single-node cluster running on your local machine. Easiest way to get started and learn. Bundles everything into one VM.

Best for learning
kubeadm

Multi-node cluster with master and workers on separate machines. More realistic than Minikube.

Best for practice
Cloud (GCP / AWS / Azure)

Hosted Kubernetes services like GKE, EKS, AKS. Fully managed — the cloud provider handles the master, you manage workers.

Best for production
play-with-k8s.com

Instant browser-based Kubernetes cluster. No installation needed — just open the browser and start.

Best for quick demo

8. Minikube

Minikube bundles all Kubernetes components into a single image/ISO. The executable downloads and deploys it inside a VM on your machine (VirtualBox, Hyper-V, or KVM).

What you need
  • • A hypervisor (VirtualBox / Hyper-V / KVM)
  • • kubectl CLI
  • • minikube executable
All-in-one VM

Everything runs inside a single VM — master, worker, etcd, scheduler — all on your local machine. Perfect for learning and testing.

# Start Minikube minikube start
# Check cluster status minikube status
# Open dashboard minikube dashboard

Tip: Minikube is like a practice kitchen — you have all the tools, but on a smaller scale. Make mistakes here before you cook for real customers!

9. kubeadm Setup (Multi-Node Cluster)

kubeadm creates a multi-node cluster with one master and multiple worker nodes on separate machines. This is more realistic and closer to a production setup.

1
Create multiple systems / VMs

Set up at least 2 machines — one for the master, one or more for workers. Can be physical or virtual.

2
Install Docker on all nodes

Every machine needs a container runtime. Install Docker (or containerd) on every node — master and workers.

sudo apt install docker.io
3
Install kubeadm on all nodes

Install kubeadm, kubelet, and kubectl on every machine. These are the Kubernetes binaries.

sudo apt install kubeadm kubelet kubectl
sudo apt-mark hold kubeadm kubelet kubectl
4
Initialize the master

On the master node, run kubeadm init. This sets up the control plane components.

sudo kubeadm init
5
Set up the POD network

Install a Container Network Interface (CNI) plugin. Options: Calico, Flannel, Weave, Cilium. This allows pods to talk to each other across nodes.

# Example with Calico kubectl apply -f https://docs.projectcalico.org/manifests/calico.yaml
6
Join worker nodes

On each worker node, run the join command with the token from kubeadm init. This connects the worker to the master.

# Run this on each worker node sudo kubeadm join --token <token> <master-ip>:6443

Analogy: kubeadm is like building a real factory. You set up each machine (node), install tools (Docker), hire a manager (kubeadm init), lay cables between machines (POD network), and bring workers in (kubeadm join).
