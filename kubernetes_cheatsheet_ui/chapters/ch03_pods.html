Chapter 3: PODs

The smallest building block of Kubernetes — wrapping containers into deployable units

1

Assumptions

Before we jump into PODs, let's get on the same page. This chapter assumes two things are already done:

  • Your app is built into a Docker image — and that image is pushed to a registry like Docker Hub (e.g. amit/myapp:latest).
  • A Kubernetes cluster is running — whether it's Minikube on your laptop, a cloud cluster (EKS, GKE, AKS), or a local setup with kind/kubeadm.
Our focus here is purely on deploying an application into K8s. Building the image and setting up the cluster are prerequisites we treat as done.
2

What is a POD?

A POD is the smallest and most fundamental unit you work with in Kubernetes. Think of it as a wrapper — or a "logical host" — that runs your container.

Simple Analogy

Imagine a shipping container at a port. The shipping container is the POD. The actual cargo (your application) is the container inside it. The port crane (Kubernetes) picks up and moves entire shipping containers — not loose cargo.

Key Point

Kubernetes does NOT deploy containers directly. A container is always encapsulated inside a POD. The POD is what gets scheduled onto a Node. No POD = no running container.

In One Sentence

A POD is a single instance of your application — a wrapper around one (or more) containers that shares network, storage, and a lifecycle.

3

PODs & Scaling

There is usually a one-to-one relationship between a POD and the container running inside it. When you need to scale your application, you don't stuff more containers into an existing POD — you create new PODs.

Scale Up

Traffic spikes → create more PODs. Each new POD runs its own instance of the application.

1 POD = 1 instance 3 PODs = 3 instances

Scale Down

Traffic drops → delete PODs. Kubernetes removes entire PODs, not individual containers inside them.

5 PODs → 2 PODs 2 instances remain
Remember: In Kubernetes, you scale by adding or removing PODs, not containers. More PODs = more replicas = higher availability.
4

Multi-Container PODs

While rare, a single POD can host multiple containers. These are usually helper or sidecar containers that work alongside your main application container.

Same Network

Containers share the same IP and port space — they talk via localhost.

Same Storage

They can mount and share the same volumes.

Same Fate

Created together, destroyed together — they share a lifecycle.

Real-World Example

A web application container + a helper "log rotator" container that processes logs. They live in the same POD so they share the filesystem and network — the helper simply watches log files and rotates them. No need for complex external links.

Note: Multi-container PODs are the exception, not the rule. Start with one container per POD and only add sidecars when you have a clear need.
5

PODs vs Docker — Understanding the Shift

Without Kubernetes, you deploy with docker run. Life is simple — until your app grows and needs helper containers.

Without K8s (Docker)

  • Run containers manually with docker run
  • Helper containers need explicit --link flags
  • Networks, volumes, monitoring — all manually configured
  • No built-in auto-healing or co-scheduling

With K8s (PODs)

  • Define everything declaratively in YAML
  • Containers in a POD share network — no links needed
  • Shared volumes, automatic lifecycle management
  • K8s keeps PODs running (self-healing)

The Big Idea

In the Docker world, you wire everything by hand. In Kubernetes, you define a POD with its containers, and K8s takes care of the rest — same network, same storage, same fate. Create together, die together, scale together.

6

kubectl for PODs

The kubectl CLI is your primary tool for interacting with Kubernetes. Here are the essential commands for working with PODs:

Create a POD — kubectl run nginx --image nginx 
$ kubectl run nginx --image nginx
pod/nginx created
This command launches a POD named nginx from the nginx image on Docker Hub. K8s pulls the image, creates the container inside a POD, and schedules it onto a Node. Note: kubectl run actually creates a Deployment (not just a Pod) in modern K8s versions. For a bare Pod, use a YAML file instead.
List PODs — kubectl get pods 
$ kubectl get pods
NAME                     READY   STATUS              RESTARTS   AGE
nginx-xxx-yyy            0/1     ContainerCreating   0          5s
nginx-xxx-yyy            1/1     Running             0          12s
Columns: NAME (POD name with unique hash), READY (containers ready / total), STATUS (ContainerCreating → Running), RESTARTS (how many times restarted), AGE (time since creation).
Image Pull: When you create a POD, Kubernetes automatically pulls the specified image from Docker Hub (the default registry) if it's not already cached on the Node.
7

PODs with YAML — Definition Files

Kubernetes uses YAML (or JSON) to define objects declaratively. Every Kubernetes YAML file — for any object — has 4 required top-level fields:

apiVersion

The K8s API version to use. For Pods: v1. For Deployments, ReplicaSets: apps/v1.

kind

The type of object: Pod, Service, ReplicaSet, Deployment, etc.

metadata

Data about the object: name (string) and labels (dictionary of key:value pairs).

spec

The desired state. For Pods: containers (list/array), each with name and image.

Quick Memory Trick

apiVersion + kind + metadata + spec = every K8s YAML file

8

Pod YAML Example — Putting It All Together

Here is a complete YAML file that defines a Pod with a single Nginx container:

pod-definition.yml 
apiVersion: v1
kind: Pod
metadata:
  name: myapp-pod
  labels:
    app: myapp
    type: front-end
spec:
  containers:
  - name: nginx-container
    image: nginx
apiVersion: v1

Pods use the core v1 API.

kind: Pod

Tells K8s we're creating a Pod object.

metadata.name: myapp-pod

The name of our Pod — must be unique within the Namespace.

metadata.labels

Key-value pairs to organize, filter, and select this Pod (e.g. app: myapp).

spec.containers

A list/array of container definitions. Each item has name and image.

image: nginx

The Docker image to pull (from Docker Hub by default). Can be nginx:1.25 or myrepo/myapp:v2.

Create the Pod from the YAML file 
$ kubectl create -f pod-definition.yml
pod/myapp-pod created
The -f flag tells kubectl create to read the YAML (or JSON) file. You can also use kubectl apply -f pod-definition.yml (declarative, preferred for updates).

kubectl get & describe — Inspecting PODs

Once your POD is running, you'll want to inspect its status and troubleshoot issues. Two commands are your best friends:

List all PODs in the default namespace 
$ kubectl get pods
NAME          READY   STATUS    RESTARTS   AGE
myapp-pod     1/1     Running   0          2m
STATUS tells you the current phase: Running (healthy), Pending (waiting to start), CrashLoopBackOff (crashing repeatedly), ContainerCreating (image still pulling).
Get detailed info about a specific POD 
$ kubectl describe pod myapp-pod
Name:             myapp-pod
Namespace:        default
Node:             minikube/192.168.49.2
Labels:           app=myapp
                  type=front-end
Annotations:      <none>
Status:           Running
IP:               10.244.0.5
Containers:
  nginx-container:
    Container ID:   docker://abc123...
    Image:          nginx
    State:          Running (started ...)
Events:
  Type    Reason     Age   From               Message
  ----    ------     ----  ----               -------
  Normal  Scheduled  2m    default-scheduler  Successfully assigned...
  Normal  Pulled     2m    kubelet            Container image "nginx" already present
  Normal  Created    2m    kubelet            Created container nginx-container
  Normal  Started    2m    kubelet            Started container nginx-container

What describe shows you

Name & Namespace Node assigned to Labels & Annotations Status (Running/Pending/etc) IP address Container details Events timeline (Scheduled → Pulled → Created → Started)
Troubleshooting tip: The Events section at the bottom of kubectl describe is the most valuable part when something goes wrong — it shows a chronological log of what K8s did and any errors encountered.
10

Tips & Tricks for YAML

A few mental models and best practices to keep your YAML clean and your Kubernetes life easier:

1. The Quad Structure

Every YAML file follows the same skeleton. Memorize it: 

apiVersion: <string>     # which K8s API to use
kind: <string>           # Pod, Service, Deployment, ...
metadata:                   # name + labels
  name: <string>
  labels: <dict>
spec:                       # desired state
  containers: <list>   # each has name + image

2. Labels Organize Everything

Labels are key-value pairs you attach to any K8s object. They let you filter, group, and select PODs: 

labels:
  app: myapp
  type: front-end      # filter: kubectl get pods -l type=front-end
  env: production       # filter: kubectl get pods -l env=production

3. Selectors Link Objects

Labels plus selectors are how one K8s object finds another. For example, a Service uses a selector to know which PODs to forward traffic to: 

# Service YAML — routes traffic to PODs with label "app: myapp"
selector:
  app: myapp             # matches PODs that have this label

4. Quick YAML Hygiene

  • Use 2 spaces for indentation — tabs break YAML.
  • Always quote values that look like numbers or booleans ("true", "123") in labels/annotations.
  • Validate YAML with kubectl create --dry-run=client -f file.yml before applying.
  • Keep related labels consistent (e.g. always include app, tier, env).
Golden Rule: When in doubt, run kubectl explain pod — it shows you the exact YAML schema for any K8s object directly in your terminal. No need to Google!
