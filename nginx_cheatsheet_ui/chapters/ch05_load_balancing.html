Your First Load Balancer

You've deployed a Rails app to a single server. Mom submits it to Reddit. It hits the front page. Thousands of visitors arrive. One server can't handle the load — you need to scale out with a load balancer.

The load balancer receives all incoming traffic and distributes it across a pool of application servers. nginx runs as a software load balancer using the http_proxy module.

Most basic config:

http {
  upstream backend {
    server 192.0.2.10;
    server 192.0.2.11;
  }

  server {
    listen 80;
    location / { proxy_pass http://backend; }
  }
}

The default load balancing method is round-robin — first request to 192.0.2.10, second to 192.0.2.11, third to 192.0.2.10, and so on. The proxy_pass + upstream directives make this work.

Load Balancing vs Reverse Proxy

Load balancing is a form of reverse proxying with three fundamental differences:

1. Backends

Load balancers typically reverse proxy across many backends, while a traditional reverse proxy serves a single backend.

2. Layer

Load balancers operate at Layer 7 (HTTP) or Layer 4 (TCP). Reverse proxies typically operate at Layer 7 only.

3. Scale

Load balancers see 10,000+ req/s, while an app server handles 100–200 req/s. That's 20x the traffic.

Handling Failure

When a server crashes, trips over a power cord, or just goes away — by default, a failed server is removed from the pool for 10 seconds.

Load balancers solve two fundamental problems:

Horizontal Scaling

Spread load across 5 cheap medium-powered servers instead of one single very-powerful expensive server.

High Availability

Servers are ephemeral. Load balancers provide redundancy — when one dies, traffic goes to the others.

Who load balances to load balancers?

With a single load balancer, you're back to a single point of failure. The answer is DNS. Use DNS load balancing to present multiple IPs for a single A Record.

# dig A example.com shows multiple A records
example.com.   287 IN   A   208.0.113.36
example.com.   287 IN   A   208.0.113.34
example.com.   287 IN   A   208.0.113.38

DNS drawbacks: poor clients use first IP, DNS caching, no failure indication.

Solution: DNS + keepalived (heartbeat + IP takeover via ARP broadcast).

AWS note: keepalived 1.2.8+ supports unicast and works on AWS where broadcast is filtered.

Configuring the Upstream Directive

The upstream block represents a group of servers. Servers can be IP addresses, hostnames, unix sockets, or a mix:

upstream backend {

  # IP Address with Port
  server 192.0.2.10:443;

  # Hostname
  server app1.example.com;

  # Unix Socket
  server unix:/u/apps/my_app/current/tmp/unicorn.sock;
}

Weighted Servers

Weights alter the proportion of traffic to each server. Useful for faster hardware or testing changes with less traffic.

upstream backend {
  server app1.example.com weight=3;
  server app2.example.com;
  server app3.example.com;
}

app1 gets 3x more traffic (weight 3 vs default 1).

You can also lower weight to test changes — a server with weight 1 in a pool of weight 2+2+1 receives only 20% of traffic.

Health Checks

Open Source Limitations

Open source nginx only has passive health checks — checks that occur during the request lifecycle. No active health checking.

  • Passive only — does not actively check health outside of requests
  • Does not validate response content — 500 errors are considered "healthy" as long as HTTP responds

Default: 1 error = server removed from pool for 10s. Three directives control behavior:

max_fails

Number of failures before server is removed from the pool. Default: 1.

upstream backend {
  server app1.example.com max_fails=2;
  server app2.example.com max_fails=100;
}

fail_timeout

Controls two things: (1) how long to remove the server from the pool, (2) the time window in which max_fails is counted. Default: 10s.

upstream backend {
  server app1.example.com max_fails=2 fail_timeout=5;
  server app2.example.com max_fails=100 fail_timeout=50;
}

proxy_next_upstream

Controls what conditions count as a failed request (incrementing max_fails). Default: error, timeout, invalid_header.

Name Meaning Default
error Error communicating with upstream Yes
timeout Timeout during communication Yes
invalid_header Empty or invalid response Yes
http_500 Server returned 500 status No
http_502 Server returned 502 status No
http_503 Server returned 503 status No
http_504 Server returned 504 status No

Note: error, timeout, and invalid_header are always enabled even if not explicitly set.

Recommendation: turn on http_502, http_503, http_504 — they indicate an unhealthy server (unresponsive or out of workers). Leave http_500 off — it can be triggered by broken code, not a sick server.

location / {
  proxy_next_upstream http_502 http_503 http_504;
  proxy_pass http://backend;
}

Removing a Server from the Pool

Use down to mark a server as permanently unavailable instead of commenting it out:

upstream backend {
  server app1.example.com;
  server app2.example.com down;
  server app3.example.com;
}

Using down preserves hashes when using ip_hash — removing the line entirely would remap all sticky sessions.

Backup Servers

Backup servers only receive traffic if all other servers in the pool are unavailable:

upstream backend {
  server app1.example.com;
  server app2.example.com;
  server app3.example.com;
  server app4.example.com backup;
}

Slow Start

Dynamically adjusts the weight over time, allowing a server to ramp up gradually. Essential for JIT languages (JVM) that need minutes to warm up:

upstream backend {
  server app1.example.com slow_start=60s;
  server app2.example.com;
}

DNS Resolution in Upstream

CRITICAL GOTCHA

nginx resolves hostnames ONCE at startup and caches the IP address FOREVER. If the IP of an upstream hostname changes (e.g., Amazon ELB), nginx will still use the old IP — proxying to the wrong website!

Fix: use the resolve parameter on the server directive plus the resolver directive:

http {
  resolver 8.8.8.8;

  upstream backend {
    server loadbalancer.east.elb.amazonaws.com resolve;
  }
}

Prefer a local DNS cache like dnsmasq over Google's public resolver.

Load Balancing Methods

Open source nginx ships with four load balancing algorithms:

Weighted Round Robin (Default)

Chooses servers in sequential order, respects weights. First request to server 1, second to server 2, etc. Resets to top after last server.

Least Connections

Picks the server with the fewest active connections. Enabled with least_conn.

upstream {
  least_conn;
  server app1.example.com;
  server app2.example.com;
}

Pitfall: can cause traffic spikes on recovered servers (they come back with 0 active connections). Active connection count is not a reliable indicator of server load.

IP Hash

Sticky sessions based on client IP. Same user always hits the same server. Enabled with ip_hash.

upstream {
  ip_hash;
  server app1.example.com;
  server app2.example.com;
}

Use down not removal to preserve hashes. Not recommended — sticky sessions are often a symptom of an unscalable application.

Hash

Hash on any arbitrary variable (URI, host, etc.). The consistent parameter uses the ketama algorithm to prevent full remap when servers are added/removed.

# Hash based on URI
upstream {
  hash $uri consistent;
  server app1.example.com;
  server app2.example.com;
}
# Implement ip_hash using hash
upstream {
  hash $remote_addr consistent;
  server app1.example.com;
  server app2.example.com;
}

Sticky Sessions (Cookie)

Cookie-based sticky sessions are available in nginx plus (commercial) only.

C10K with nginx

The "C10K Problem" is the challenge of serving 10,000 simultaneous concurrent connections. With tuning, nginx handles this easily — and can scale to 100,000+ connections.

Scalable load balancer configuration:

worker_processes auto;

events {
  worker_connections 16384;
}

http {
  sendfile on;
  tcp_nopush on;
  keepalive_timeout 90;

  server {
    listen *:80 backlog=2048 reuseport;
    listen *:443 ssl backlog=2048 reuseport;
    ssl_session_cache shared:SSL:20m;
    ssl_session_timeout 10m;
    ssl_session_tickets on;
    ssl_stapling on;
    ssl_stapling_verify on;
    ssl_trusted_certificate /etc/nginx/cert/trustchain.crt;
    resolver 8.8.8.8 8.8.4.4 valid=300s;
  }
}

Tuning Linux for Network Heavy Load

Without tuning the Linux kernel, even the most optimized nginx config won't reach peak performance.

net.core.somaxconn

Defines the kernel queue size for accepting new TCP connections. Default is a ridiculously low 128.

If you see "possible SYN flooding" in your syslog, you need to increase it:

# Set immediately
sysctl -w net.core.somaxconn=10000

# Persist across reboot — add to /etc/sysctl.conf
net.core.somaxconn=10000

Set it high enough for your burst traffic. If you can handle 10,000 req/s, set it to 10,000.

nginx vs ELB vs HAProxy

nginx vs ELB

ELB lacks URI routing, HTTP caching, and VirtualHost support. For anything serious on AWS, use nginx as your HTTP routing layer.

nginx vs HAProxy

HAProxy may be 5–10% faster on paper, but nginx simplifies your stack — you only need to become an expert in one piece of software. That trade-off beats a marginal speed gain.

Recommendation: nginx for everything.

HTTP and TCP Load Balancing

Layer 7 (HTTP)

  • Parses request, modifies headers
  • Routes by hostname
  • Slower — overhead of parsing HTTP
  • SSL terminates at LB

Layer 4 (TCP)

  • Forwards raw packets, no parsing
  • Faster — no HTTP overhead
  • SSL pass-thru to backend
  • Available since nginx 1.9.0 (open source)

TCP load balancing uses the stream block instead of http. No location blocks:

stream {
  server {
    listen *:80;
    proxy_pass backend;
  }

  upstream backend {
    server app01;
    server app02;
    server app03;
  }
}

TCP Proxy Protocol

TCP load balancing loses the client IP — packets appear to come from the load balancer. The Proxy Protocol solves this by injecting the originating source address into the TCP connection.

On the load balancer:

stream {
  server {
    listen *:80;
    proxy_pass backend;
    proxy_protocol on;
  }
}

On the backend server:

server {
  listen *:80 proxy_protocol;
  proxy_set_header X-Real-IP $proxy_protocol_addr;
}
