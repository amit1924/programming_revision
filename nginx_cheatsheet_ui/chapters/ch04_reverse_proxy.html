Forward Proxy vs Reverse Proxy

Unlike Apache, nginx does not have the ability to embed the programming language interpreter into the webserver (like Apache does with mod_php). Instead, nginx takes a much lighter weight approach — it's just a webserver and delegates running a web application to a separate server, proxying requests upstream.

Forward Proxy

Sits between all outgoing connections and the internet. The proxy terminates outgoing requests and forwards them. To the internet, all computers appear to be coming from the same source — the forward proxy.

Reverse Proxy

Multiplexes many connections from the internet to a backend application. The reverse proxy terminates the request and forwards it to the backend. This is the exact same concept as load balancing!

Load balancer vs Reverse Proxy: A load balancer typically communicates with upstream servers on different physical machines, while a reverse proxy often talks to a service on the same machine. The underlying concepts are nearly identical — since a reverse proxy just proxies HTTP and most dynamic applications speak HTTP, you can think of it as a local load balancer.

Configuring a Basic Rails Application

A Rails app running on WEBrick (port 3000) is great for development but not production. We use nginx to listen on port 80 and act as a reverse proxy.

# Basic Reverse Proxy configuration
http {
    upstream rails_app {
        server 127.0.0.1:3000;
    }

    server {
        listen *:80;
        root /path/to/application/public;

        location / {
            proxy_pass http://rails_app;
        }
    }
}
Scalability

WEBrick is single-threaded — nginx multiplexes incoming connections while waiting for upstream processes to finish.

Error Handling

If upstream times out or goes down, nginx gracefully returns 503 Service Unavailable or 502 Bad Gateway.

Serving Static Assets via nginx

Add a location block for /assets to serve static files directly through nginx (much faster):

server {
    listen *:80;
    root /path/to/application/public;

    location / {
        proxy_pass http://rails_app;
    }

    location /assets {

    }
}

With cache headers for maximum cache-ability:

location /assets {
    expires max;
    add_header Cache-Control public;
}

expires max sets the Expires header to "Thu, 31 Dec 2037 23:55:55 GMT" and Cache-Control to 10 years. The Cache-Control defaults to private — we set it to public so intermediate caches can also cache shared assets.

# Verify cache headers
$ curl -I 127.0.0.1/assets/test.jpg
HTTP/1.1 200 OK
Server: nginx/1.4.6 (Ubuntu)
Expires: Thu, 31 Dec 2037 23:55:55 GMT
Cache-Control: max-age=315360000
Cache-Control: public

A More Robust Reverse Proxy

Use try_files to check for static files before proxying — enabling maintenance mode and dynamic file serving.

Maintenance Mode

server {
    listen *:80;
    root /path/to/application/public;

    location / {
        try_files maintenance.html @rails;
    }

    location @rails {
        proxy_pass http://rails_app;
    }
}

Dynamic File Existence Check

server {
    listen *:80;
    root /path/to/application/public;

    location / {
        try_files $uri $uri/index.html @rails;
    }

    location @rails {
        proxy_pass http://rails_app;
    }
}

$uri contains the normalized (decoded and sanitized) URI of the web request. This allows any files and folders in the root path to be served statically by nginx instead of being forwarded to the backend.

Warning: Everything in the root path will be publicly accessible — never set root above your public directory. If root is set to /path/to/application, anyone could read source code directly by accessing http://example.org/app/config/secrets.yml.

Equivalent Apache Configuration

# Apache equivalent of try_files $uri $uri/index.html @rails
<VirtualHost *:80>
  DocumentRoot /path/to/application/public
  RewriteEngine On

  RewriteCond %{DOCUMENT_ROOT}/%{REQUEST_FILENAME} !-f
  RewriteRule ^/(.*)$ balancer://rails [P,QSA,L]

  <Proxy balancer://rails>
    BalancerMember http://127.0.0.1:3000
  </Proxy>
</VirtualHost>

Upstream with Unix Domain Sockets

When your upstream server is on the same machine, skip the TCP/Network stack overhead by using Unix Domain Sockets — inter-process communication within the OS kernel using the file system as the namespace.

Start thin with a Unix socket:

$ thin start --socket /tmp/rails.sock

Configure nginx to talk over the domain socket:

upstream rails_app {
    server unix:/tmp/rails.sock;
}

Custom Error Pages

HTTP status codes: 2xx Success 3xx Redirect 4xx Client Error 5xx Server Error. Common errors: 403 Forbidden, 404 Not Found, 500 Internal Server Error, 502 Bad Gateway.

Hiding nginx version: Use server_tokens off; to prevent nginx from returning its version and OS in error pages and the Server HTTP header.

error_page Directive

server {
    listen *:80;
    root /path/to/application/public;

    location / {
        error_page 404 /404.html;
        error_page 500 502 503 504 /50x.html;

        try_files $uri $uri/index.html @rails;
    }

    location @rails {
        proxy_pass http://rails_app;
    }
}

Other Neat Things with error_page

Change the status code

error_page 500 =200 /index.html;

Turns a 500 Internal Server Error into a 200 Ok (use with caution).

Redirect to a different URL

error_page 500 http://www.google.com;

Returns a 302 Found redirecting to an external URL.

Redirect to a named location

location / {
  error_page 404 = @fallback;
}

location @fallback {
  proxy_pass http://different_backend;
}

Forwards to a different upstream for dynamic error page generation.

Note: For redundancy or high-availability (retrying a request on a different backend), use proxy_next_upstream instead of error_page (see Chapter 7).

Adding Headers to the Upstream

Since reverse proxying is just HTTP, nginx can modify HTTP headers when forwarding requests using proxy_set_header.

X-Forwarded-Proto

proxy_set_header X-Forwarded-Proto $scheme;

Tells the backend whether the original request came as HTTP or HTTPS. $scheme contains either http or https.

Host Header

proxy_set_header Host $host;

By default nginx sets Host to $proxy_host (name:port from proxy_pass). Override with $host to preserve the actual domain used by the client.

# Example: setting headers in a named location block
location @rails {
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header Host $host;
    proxy_pass http://rails_app;
}

Real IP Module

Problem: when nginx proxies a request, the backend sees the load balancer's IP (e.g., 192.0.2.9) instead of the original client IP (e.g., 203.0.113.1). The Real IP module (--with-http_realip_module) solves this by injecting the X-Real-IP header.

On the Load Balancer

http {
  real_ip_header X-Real-IP;

  server {
    ...
  }
}

Enabled by default when the module is installed, but best practice to define it explicitly.

On the Reverse Proxy

http {
  real_ip_header X-Real-IP;
  set_real_ip_from 203.0.113.1;

  server {
    ...
  }
}

set_real_ip_from restricts which sources are trusted for the header — prevents IP spoofing.

Multiple Load Balancers

http {
    real_ip_header X-Real-IP;
    set_real_ip_from 203.0.113.1;
    set_real_ip_from 203.0.113.2;
    set_real_ip_from 203.0.113.0/24;

    server {
        ...
    }
}

DIY Alternative: Use proxy_set_header directly: proxy_set_header X-Real-IP $remote_addr; — a simpler approach that doesn't require the module.

Reverse Proxying Node.js

Basic Node app listening on port 3000:

// app.js
var http = require('http');

http.createServer(function (request, response) {
  time = (new Date).getTime().toString();
  response.writeHeader(200, {"Content-Type": "text/plain"});
  response.end(time);
}).listen(3000, "127.0.0.1");

console.log("Starting server running at http://127.0.0.1:3000/");

Process Supervisor: For production, use a process supervisor like pm2 instead of running node directly. Install with npm install -g pm2. pm2 provides CLI, monitoring tools, and log viewing.

The nginx configuration is nearly identical to Rails:

http {

    upstream node_app {
        server 127.0.0.1:3000;
    }

    server {
        listen *:80;
        root /path/to/application/public;

        location / {
            try_files $uri $uri/index.html @node;
        }

        location @node {
            proxy_pass http://node_app;
        }
    }
}

Reverse Proxy with WebSockets

WebSockets (standardized 2011) allow two-way communication over an HTTP connection. The client sends Connection: Upgrade and Upgrade: websocket headers; the server responds with 101 Switching Protocols.

# Client handshake request
GET /websocket HTTP/1.1
Host: www.example.org
Upgrade: websocket
Connection: Upgrade

# Server response
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade

Out of the box, nginx supports WebSockets. However, reverse proxying needs HTTP 1.1 for the backend (default is 1.0), and the Upgrade/Connection headers must be explicitly forwarded (they are hop-by-hop headers).

Basic WebSocket Config

location /chat {
  proxy_pass http://node_app;
  proxy_http_version 1.1;
  proxy_set_header Upgrade $http_upgrade;
  proxy_set_header Connection "upgrade";
}

Dynamic Mapping with map

The above config tries to upgrade every connection. Use map to dynamically set Connection based on the Upgrade header:

map $http_upgrade $connection_upgrade {
  'websocket' upgrade;
  default close;
}

location @node {
  proxy_pass http://node_app;
  proxy_http_version 1.1;
  proxy_set_header Upgrade $http_upgrade;
  proxy_set_header Connection $connection_upgrade;
}

The map block is equivalent to this pseudo-code:

switch ($http_upgrade) {
  case "websocket":
    $connection_upgrade = "upgrade";
    break;
  default:
    $connection_upgrade = "close";
}

WebSocket Node.js Server Example

// WebSocket server with 'websocket' library
var WebSocketServer = require('websocket').server;
var http = require('http');

var server = http.createServer(function (request, response) {
  time = (new Date).getTime().toString();
  response.writeHeader(200, {"Content-Type": "text/plain"});
  response.end(time);
});

server.listen(3000, "127.0.0.1");

websocketServer = new WebSocketServer({
  httpServer: server,
  autoAcceptConnections: false
});

websocketServer.on('request', function(request) {
  console.log("Received connection");
  var connection = request.accept('echo-protocol', request.origin);
  time = (new Date).getTime().toString();
  connection.SendUTF(time);
});

Don't forget about timeouts! proxy_read_timeout defaults to 60 seconds. If a WebSocket sits idle longer, nginx closes the connection. Instead of setting a very high timeout, implement a ping message every 20-30 seconds to keep the connection alive.
