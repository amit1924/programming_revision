The nginx.conf File

Like most software on Linux, the way that nginx works is specified in a configuration file called nginx.conf. When nginx is built from source, the path to the configuration file can be specified by changing the --conf-path flag.

If nginx was installed from source, the default location of the nginx.conf file is /usr/local/nginx/conf. If nginx was installed from a package, it may be located in /etc/nginx or /usr/local/etc/nginx, depending on the package maintainer and Linux distribution.

If you're not sure where to find the nginx.conf file, you can run nginx -t to determine the location:

# Check config file location and test syntax
$ /usr/sbin/nginx -t
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful

What does nginx -t do?

In addition to running as a web server, the nginx binary includes a few extra bits of utility functions that you can use. Passing the -t command line flag just tests that the configuration file is valid and exits.

Here is a table for reference (this can be accessed by running nginx -h):

Option Description
-?, -hshow the help
-vshow version and exit
-Vshow version AND configure options then exit
-ttest configuration and exit
-qsuppress non-error messages during configuration testing
-s signalsend signal to master process: stop, quit, reopen, reload
-p prefixset prefix path (default: /usr/share/nginx)
-c filenameset configuration file (default: /etc/nginx/nginx.conf)
-g directivesset global directives out of configuration file
-Tdumps the entire configuration to stdout

If you don't want to use the default path of the nginx configuration file, you can pass in your own location with nginx -c filename.

# Use a custom config file location
$ nginx -c /home/user/nginx.conf

Configuring and Running nginx

The nginx configuration file is easy to understand and quite readable — the syntax reads somewhat like code. The most basic nginx configuration that does something is shown below:

events {
}

http {
  server {
  }
}

If you used a package manager to install nginx, it was probably packaged with an init script: service nginx start will start the server. If you installed nginx from source, you can simply run nginx to start the server.

To verify that nginx is running, use ps or curl:

# Verify with ps — should see master and worker processes
$ ps aux | grep nginx
root 24323 0.0 0.0 85772 1213 ? Ss 01:24 0:00 nginx: master process
nobody 24324 0.0 0.0 85992 2004 ? S 01:24 0:00 nginx: worker process
# Verify with curl — should see HTML output
$ curl 127.0.0.1
<!DOCTYPE html>
<html>
<head>
<title>Welcome to nginx!</title>

Filling in the Blanks (Default Values)

With a nearly blank configuration file, nginx still serves HTTP requests to /usr/share/nginx/html. Here is what that configuration file actually looks like with the default values added:

# Basic configuration file, with default values
user nobody nogroup;
worker_processes 1;

events {
  worker_connections 512;
}

http {
  server {
    listen *:80;
    server_name "";
    root /usr/share/nginx/html;
  }
}

The configuration file is made up of directives. There are two types:

Simple Directives

A simple statement like listen *:80;. Made up of a name, parameters, and a closing semicolon. Simple directives can take multiple parameters, some optional (key-value pairs or just the key name for true values).

listen *:80 ssl backlog=511;

For ssl, the parameter was passed without a corresponding value — this indicates a true value and turns SSL on.

Context Directives

Similar to a simple directive but wraps a group of directives inside curly braces instead of ending in a semicolon. Context directives can be nested and provide a configuration inheritance model. Examples: events, http, and server.

Directive Inheritance

nginx has a very lightweight inheritance model. Directives are always inherited downwards. You may overwrite previously defined directives in nested contexts:

server {
  root /usr/share/nginx/html;

  location /foo {
    root /usr/share;
  }
}

If the root directive was not explicitly specified inside the location block, the value would be inherited from the server context.

user and worker_processes

The user directive sets the unix user and group that the nginx worker processes will run as. By default, the user is nobody and the group is nogroup.

Running nginx as a non-root user

If you choose to run nginx as a non-root user, the user directive will be ignored. nginx will also not be able to bind to ports below 1024.

When you run ps, you'll see two nginx processes — a master running as root and a worker running as nobody. On Linux, only the root user can bind to ports below 1024. The master process reads the config, binds ports, and runs the worker processes. The worker process serves incoming HTTP requests.

The worker_processes directive configures the number of worker processes. Default is 1. It's common to set this to the number of CPU cores. The value auto can be set to have nginx auto-detect the number of logical CPU cores.

# ps output showing root master and nobody worker
$ ps aux | grep nginx
root 24484 0.0 0.0 85772 1312 ? Ss 1:38 0:00 nginx: master process
nobody 24485 0.0 0.0 85992 2004 ? S 1:38 0:00 nginx: worker process

Events Context

The events context is used to configure parts of the connection processing in nginx. There can only ever be one events context and it must be in the main context.

events {
  worker_connections 512;
}

nginx is an event-driven server. Each worker process is single-threaded and runs a non-blocking event loop to process requests very quickly. The worker_connections directive sets the maximum number of simultaneous connections per worker process (default: 512).

This limit includes connections from clients and any subsequent connections nginx makes to talk to your PHP or Rails application. On Linux, each connection counts as an open file, and there is an OS limit on maximum open files per process.

HTTP and Server Contexts

The HTTP context is where you define your HTTP servers. It is mostly a container for holding one or more server contexts. Shared directives placed in the HTTP context apply to all server contexts within.

http {
  server {
    listen *:80;
    server_name "";
    root /usr/share/nginx/html;
  }
}

Listen Directive

The listen directive tells the server which network interface and port to listen on, defaulting to *:80. It may be specified multiple times in a single server block:

server {
  listen *:80;
  listen *:443 ssl;
}

server_name Directive

The server_name directive is used to determine which server context to use for an incoming request. It is matched against the HTTP Host header. It can be an exact domain name, a wildcard, or a regular expression. A value of "" means no Host header is necessary.

# Example HTTP request with Host header
GET /foobar.html HTTP/1.0
Host: example.org
User-Agent: FakeUserAgent/1.0

Root Directive

The root directive specifies the path of the directory to serve static files out of. Any and all files in the root directory will become publicly available over HTTP. The URI is appended to the root path — a request to http://127.0.0.1/foo/test.html resolves to /usr/share/nginx/html/foo/test.html.

server {
  listen *:80;
  server_name "";
  root /usr/share/nginx/html;
}

Reloading and Stopping nginx

When you modify the nginx configuration, nginx does not pick it up automatically — you need to reload the process. To reload, send the HUP signal:

# Reload nginx configuration gracefully
$ kill -HUP `cat /var/run/nginx.pid`

When you reload, nginx verifies the config syntax first, so you don't have to worry about accidentally killing nginx with an invalid configuration. Reloading starts new worker processes and kills off old ones gracefully without dropping any requests.

To shutdown nginx gracefully:

# Graceful shutdown — no dropped requests
$ kill -QUIT `cat /var/run/nginx.pid`

The list of Unix signals that nginx responds to:

Signal Description
TERM, INTQuick shutdown
QUITGraceful shutdown
KILLHalts a stubborn process
HUPConfiguration reload
USR1Reopen the log files (useful for log rotation)
USR2Upgrade executable on the fly
WINCHGracefully shutdown worker processes

Making configuration changes

Anytime you make a configuration change to your nginx.conf file, you'll have to explicitly tell nginx to reload the configuration with the HUP signal — nginx does not pick up configuration changes automatically.

Upgrading the nginx binary without Downtime

nginx can upgrade itself on the fly without any downtime:

# 1. Find the master PID
$ cat /var/run/nginx.pid
24484

# 2. Send USR2 — starts new master process and workers
$ kill -USR2 24484

# 3. Send WINCH to old master — gracefully stop old workers
$ kill -WINCH 24484

# 4. Once old workers are done, send QUIT to kill old master
$ kill -QUIT 24484

After USR2, both old and new processes serve requests together. WINCH tells the old master to stop taking new requests and shut down children once in-flight requests complete. If you need to bail out, send HUP to the old master to spin up children again.

Serving Static Files

The most basic case for nginx is serving static files (HTML, CSS, JavaScript, images, etc). All files are stored in a common directory called a document root. When someone requests http://example.org/test.html, nginx looks for test.html inside the document root directory.

# Nginx with a document root
server {
  listen *:80;
  root /usr/share/nginx/html;
}

By default, nginx blesses a file named index.html to be shown when a filename isn't specified in the URL. You can override this with the index directive:

# Make foobar.html the index
server {
  listen *:80;
  root /usr/share/nginx/html;
  index ADifferentIndexFile.html;
}

You may also pass multiple index files. nginx will check for the existence of each file and serve the first one found:

# Multiple index files — checks existence in order
server {
  listen *:80;
  root /usr/share/nginx/html;
  index maintenance.html index.html;
}

Maintenance mode pattern

Create a maintenance.html page and nginx will serve that instead of index.html. When you're done, just delete the file and it goes back to serving the regular index page. This is a common way to handle deployments or scheduled downtime.

The Location Block

The location block allows us to provide a custom configuration for an incoming request URI by matching it against a prefix string or regular expression.

# Basic location block syntax
location optional_modifier uri_matcher {
  configuration_directives
}

Prefix matching: The most specific match wins. Order of prefix blocks does not matter.

# Basic location block example
location / {
  root /var/www/html;
}
location /foobar/ {
  root /data;
}

A request to http://example.org/foobar/test.html resolves to /data/foobar/test.html.

root vs alias

root appends the URI path to the root value. alias replaces the location path with the specified path. The trailing slash is important with alias.

# alias replaces the specified location path
location /gifs/ {
  alias /data/images/;
}

A request to http://example.org/gifs/business_cat.gif resolves to /data/images/business_cat.gif. With root, it would resolve to /data/images/gifs/business_cat.gif.

Exact Match (=)

The exact match modifier (=) matches an exact request URI and terminates the search immediately. It can improve performance for highly accessed URIs.

# Exact match — terminates search immediately
location = /foobar/ {
  ...
}
location /foobar/ {
  ...
}

A request URI for /foobar/ will always use the first block, even though the prefix block also matches.

Regular Expression Location Blocks

~ for case-sensitive regex, ~* for case-insensitive. Order matters — the first regex match wins.

# Case-sensitive: matches .gif and .jpg
location ~ \.(gif|jpg)$ {
  ...
}

# Case-insensitive: matches .GIF, .Gif, etc.
location ~* \.(gif|jpg)$ {
  ...
}

Regex is processor-intensive — use only when necessary. Prefix matching is always faster.

Skipping Regular Expressions (^~)

The ^~ modifier (carat-tilde) skips regex matching when this prefix is the best match:

# Using ^~ to skip regex evaluation
location ^~ /foobar/images {
  root /var/www/foobar;
}

location ~* \.(gif|jpg)$ {
  root /var/www/images;
}

Without ^~, a request for /foobar/images/dog.gif would match the regex block. With ^~, it uses the prefix block instead.

Location Block Selection Algorithm

The exact search algorithm nginx uses to select the location block:

Modifier Name Description
(none)PrefixMatches on the prefix of a URI
=Exact MatchMatches an exact URI
~Case-Sensitive RegexMatches against a case-sensitive regular expression
~*Case-Insensitive RegexMatches against a case-insensitive regular expression
^~Non-Regex PrefixMatches against a prefix and skips regex matching

Selection algorithm:

  1. Exact match (=) blocks are checked first. If found, terminate.
  2. Check prefix blocks for the longest matching prefix.
    a. If the best match has ^~, terminate.
  3. Check regex blocks in sequential order. First match wins, terminate.
  4. If no regex matched, use the best prefix from step 2.

Named Location Blocks

Named location blocks are denoted by the @ prefix. They cannot match the request URI directly and are used for internal redirection.

# Named location block (does nothing by itself)
location @foobar {
  ...
}

Named locations are commonly used with the try_files directive:

# Named location used with try_files
location / {
  try_files maintenance.html index.html @foobar;
}

location @foobar {
  ...
}

try_files checks for the existence of each file in order and uses the first one found. The last parameter may be a named location or an explicit error code:

# try_files with an error code
location / {
  try_files maintenance.html index.html =404;
}

If neither file is found, nginx returns a 404 error.

Location Block Inheritance

Directives defined in parent contexts (such as server or http) are inherited by nested location blocks. You can override inherited directives inside a location block to customize behavior for specific URI patterns. If a directive is not explicitly set in the location block, the value from the enclosing context is used.

Virtualhosts

nginx allows us to define as many server blocks as we want — this is called virtual hosting. Each server block can host a different website.

# Basic virtual hosts example
server {
  listen 80;
  server_name example.com;
}

server {
  listen 80;
  server_name foobar.com;
}

The server_name can contain subdomains, wildcards, and regular expressions:

# Multiple server names
server_name example.com www.example.com;

# Wildcards
server_name example.com *.example.com www.example.*;

# Matches both example.com and *.example.com
server_name .example.com;

# Regular expression
server_name ~^www[0-9]\.example\.com$;

Regular expressions can contain named capturing groups to set dynamic variables:

# Using capture groups in server_name
server {
  listen 80;
  server_name ~^(www\.)?(?<domain>.+)$;

  location / {
    root /sites/$domain;
  }
}

The (?<domain>.+) syntax creates a named capture group, setting the $domain variable to dynamically set the root path.

Default Server Block

nginx matches the IP:Port combination first, then the Host header against server_name:

  1. The exact name (www.example.com)
  2. The longest wildcard starting with an asterisk (*.example.com)
  3. The longest wildcard ending with an asterisk (www.*)
  4. The first matching regex, in order defined in the config

If no server_name matches, the default server is used. By default, this is the first server block defined. You can set it explicitly:

# Explicitly setting the default_server parameter
server {
  listen 80;
  server_name example.com;
}

server {
  listen 80 default_server;
  server_name foobar.com;
}

Dropping requests without a server name

You can drop requests made to your server without a Host header by returning the special nginx error code 444 (immediately close the connection):

# Server that drops requests without a Host header
server {
  listen 80;
  server_name "";
  return 444;
}

Configuring SSL

SSL (Secure Sockets Layer) creates a secure connection between an HTTP Client and an HTTP(S) Server. nginx offers a very robust and high performance SSL implementation.

# Most basic SSL Configuration
server {
  listen 80;
  listen 443 ssl;
  server_name www.foobar.com;
  ssl_certificate www.foobar.com.crt;
  ssl_certificate_key www.foobar.com.key;
}

Two listen directives allow a compact server block that serves both non-SSL and SSL requests. The ssl parameter tells nginx to expect SSL traffic on that port. ssl_certificate specifies the path to the signed certificate (PEM format), and ssl_certificate_key specifies the key.

If you specify a relative path, nginx prefixes it with the configuration directory (/etc/nginx). You may also specify an absolute path.

Beware outdated SSL information

In previous versions of nginx (prior to 0.7.14), you had to configure separate server blocks for non-SSL and SSL. The modern approach shown above is the correct syntax.

Sharing a wildcard certificate

You can generate a wildcard SSL certificate valid for multiple subdomains (e.g., *.example.com). Instead of configuring ssl_certificate for each server block, set it at the http block level for inheritance. This also has a lighter memory footprint as the certificate is loaded only once.

# Sharing SSL directives at the http level
http {
  ssl_certificate star.example.com.crt;
  ssl_certificate_key star.example.com.key;

  server {
    listen 80;
    listen 443 ssl;
    server_name www.example.com;
  }

  server {
    listen 80;
    listen 443 ssl;
    server_name billing.example.com;
  }
}

SNI (Server Name Indication)

Up until recently, each HTTPS site needed its own dedicated IP address because the entire HTTP payload was encrypted — including the Host header needed to determine which SSL configuration to use. SNI solves this by passing the domain name unencrypted, allowing multiple SSL sites on a single IP address.

SNI is supported on modern browsers:

Chrome (Vista+)
Safari 3.2.1 (Vista+)
Firefox 2.0+
MSIE 7.0 (Vista+)
Opera 8.0+
