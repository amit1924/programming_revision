Chapter 7: Storage & Volumes

How Docker manages data — file system layers, volumes, bind mounts, and storage drivers

File System Layered Architecture Container Layer Copy-on-Write Volumes Storage Drivers

1. Docker File System

Docker stores all its data — images, containers, volumes, build caches — under /var/lib/docker on the host machine.

# Docker's data directory structure
/var/lib/docker/
├── aufs/ # storage driver data (AUFS backend)
├── containers/ # each container's config, logs, metadata
├── image/ # image layer data and metadata
├── volumes/ # named volumes (persistent data)
├── overlay2/ # overlay2 driver data (modern default)
└── buildkit/ # BuildKit cache for faster builds
# On the host, inspect Docker's storage usage
$ docker system df
TYPE TOTAL ACTIVE SIZE RECLAIMABLE
Images 5 3 1.2GB 452MB (37%)
Containers 4 2 25.4MB 25.4MB (100%)
Local Volumes 3 1 312MB 0B (0%)
Build Cache 12 - 89.7MB 89.7MB

Real-world analogy: Think of /var/lib/docker like a filing cabinet. Each drawer has a purpose — one for recipes (images), one for cooked meals (containers), and one for leftovers (volumes).

2. Layered Architecture

Every Dockerfile instruction creates a read-only layer. Layers are cached and reused across builds. If two images share the same base (e.g. Ubuntu), they share all the common layers — zero extra disk cost.

# Image A Dockerfile
FROM ubuntu:22.04 ← Layer 1 (base)
RUN apt update && apt install -y python3
← Layer 2 (shared)
COPY app.py /app/ ← Layer 3
CMD ["python3", "/app/app.py"]
# Image B Dockerfile
FROM ubuntu:22.04 ← Layer 1 (same, shared)
RUN apt update && apt install -y python3
← Layer 2 (same, shared)
COPY server.py /app/ ← Layer 3 (different)
CMD ["python3", "/app/server.py"]
# Build both images and check shared bytes
$ docker build -t image-a -f Dockerfile.a .
$ docker build -t image-b -f Dockerfile.b .
$ docker images
REPOSITORY TAG IMAGE ID CREATED SIZE
image-b latest a1b2c3d4e5f6 10 seconds ago 198 MB
image-a latest 9f8e7d6c5b4a 20 seconds ago 195 MB
ubuntu 22.04 6a7b8c9d0e1f 2 weeks ago 77.8 MB
# See the layers of any image
$ docker history image-a
IMAGE CREATED CREATED BY SIZE
9f8e7d6c5b4a 20 seconds ago CMD ["python3" "/app/app.py"] 0B
d4c3b2a1f0e9 20 seconds ago COPY app.py /app/ 5.2kB
b8a7c6d5e4f3 30 seconds ago RUN apt update && apt install -y python3 117MB
6a7b8c9d0e1f 2 weeks ago /bin/sh -c #(nop) CMD ["bash"] 0B
...

Analogy: Like building blocks. The same flat base plate (Ubuntu) can be used to build a house or a castle. The shared blocks cost nothing extra and make the next build faster.

3. Container Layer (Read-Write)

When a container starts, Docker adds a thin read-write layer on top of the image's read-only layers. All changes made inside the container — creating, modifying, deleting files — happen in this writable layer. The original image is never touched.

Image Layers (read-only)
┌─────────────────────────────┐
│ CMD ["python3", "app.py"] │ ← Layer 3
├─────────────────────────────┤
│ COPY app.py /app/ │ ← Layer 2
├─────────────────────────────┤
│ ubuntu:22.04 base │ ← Layer 1
└─────────────────────────────┘
Running Container
┌─────────────────────────────┐
│ Container Layer (R/W) │
│ app.py modified, logs │
│ temp files, changes │ ← NEW — unique to this container
└─────────────────────────────┘
┌─────────────────────────────┐
│ CMD ["python3", "app.py"] │
├─────────────────────────────┤
│ COPY app.py /app/ │ ← Shared read-only
├─────────────────────────────┤
│ ubuntu:22.04 base │
└─────────────────────────────┘
# Start a container and modify a file
$ docker run -d --name myapp image-a
$ docker exec myapp sh -c "echo 'print(\"modified\")' > /app/app.py"
$ docker exec myapp cat /app/app.py
print("modified")

# The image is untouched
$ docker run --rm image-a cat /app/app.py
print("original")

Key insight: The image is like a read-only master CD. Each container is a sticky note taped on top — you can write all you want on the note, but the CD stays pristine. Delete the container, and the sticky note is gone too (unless you use a volume).

4. Copy-on-Write (CoW)

When a container modifies a file that exists in a lower read-only layer, Docker copies that file up to the container's writable layer first — then makes the change. The original in the image layer stays untouched. This is called copy-on-write.

Before edit
Container Layer: (empty)
───
Image Layer: temp.txt "hello"
After edit
Container Layer: temp.txt "hello world" ← copied up, then modified
───
Image Layer: temp.txt "hello" ← untouched
# CoW in action
$ docker run -d --name demo ubuntu:22.04 sleep 300
$ docker exec demo bash -c "echo 'hello world' > /tmp/temp.txt"
# /tmp/temp.txt didn't exist in the image, but that's fine
# If it existed in a lower layer, Docker copies it up first.
$ docker exec demo cat /tmp/temp.txt
hello world

# The image layer is untouched — new container still has original
$ docker run --rm ubuntu:22.04 cat /tmp/temp.txt
cat: /tmp/temp.txt: No such file or directory

Analogy: It's like photocopying a single page from a library book so you can scribble notes on it. The original book stays clean on the shelf. You only copy what you need to change — efficient and safe.

5. Volumes & Bind Mounts

By default, data written inside a container is lost when the container is deleted. Volumes and bind mounts let you persist data outside the container's writable layer.

Named Volume
# Create a named volume
$ docker volume create data_volume
data_volume

# Mount it into a container
$ docker run -v data_volume:/var/lib/mysql mysql

# Volumes live here:
/var/lib/docker/volumes/data_volume/_data
Bind Mount
# Mount a host directory (any path)
$ docker run -v /data/mysql:/var/lib/mysql mysql

# Newer, more explicit syntax:
$ docker run \
--mount type=bind,source=/data/mysql,target=/var/lib/mysql \
mysql
# Full example: MySQL with persistent database
$ docker volume create mysql_data
mysql_data

$ docker run -d \
--name mysql-db \
-e MYSQL_ROOT_PASSWORD=secret \
-v mysql_data:/var/lib/mysql \
mysql:8.0
a1b2c3d4e5f6...

# Stop and remove the container
$ docker stop mysql-db && docker rm mysql-db

# Start a new container with the same volume — data is still there!
$ docker run -d \
--name mysql-db-new \
-e MYSQL_ROOT_PASSWORD=secret \
-v mysql_data:/var/lib/mysql \
mysql:8.0
# List and inspect volumes
$ docker volume ls
DRIVER VOLUME NAME
local mysql_data
local data_volume

$ docker volume inspect mysql_data
[
{
"CreatedAt": "2025-01-15T10:30:00Z",
"Driver": "local",
"Mountpoint": "/var/lib/docker/volumes/mysql_data/_data",
"Name": "mysql_data"
}
]
Volume — Pros
  • Managed by Docker
  • Works on all OSes
  • Safer & isolated
  • Can be shared across containers
  • Backup/restore with Docker CLI
Bind Mount — Pros
  • Use any host path
  • Great for development (live code reload)
  • Files appear directly on host
  • No Docker daemon management needed

Analogy: A volume is like a USB drive — you plug it into a computer (container), save your work, and even if you turn off the computer, the data is still on the USB drive. Plug it into a different computer, and your files are right there.

6. Storage Drivers

Storage drivers are the technology that Docker uses to manage layers, copy-on-write, and container filesystems. They determine how Docker interacts with the underlying host filesystem.

Driver Description Best For
overlay2 Modern union filesystem; merges multiple dirs Default on most modern Linux distros
overlay Predecessor of overlay2 (fewer inodes) Older kernels (<4.0)
aufs Advanced multi-layered union fs Older Docker versions, Ubuntu <16.04
devicemapper Kernel-based block-level storage RHEL/CentOS <7 (no longer recommended)
btrfs / zfs Advanced filesystem with snapshots Systems already using btrfs/zfs
vfs Simple copy (no CoW, no layering) Testing only (very slow, no sharing)
# Check which storage driver Docker is using
$ docker info | grep -i "storage driver"
Storage Driver: overlay2

# See detailed driver configuration
$ docker info | grep -A 10 "Storage Driver"
Storage Driver: overlay2
Backing Filesystem: extfs
Supports d_type: true
Native Overlay Diff: true

Which one should you use? If you're on a modern Linux (kernel 4.0+), overlay2 is the default and best choice — performant, stable, and well-supported. You almost never need to change it.

Quick Recap

  • File System — All Docker data lives in /var/lib/docker/
  • Layers — Each Dockerfile instruction is a read-only layer; layers are shared between images
  • Container Layer — A thin R/W layer sits on top; changes stay in the container
  • Copy-on-Write — Files are copied up from image layers only when modified
  • Volumes / Bind Mounts — Persist data outside the container lifecycle
  • Storage Drivers — overlay2 (modern default), aufs, devicemapper, btrfs, zfs
