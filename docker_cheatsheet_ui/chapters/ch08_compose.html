Chapter 8: Docker Compose

Define and run multi-container apps with a single YAML file

What is Docker Compose?

Docker Compose is a tool that lets you define and run multi-container Docker applications. Instead of typing many docker run commands one by one, you write a single YAML file that describes all your services, networks, and volumes — then launch everything with one command.

Analogy: Making a full dinner. Without Compose, you'd cook rice (one docker run), then cook curry (another docker run), then set the table (another). With Compose, you write the whole recipe in one file and execute it — everything happens together.

One command to start everything:

docker-compose up

One command to stop everything:

docker-compose down

All containers are created on the same network by default, so they can talk to each other using service names as hostnames.

Basic docker-compose.yml

The docker-compose.yml file is the heart of Compose. The services: section defines each container. Here's a simple example with four services:

# docker-compose.yml
services:
  web:
    image: "mmumshad/simple-webapp"
  database:
    image: "mongodb"
  messaging:
    image: "redis:alpine"
  orchestration:
    image: "ansible"

Each service name becomes a hostname. So the web service can reach the database at database (not localhost). No more manually creating networks or linking containers — Compose handles it automatically.

Run it:

docker-compose up -d

The -d flag runs containers in the background (detached mode).

Sample Voting Application

The classic "voting app" example used throughout Docker's official docs. It has 5 services, each written in a different language:

voting-app (Python) — Web UI to cast votes
result-app (Node.js) — Real-time results display
redis (In-memory DB) — Buffers incoming votes
db (PostgreSQL) — Stores votes permanently
worker (.NET) — Moves votes from redis to PostgreSQL

Architecture flow:

[Browser] ──> voting-app ──> redis ──> worker ──> db
[Browser] ──> result-app ──────────────────> db

Each service runs in its own container with its own language runtime. Compose makes it trivial to wire them all together.

docker run --link (Legacy)

Before Compose and user-defined networks, you connected containers using the --link flag. It's deprecated (still works but not recommended), but you'll see it in old tutorials.

Pain point: Running the voting app without Compose means 5 separate docker run commands with multiple --link flags. One typo and your app breaks!

# Start redis (db for votes)
docker run -d --name=redis redis:alpine

# Start db (PostgreSQL)
docker run -d --name=db postgres:9.4

# Start vote app, link to redis
docker run -d --name=vote -p 5000:80 --link redis:redis voting-app

# Start result app, link to db
docker run -d --name=result -p 5001:80 --link db:db result-app

# Start worker, link to redis + db
docker run -d --name=worker --link redis:redis --link db:db worker

Now compare this to the Compose version later — 5 commands vs one file.

Docker Compose with Build

Instead of pulling a pre-built image from a registry (image:), you can tell Compose to build an image from a Dockerfile using the build: directive.

services:
  vote:
    build: ./vote           # Path to Dockerfile
    ports:
      - "5000:80"
    links:
      - redis

  result:
    build: ./result
    ports:
      - "5001:80"
    links:
      - db

  redis:
    image: redis:alpine   # Pre-built image - no build needed

  db:
    image: postgres:9.4

  worker:
    build: ./worker

When you run docker-compose up, Compose will:

  1. Build images for vote, result, and worker from their Dockerfiles
  2. Pull redis:alpine and postgres:9.4 from Docker Hub
  3. Start all 5 containers together on the same network

Docker Compose Versions

Compose file format has evolved. Here's the same voting app in all 3 versions:

Version 1 (Simple, no version key)

No networks, no depends_on. Relies on links like docker run --link.

# docker-compose.yml — Version 1
web:
  build: ./vote
  ports:
    - "5000:80"
  links:
    - redis

result:
  build: ./result
  ports:
    - "5001:80"
  links:
    - db

redis:
  image: redis:alpine

db:
  image: postgres:9.4

worker:
  build: ./worker
  links:
    - redis
    - db

Version 2 (Networking built-in)

Add version: '2'. depends_on replaces links. Every service is automatically on the same network.

version: '2'
services:
  vote:
    build: ./vote
    ports:
      - "5000:80"
    depends_on:
      - redis

  result:
    build: ./result
    ports:
      - "5001:80"
    depends_on:
      - db

  redis:
    image: redis:alpine

  db:
    image: postgres:9.4

  worker:
    build: ./worker
    depends_on:
      - redis
      - db

Version 3 (Swarm-ready)

Add version: '3'. Adds deploy section for Docker Swarm (replicas, restart policy, resource limits).

version: '3'
services:
  vote:
    build: ./vote
    ports:
      - "5000:80"
    depends_on:
      - redis
    deploy:
      replicas: 3

  result:
    build: ./result
    ports:
      - "5001:80"
    depends_on:
      - db

  redis:
    image: redis:alpine

  db:
    image: postgres:9.4

  worker:
    build: ./worker
    depends_on:
      - redis
      - db

Key differences:

  • V1 — No version key. Uses links. Top-level keys are service names.
  • V2 — version: '2'. services: is explicit. depends_on replaces links. Auto-networking.
  • V3 — version: '3'. Adds deploy, healthcheck, Swarm integration.

Compose with Networks

For better security, you can define custom networks and assign services to them. The voting app uses two networks: front-end and back-end.

version: '3'
services:

  vote:
    build: ./vote
    ports:
      - "5000:80"
    networks:
      - front-end
    depends_on:
      - redis

  result:
    build: ./result
    ports:
      - "5001:80"
    networks:
      - front-end
      - back-end
    depends_on:
      - db

  redis:
    image: redis:alpine
    networks:
      - back-end

  db:
    image: postgres:9.4
    networks:
      - back-end

  worker:
    build: ./worker
    networks:
      - back-end
    depends_on:
      - redis
      - db

networks:
  front-end:
  back-end:

Security benefit: The database and worker are only on back-end — they are never exposed to the browser-facing front-end network. The result service sits on both networks, acting as a bridge between them.

front-end network

vote, result

back-end network

redis, db, worker, result
