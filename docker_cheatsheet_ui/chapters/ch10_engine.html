Chapter 10: Docker Engine & Internals

What happens under the hood — architecture, namespaces, and cgroups

Architecture Namespaces cgroups

Docker Engine Architecture

The Docker Engine follows a modular client-server architecture with three distinct components:

CLI

docker run, build, pull

REST API

HTTP requests / responses

Daemon (dockerd)

Build, run, manage containers

When you type docker run nginx, the CLI translates your command into a REST API call and sends it to dockerd (the daemon). The daemon does the real work — pulling images, creating containers, and managing resources.

Behind the scenes of docker run nginx 
# 1. You type this:
$ docker run nginx

# 2. CLI sends REST API call to dockerd:
POST /containers/create  ← HTTP request to daemon

# 3. Daemon checks if image exists locally
#    If not → pulls from registry
#    Then → creates writable layer, starts container

# 4. Daemon sends response back to CLI
{ "Id": "abc123..." }    ← HTTP response

You can even run the CLI on one machine and the daemon on another:

$ docker -H=remote-docker-engine:2375 run nginx

Simple Analogy

CLI = remote control, Daemon = TV, REST API = infrared signal. You press a button on the remote (CLI), it sends an infrared signal (REST API), and the TV (daemon) changes the channel. The remote and TV don't need to be in the same room — you could point one remote at another TV.

Port 2375 is the default port for the Docker REST API (unencrypted). Port 2376 is used for TLS-encrypted communication.

Namespaces — Container Isolation

Namespaces are a Linux kernel feature that gives each container its own isolated view of the system. Every container thinks it's running on its own dedicated machine.

PID Namespace

Containers see only their own processes. PID 1 inside the container is not PID 1 on the host.

Network Namespace

Each container has its own network stack — own IP address, routing table, and ports.

Mount Namespace

Containers have their own filesystem. Changes inside don't affect the host.

UTS Namespace

Unix Timesharing — hostname isolation. Each container can have its own hostname.

When Docker starts a container, it creates a new set of namespaces for that container. The container sees only what's inside its own namespace:

# On the HOST — see all processes
$ ps aux | grep nginx
root      3201  ...  nginx: master process  ← PID 3201 on host

# Inside the CONTAINER — different view!
$ docker exec -it mynginx bash
root@mynginx:/# ps aux
root      1  ...  nginx: master process   ← Shows as PID 1!

The same process has PID 3201 on the host but PID 1 inside the container. That's the PID namespace in action — each container lives in its own process bubble.

IPC Namespace

InterProcess Communication isolation — containers can't access each other's shared memory or semaphores.

User Namespace

Map container's root user to a non-privileged user on the host for extra security.

Cgroup Namespace

Hides cgroup hierarchy — each container sees only its own resource limits.

Simple Analogy

Each container lives in its own "room" with its own view. The room has its own window (PID), its own phone line (network), its own furniture (filesystem), and its own room number (hostname). From inside the room, you can't see what's happening in other rooms — you only see your own space.

cgroups — Resource Limits

While namespaces provide isolation (what a container can see), cgroups (Control Groups) provide limitation — how much CPU, memory, and I/O a container is allowed to use.

Without cgroups, a single runaway container could consume all system resources and starve other containers (or even the host OS). cgroups prevent that by capping each container's consumption.

CPU Limit — half a core 
$ docker run --cpus=.5 ubuntu
# Container gets at most 50% of one CPU core
# Even if the host has 16 cores, this container
# can only use 0.5 cores worth of CPU time
Memory Limit — 100 MB 
$ docker run --memory=100m ubuntu
# Container is capped at 100 megabytes of RAM
# If it tries to use more, it gets OOM-killed
# (Out Of Memory killer stops it)

You can combine both limits for fine-grained control:

$ docker run --cpus=.5 --memory=100m --memory-swap=150m nginx

# ┌──────────┬────────────┐
# │ Resource │   Limit    │
# ├──────────┼────────────┤
# │ CPU      │ 0.5 cores  │
# │ Memory   │ 100 MB RAM │
# │ Swap     │ 150 MB max │
# └──────────┴────────────┘

You can also inspect which cgroups a container belongs to:

$ docker inspect mynginx --format '{{.HostConfig.CpuShares}}'
512                # ← relative CPU weight (default 1024 = 1 core)

$ docker inspect mynginx --format '{{.HostConfig.Memory}}'
104857600          # ← 100 MB in bytes

What happens without limits? One container could consume all CPU and memory, slowing or crashing other containers and even the host. cgroups ensure fair sharing.

Simple Analogy

Think of an apartment building with capped utilities. Each apartment (container) has a limit on electricity (CPU) and water (memory). You can use your fair share, but you can't crank the AC so high that everyone else goes without power. If you exceed your cap, the building shuts off your utility (OOM-kill).

Key Takeaways

CLI → REST API → Daemon. The CLI sends HTTP requests to dockerd which does the actual work

Namespaces isolate what a container can see — PID, network, mount, UTS, IPC

cgroups limit what a container can use — CPU via --cpus, memory via --memory

The -H flag lets you control a remote daemon from your local CLI
